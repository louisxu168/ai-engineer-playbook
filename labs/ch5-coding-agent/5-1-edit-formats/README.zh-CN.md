# 实验 5-1：Coding Agent 怎么改代码 —— 三种编辑格式

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. 一个 coding agent 最核心的工程决定：**让模型用什么格式说「改哪儿」**
> 2. 三种主流格式的**成本差 2.1 到 7.8 倍**——而且差多少取决于「改动占文件多大比例」
> 3. `whole_file` 的成本几乎**不随改动量变化**，只跟文件大小走；另两种正好相反
> 4. 「diff 格式容易对不上」这个说法，在实测里**没有复现**（两个任务、三种格式、零失败）
>
> **怎么学**：判据是**真的跑 unittest**——本仓库里最硬的判据，没有解释空间。
>
> **需要多久**：25 分钟（不联网）。
>
> ⚠️ 这个实验会**执行代码**（跑测试）。它跑的是 `workspace/` 的一份副本，
> 模型改不了测试文件。但**这不是沙箱**——真实项目请用容器。

---

## 先搞清楚问题是什么

你要写一个能改代码的 agent。模型读完文件，想把第 24 行改一下。

**它怎么把这件事告诉你的程序？**

这不是小事——它是 coding agent 里**最影响成败的一个设计选择**，三种主流做法：

```
whole_file      "这是这个文件修改后的完整内容：<130 行全文>"
search_replace  "把 `return ordered[middle]` 换成 `<新的三行>`"
line_range      "第 24 到 24 行，换成 `<新的三行>`"
```

三种都能用，真实产品各选了一种。这个实验让**同一个模型改同一个 bug**，
只换这一件事，然后量三个数：

| 量什么 | 为什么重要 |
|---|---|
| 测试过了没有 | **客观判据**——真的跑 unittest |
| 模型吐了多少字 | 三种格式的**成本**差别 |
| 编辑应用失败几次 | 三种格式的**可靠性**差别 |

## 这个实验的素材

`workspace/` 里有两个文件，你可以直接打开看：

- **`stats.py`** —— 一个 130 行的小统计库，**里面有一个 bug**
- **`test_stats.py`** —— 20 个单元测试，其中 3 个抓到了那个 bug

⚠️ **agent 不许改测试文件**。程序会在两个地方拦住它（提示词里说 + 代码里查）。

> 为什么要拦？因为「把测试改成期望错误答案」是让测试通过最省事的办法，
> 而 AI 写代码时**真的会这么干**。
>
> 这正好呼应实验 4-1 的结论：**能在接口层面拦住的约束，别只写在提示词里。**

### 两个难度不同的任务

```bash
python3 agent.py <模式>            # 默认 fix 任务
python3 agent.py <模式> refactor   # 难的那个
```

| 任务 | 要改几处 | 难在哪 |
|---|---|---|
| `fix` | **1 处，2 行** | 不难。这是三种格式的**最好情况** |
| `refactor` | **8 处** | 其中 7 处的上下文**几乎一模一样**，只有引号里的函数名不同 ★ |

`refactor` 那 7 处长这样，你先看一眼，想想哪种格式会最难受：

```python
    if len(numbers) == 0:
        raise ValueError("mean() 需要至少一个数")      # ← 这样的还有 6 处
```

> 这是做 agent 评测的基本功：**如果你不能手工验证"什么叫做对了"，
> 那你也没法自动判分。** 本仓库里判据最硬的就是这个实验——
> 因为「测试过不过」这件事，没有第二种解释。

## 第 1 步：跑简单任务，先看成本（6 分钟）

```bash
python3 agent.py all
```

### 🤔 先猜

三种格式，模型吐的字数比例大概是多少？ ___ : ___ : ___

### 👀 观察什么

对比表里的 **「模型输出」** 那一列。

### 💡 学到什么

差距比大多数人猜的大得多（具体数字见 SOLUTION）。

原因很简单，但值得说透：

```
whole_file      成本 ≈ 文件有多大        ← 和你改了多少【无关】
search_replace  成本 ≈ 改动有多大        ← 和文件多大【无关】
line_range      成本 ≈ 改动有多大（更省，因为连原文都不用重复）
```

> **这不是"省一点 token"的问题。**
> 你在一个 2000 行的文件里改 2 行，`whole_file` 要吐 2000 行。
> 而 agent 的循环可能要改十几轮。

## 第 2 步：跑难任务，看成本怎么变（6 分钟）★

```bash
python3 agent.py all refactor
```

### 🤔 先猜（这题是本实验的关键）

改动从 1 处变成 8 处，三种格式的成本**各自涨几倍**？

- `whole_file` 涨 ___ 倍
- `search_replace` 涨 ___ 倍

### 👀 观察什么

把两次 `all` 的「模型输出」放在一起比。

### 💡 学到什么

**`whole_file` 几乎没涨。** 另外两种涨了三四倍。

这就把那条规律坐实了：

> **`whole_file` 的成本由文件大小决定，`search_replace` / `line_range`
> 的成本由改动大小决定。**

推论——**它们的优劣是有交叉点的**：

| 场景 | 谁划算 |
|---|---|
| 大文件 + 小改动（**日常开发的常态**） | diff 类格式，能省一个数量级 |
| 小文件 + 大改动（重写、新建文件） | `whole_file`，而且更不容易错 |

**所以真实产品往往两种都留着**，按情况切换。

## 第 3 步：找它们的失败方式（5 分钟）

三种格式**能出什么错**，比它们省多少 token 更重要：

| 格式 | 会怎么失败 | 失败了你**知道**吗 |
|---|---|---|
| `whole_file` | 几乎不会——它给的就是最终结果 | —— |
| `search_replace` | `old` 抄错一个空格 → 找不到；或者 `old` 不唯一 | **知道，会明确报错** |
| `line_range` | 行号数错一行 | **☠ 不一定知道** |

**最后一行是重点。** 打开 `agent.py` 看 `apply_line_range()`：

```python
lines[start - 1:end] = new.split("\n")
```

行号偏一行，这行代码**照样能"成功"执行**——只是改错了地方。
`whole_file` 和 `search_replace` 出错会明确报错，**`line_range` 会安静地改坏**。

> 而且 `line_range` 还有个隐藏麻烦：**一次改多处时，前面的改动会让后面的行号全部错位。**
> 看 `apply_line_range()` 里那句「从后往前改」的注释——那不是优化，是**必须的**。

### ⚠️ 但要诚实：这次实测里，三种格式一次都没失败

两个任务 × 三种格式，**编辑应用失败 0 次**。

「diff 格式容易对不上」这个流传很广的说法，**在这个规模上没有复现**。

**这不代表它不存在**——它更可能出现在：更大的文件、更多处的改动、
更弱的模型、或者代码里有大量重复片段的时候。

但至少说明：**别把它当成不用验证就能照搬的定律。** 练习 1 会让你去找它的边界。

## 第 4 步：自己动手改（练习）

### 练习 1 ⭐⭐ 把它逼到失败

我没能让任何一种格式失败。**你来。** 几个方向：

- 把 `stats.py` 复制粘贴成 500 行（很多重复函数）→ `search_replace` 的 `old` 还唯一吗？
- 在 `fmt_line_range` 提示词里去掉「文件带了行号」那句 → 它还数得对吗？
- 把行号从 1 开始改成从 0 开始 → 看它错位没有

**成功了记下来**——那是个真实发现。

### 练习 2 ⭐ 让它作弊

把 `check_path()` 里那句拦截注释掉，重跑 `refactor`。

**先猜**：它会去改测试文件吗？

> 不管结果如何，都想清楚这件事：
> **你的 coding agent 有没有一条路径可以「改判据让自己通过」？**
> 这在真实项目里叫 reward hacking，而且它常常是无意的。

### 练习 3 ⭐⭐ 加第四种格式：unified diff

让模型直接输出标准的 `diff -u` 格式，用 `patch` 或手写解析器应用。

**先猜**：它的成本和可靠性会落在现有三种的哪个位置？

> 提示：unified diff 里**同时**有行号**和**上下文原文。
> 想想这意味着什么——它是在用冗余换容错。

### 练习 4 ⭐⭐⭐ 让它自己选格式

给模型两种格式都开放，让它自己决定这次用哪种。

**先猜**：它会怎么选？大改动时会切到 `whole_file` 吗？

> 这才是真实产品的做法。做完再想：**你怎么验证它选得对？**

### 练习 5 ⭐⭐⭐ 把测试从判据变成工具

现在测试是程序跑完再喂给模型的。改成**给它一个 `run_tests()` 工具**，
让它自己决定什么时候跑。

**先猜**：它会跑几次？会不会改一点就跑一次？

> 这是 coding agent 的另一个核心设计问题：**反馈由谁触发。**
> 回头看看实验 1-2——是同一个问题的另一个形态。

## 附：概念速查

### 三种格式的选型表

| | 成本随什么涨 | 出错时 | 适合 |
|---|---|---|---|
| `whole_file` | **文件大小** | 几乎不出错 | 新建文件、小文件、大重写 |
| `search_replace` | **改动大小** | 明确报错 | **日常改动（默认选它）** |
| `line_range` | **改动大小**（最省） | **可能静默改错** | 谨慎使用；一定要配复查 |

### 一条工程原则

> **让错误无法安静地发生。**
>
> `search_replace` 比 `line_range` 好，不是因为它更省或更准，
> 而是因为**它错的时候一定会告诉你**。

这条原则在实验 4-1 里也出现过（含糊的错误信息让 agent 分不清"被拒绝"和"执行了一半"）。
**可观测性不是奢侈品，它是正确性的前提。**

### 为什么这个实验的判据最硬

| 实验 | 判据 | 会误判吗 |
|---|---|---|
| 3-1 记忆 | 关键词 | 会（实测出现过） |
| 3-5 检索 | 集合包含 | 不会 |
| 4-1 工具 | 比对唯一正确调用 | 不会 |
| **5-1 改代码** | **真的跑 unittest** | **不会，而且它检查的是"行为"不是"形状"** |

> 前几个判据检查的是「输出长什么样」，这个检查的是「代码干了什么」。
> **这是评测 coding agent 唯一靠谱的方式**——也是为什么 SWE-bench 那类基准都跑测试。

## 卡住了？

| 你看到的 | 怎么办 |
|---|---|
| `✗ 没找到可用的后端` | 按屏幕上三个选项装任意一个 |
| `workspace/` 被改坏了 | 不会——程序每次跑都复制到 `.run_*/`，原件只读 |
| 想看它改完的代码 | 去 `.run_<模式>_<任务>/stats.py` |
| 某次跑出来和文档不一样 | **正常**，模型是随机的。看趋势，尤其看成本那一列 |
| 想看模型收到的原文 | 把 `SHOW_PROMPT` 改成 `True` |
| 忘了有哪些命令 | 敲 `python3 agent.py`（不带参数） |
