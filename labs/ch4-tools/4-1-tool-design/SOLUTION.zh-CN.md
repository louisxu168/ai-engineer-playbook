## 一、实测的 2×2

工单：`客户 alice@example.com 说她买的那副耳机是坏的，帮她退款。`
后端：Claude Code（`claude -p`），2026-07-28 实测。

|  | 错误信息有用 | 错误信息没用 |
|---|---|---|
| **描述写得好** | `good`：**✓ 3 轮，0 次失败** | `silent_errors`：**✓ 3 轮，0 次失败** |
| **描述写得烂** | `vague_desc`：**✓ 5 轮，3 次失败** | `both_bad`：**✗ 没办成** |

盯着这张表看十秒，能读出三件事：

### 1. 描述写好了，错误信息写不写无所谓

`good` 和 `silent_errors` 的数字**一模一样**：3 轮、3 次调用、0 次失败。

为什么？**因为模型一次都没错。** 错误信息再好，没触发就是零价值。

> 如果你只做了这一组对照（好描述 + 好错误 vs 好描述 + 烂错误），
> 你会得出结论：「错误信息不重要」。
>
> **这个结论是错的，而且错得很危险。**

### 2. 描述写烂了，错误信息才开始值钱 —— 而且它就是生与死的差别

同样是烂描述：

- `vague_desc`（错误信息有用）→ **办成了**，多花 2 轮
- `both_bad`（错误信息没用）→ **没办成**

**同一个变量（错误信息），在第一行毫无价值，在第二行决定成败。**

> 这在统计上叫**交互效应**：一个变量的作用，取决于另一个变量的取值。
>
> 工程上的教训是：**单独测一个变量会得出错误结论。**
> 你必须问「它在什么条件下起作用」，而不是「它有没有用」。

### 3. 错误信息是**第二道防线**，不是第一道

正确的读法：

```
好描述     →  防止犯错          （第一道防线）
好错误信息 →  犯错之后能恢复    （第二道防线）
```

两道都要有，但**顺序不能反**。指望靠错误信息教会模型怎么用你的工具，
等于让每个用户都先撞一遍墙——那几轮往返，本来只要在描述里多写两行就省掉了。

## 二、`vague_desc` 的三次失败：每一次都对应描述里缺的一句话

完整实测过程：

```
第 1 轮
  [思考] 先查 alice 的订单找到那副耳机，同时查退货政策，两件事互不依赖
  ✓ find_orders({"email": "alice@example.com", "days": 90})
     → {"orders": [{"order_id": "ORD-1001", "category": "electronics",
                    "amount_cents": 12990, "days_ago": 12, "item": "无线耳机"}, ...]}
  ✗ get_policy({"category": "headphones"})
     → 错误：category 必须是 electronics / clothing / food 之一，你传的是 "headphones"。
             这个值可以从 find_orders 返回的 category 字段直接照抄。

第 2 轮
  [思考] 政策查询的 category 要照抄订单里的值，耳机 ORD-1001 属于 electronics
  ✓ get_policy({"category": "electronics"})  → {"refund_window_days": 30}

第 3 轮
  ✗ issue_refund({"order_id": "ORD-1001", "amount": 12990,
                  "reason": "商品到货损坏（无线耳机），下单 12 天在 electronics …"})
     → 错误：缺少参数 amount_cents。issue_refund 需要这些参数：
             order_id, amount_cents, reason_code。

第 4 轮
  [思考] issue_refund 的实际参数名是 amount_cents 和 reason_code，按正确参数名重发
  ✗ issue_refund({"order_id": "ORD-1001", "amount_cents": 12990, "reason_code": "damaged"})
     → 错误：reason_code 必须是 DEFECTIVE / WRONG_ITEM / CHANGED_MIND 之一，
             你传的是 "damaged"。商品坏了用 DEFECTIVE。

第 5 轮
  ✓ issue_refund({"order_id": "ORD-1001", "amount_cents": 12990, "reason_code": "DEFECTIVE"})
     → {"ok": true, ...}
```

逐条对账：

| 第几次失败 | 栽在哪 | 描述里缺的那句话 |
|---|---|---|
| 1 | `category: "headphones"` | 「必须是 electronics / clothing / food 之一」 |
| 2 | 参数名写成 `amount` / `reason` | 正确的参数名（文档里写错了，见下） |
| 3 | `reason_code: "damaged"` | 「必须是 DEFECTIVE / WRONG_ITEM / CHANGED_MIND 之一」 |

**三次失败，三行文档。** 这就是工具描述的投入产出比。

> 顺带一提：这一组我不小心跑了两遍（第一次的补丁没打上），
> **两遍的结果完全一样**——5 轮、3 次失败、栽的还是那三个坑，连顺序都一样。
> 模型是随机的，但**「描述里缺什么，就在哪儿栽」这件事不随机**。

### ⚠️ 一个必须说清的设计缺陷

`tools_vague` 里写的是：

```
issue_refund(order_id, amount, reason)
```

而实际函数签名是 `issue_refund(order_id, amount_cents, reason_code)`。

**参数名是错的，不只是缺。** 严格来说这让 `vague_desc` 这一格同时改了两个东西：
「说明少」和「说明错」。这不是干净的单变量对照，我应该在设计时就分开。

但它反映的是真实情况——**文档和实现漂移**几乎在每个项目里都会发生。
练习 2 就是让你把这两件事拆开单独测。

> **顺带一个结论**：过时的文档比没有文档更糟。
> 没文档时模型会谨慎地试探；错文档时它会**自信地**走错路。
> 上面第 3 轮那次调用，模型完全没有怀疑，直接就按 `amount` 发了。

### 一个亮点：模型自己推出了单位

注意第 3 轮：描述里**从来没说过金额的单位**，但模型填的是 `12990`，不是 `129.9`。

因为它在第 1 轮见过这个：

```json
{"amount_cents": 12990}
```

**字段名教会了它。**

> **工具的返回值也是文档，而且是模型一定会读到的那份。**
>
> 直接可用的做法：
> - `amount_cents` 而不是 `amount`
> - `created_at_iso` 而不是 `time`
> - `duration_ms` 而不是 `duration`
> - `is_active` 而不是 `status`（布尔就别叫 status）
>
> 起对名字是**零成本**的文档 —— 它不占提示词预算，因为返回值本来就要传。

## 三、`both_bad` 那段交代：模型比工具设计更靠谱

这是本实验最该读的东西。完整过程：

```
第 1 轮
  ✓ find_orders(...)  → 找到 ORD-1001
  ✓ get_policy({"category": "electronics"})  → {"refund_window_days": 30}

第 2 轮
  [思考] 耳机 ORD-1001 是 12 天前购买，在电子产品 30 天退款窗口内，
         可以按损坏商品全额退 12990 分。
  ✗ issue_refund({"order_id": "ORD-1001", "amount": 12990, "reason": "商品到货损坏…"})
     → {"error": "调用失败。"}

第 3 轮
  [思考] 退款调用返回了一个没有细节的失败，**不确定是否真的没生效**，
         **重复调用有重复退款风险**，所以先重新查订单确认状态再决定是否重试。
  ✓ find_orders(...)  → 还是那两条订单，没有任何退款状态字段

第 4 轮
  [思考] 重查订单只返回了下单信息，没有任何退款状态字段，
         无法据此判断上一次 issue_refund 是否已经生效，
         所以在没有幂等保证的情况下不能盲目重试，交给人工确认支付侧记录。
```

然后它给出了这段交代（全文）：

> 情况交代：alice@example.com 的耳机 ORD-1001（无线耳机，129.90 元，12 天前下单）
> 属于电子产品，30 天退款窗口内，损坏全额退款是符合政策的，判定没问题。
> 但我发起 issue_refund 时工具返回了一个无细节的「调用失败」，我随后重查订单想确认状态，
> 结果 find_orders 只返回下单信息、不含任何退款/支付状态字段，
> **所以无法确定那笔退款到底是没执行、还是已执行但回包丢了。**
> 我没有再重试，因为 issue_refund 没有幂等键，**盲目重试有给客户重复退 129.90 元的风险**。
> 需要你做的：去支付/退款后台按 ORD-1001 查一下是否已有退款记录——
> 如果没有，直接重发一笔 12990 分、原因「商品到货损坏」的退款；如果已有，就不要再退。
> 另外建议给 issue_refund 加幂等键并让 find_orders 返回退款状态，否则这个坑还会再踩。

### 模型做错了什么吗？

**一件都没有。**

它的业务判断全对（订单、品类、窗口、金额、全额退），它失败的唯一原因是
**工具没告诉它发生了什么**，而它拒绝在这种情况下赌一把。

**这是正确行为。** 一个看到「调用失败」就无脑重试的 agent，会给客户退两次款。

> **这才是含糊错误信息真正的代价，而且和「多花几轮」完全不是一个量级：**
>
> 一句 `"调用失败。"` 没有区分开两种情况：
> - **被拒绝了，什么都没发生**（可以安全重试）
> - **执行了一半失败了**（重试会重复扣款）
>
> 对**只读**工具，这个区别不重要，大不了多查一次。
> 对**会改变世界**的工具（付款、退款、发邮件、删数据），
> 这个区别就是「能不能自动恢复」和「必须叫人来」的分界线。

### 推论：写工具的时候，先分清读和写

| | 错误信息含糊的代价 |
|---|---|
| 只读工具（查询、搜索） | 多几轮往返，浪费 token |
| 写入工具（付款、删除、发送） | **agent 卡死，必须人工介入**——而且这是它能做的最好选择 |

所以：**优先把错误信息的力气花在会产生副作用的工具上。**

而更根本的解法，模型自己说出来了：**幂等键**。
有了幂等键，「不确定成没成」就不再是死局——重试是安全的。练习 3 会让你做一遍。

> **有些问题不该靠提示词解决，该靠接口设计解决。**

## 四、练习答案

### 练习 1 ⭐ 只补一句话

实测（在练习 2 已经修好参数名的基础上，再补一行 `reason_code` 枚举）：

```
✓ find_orders(...)
✗ get_policy({"category": "DEFECTIVE"})        ← 见下，这次很有意思
✓ get_policy({"category": "electronics"})
✓ issue_refund({..., "reason_code": "DEFECTIVE"})    ← 一次就对
用了 3 轮，工具调用 4 次，其中失败 1 次
```

**`reason_code` 那次失败没了。** 一行字，省一轮往返。

但请看那次剩下的失败：模型把 `DEFECTIVE` 填进了 **`category`**。

**它拿了我唯一写出来的那个枚举，填进了我没写的那个槽位。**

> **这是个真实存在的坑：部分文档会误导。**
> 一份「只写了一半」的文档，比完全不写更容易让模型把已知信息**用错地方**——
> 因为它现在手上有一个看起来很正式的枚举值，而另一个参数它一无所知。
>
> 实践含义：**枚举要么全写，要么别指望模型自己分得清哪个枚举属于哪个参数。**

### 练习 1 附：把三个变体放一起看

| 版本 | 轮数 | 失败次数 | 还栽在哪 |
|---|---|---|---|
| `vague_desc` 原样 | 5 | 3 | category 枚举、参数名、reason 枚举 |
| 只修参数名（练习 2） | 4 | 2 | category 枚举、reason 枚举 |
| 修参数名 + 补 reason 枚举 | 3 | 1 | category 枚举 |
| `good` | 3 | **0** | —— |

**一条干净的阶梯，而且每一级都对应一处具体的文档缺失。**

> 反过来想：你的工具被调用一万次，你在描述里省下的那一行，
> 要被这一万次分摊着重新付出去。

### 练习 2 ⭐⭐ 分清「写得少」和「写得错」

把 `tools_vague` 第 3 行改成正确的参数名：

```python
3. issue_refund(order_id, amount_cents, reason_code) —— 处理退款
```

实测：**5 轮 3 次失败 → 4 轮 2 次失败**。参数名那次没了，
`category` 和 `reason_code` 两个枚举还在：

```
✓ find_orders(...)
✗ get_policy({"category": "headphones"})              ← 枚举没列
✓ get_policy({"category": "electronics"})
✗ issue_refund({..., "reason_code": "damaged"})       ← 枚举没列
✓ issue_refund({..., "reason_code": "DEFECTIVE"})
```

这就把两个变量拆开了：

| | 缺失的信息 | 后果 |
|---|---|---|
| **写得少**（枚举没列） | 模型不知道有哪些值 | 猜一个合理的（`"headphones"`、`"damaged"`），失败，然后改对 |
| **写得错**（参数名过时） | 模型以为自己知道 | **完全不怀疑**，直接按错的发 |

> 差别在于**模型有没有意识到自己在猜**。
> 缺信息时它知道自己在猜，会准备好被纠正；
> 错信息时它以为自己有信息，不会准备。
>
> 所以：**宁可不写，也别写错。** 而更实际的做法是：
> **让文档从代码生成**，别手写——手写的一定会漂移。

### 练习 3 ⭐⭐⭐ 加幂等键

参考实现：

```python
REFUND_LOG = {}      # idempotency_key -> 上次的返回结果

def tool_issue_refund(args, good_errors):
    key = args.get("idempotency_key")
    if key is None:
        return error(good_errors, "err_good_missing", param="idempotency_key", ...)
    if key in REFUND_LOG:
        return REFUND_LOG[key]        # ★ 同一个 key 直接返回上次的结果，不重复退款

    ... 原来的校验和退款逻辑 ...

    REFUND_LOG[key] = result
    return result
```

加了之后 `both_bad` 还会卡死吗？**大概率不会。** 因为「重试是安全的」这件事
现在写在接口里了：模型即使不知道上次成没成，重试一次也不会造成损失。

> **这道题真正的意思是：**
> `both_bad` 的死局，表面看是「错误信息太差」，
> 根子上是「这个接口不允许在不确定的情况下重试」。
>
> 改错误信息是在**缓解症状**；加幂等键是在**移除病因**。
>
> 一个更一般的判断法：
> **如果你的解法是「把这件事在提示词里说清楚」，先停一下，
> 问问能不能让它在接口层面根本不可能出错。**

### 练习 4 ⭐⭐⭐ 把错误信息改成「过度详细」

结果通常是：**成功率不变，token 明显变多。**

原因很简单——模型需要的是**这一次错在哪**，不是这个 API 的全部知识。
把整份文档贴进错误里，等于每犯一次错就把文档重发一遍。

> **好的错误信息是「针对性」的，不是「全面」的。**
>
> 三件事就够了：
> 1. 什么错了　2. 你传的是什么　3. 该怎么改
>
> 再多的，属于工具描述该干的活 —— 而且**描述只发一次，错误信息可能发很多次**。
> 把长内容放在只发一次的地方，这是纯粹的成本问题。

### 练习 5 ⭐⭐⭐ 换个办不成的工单

`alice@example.com 要退她买的咖啡豆。` ——ORD-1002 是食品，窗口 7 天，
40 天前下单，**按政策就是不能退**。

- **`good` 模式**：会明确告诉你「过了退款窗口，不能退」，因为错误信息里写清了
  「订单 ORD-1002 属于 food 品类，退款窗口是 7 天，但它是 40 天前下的单，已经超期」。
  它会把这件事作为**结论**交代出来。

- **`both_bad` 模式**：只会得到「调用失败。」，它没法区分
  「政策不允许」和「我参数填错了」，于是很可能一直试不同的参数组合，
  最后交代「我搞不定这个工具」。

**这才是最要命的地方**：

> 这两种情况在你的监控里长得**一模一样**：都是「agent 没完成任务」。
>
> 但一个是**系统工作正常**（政策就是不允许），
> 另一个是**系统坏了**（工具没法用）。
>
> **含糊的错误信息让你失去了区分这两者的能力。**

所以生产环境的做法是：**把「业务拒绝」和「调用错误」用不同的形状返回**，
比如：

```python
{"ok": False, "reason": "POLICY_WINDOW_EXPIRED", "detail": "..."}   # 业务拒绝，别重试
{"error": "...", "retryable": True}                                  # 调用错误，改了再来
```

模型能区分，你的监控也能区分。

## 五、可以直接抄走的清单

写一个工具的时候，对着过一遍：

**描述**
- [ ] 每个参数的**类型 + 单位**（分/元、秒/毫秒、UTC/本地）
- [ ] **取值范围**（max 90、必须为正）
- [ ] **枚举值全部列出**，别指望模型猜
- [ ] 给**例子**（`"alice@example.com"` 胜过「邮箱地址」）
- [ ] 说清**这个值从哪来**（「照抄 find_orders 的 category」）
- [ ] **不可逆操作**明确标注

**返回值**
- [ ] 字段名**自带单位**（`amount_cents` / `duration_ms` / `created_at_iso`）
- [ ] 写入类工具返回**足以判断是否已生效**的信息

**错误信息**
- [ ] 说清 ①什么错了 ②你传的什么 ③怎么改
- [ ] **业务拒绝**和**调用错误**用不同形状区分开
- [ ] 写入类工具：明确 **能不能重试**

**接口本身**
- [ ] 有副作用的操作，考虑**幂等键**
- [ ] 文档**从代码生成**，不要手写（手写必漂移）
