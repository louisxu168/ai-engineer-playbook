## 一、实测结果总览

任务：`分析这批日志，告诉我哪个用户触发的错误最多，是什么错误。`
后端：Claude Code（`claude -p`），2026-07-28 实测。

| 模式 | 泄露 | 任务 | 模型指认的用户 |
|---|---|---|---|
| `raw` | ☠ **5 类真实敏感信息进入上下文** | ✓ 完成 | `zhang.wei@example.com` |
| `redacted` | ✓ 零泄露 | ✗ **做不成** | —（明确说"做不到"） |
| `tokenized` | ✓ 零泄露 | ✓ 完成 | `USER_1` |

**这是本仓库里第一个「教科书式预期完全复现」的实验。** 前面几个实验的
预期失败模式经常没出现（见 1-1 / 1-3 / 2-1 的 SOLUTION），这一个没有——
因为这里的机制不是概率性的，是**信息论层面的**：信息被删掉了，就是真没了。

## 二、三种模式的完整实测输出

### `raw` —— 任务能做，代价是全泄露

```
====================================================================
  第 1 轮 / 共 6 轮     模式：raw
  处理方式：不处理，日志原样发给模型
====================================================================

  正在问模型… 用了 6.5 秒

  [思考] 先取最近日志再分析错误分布

  [工具] fetch_logs()
  ┌─ 模型看到的日志（前 4 行）─────────────────
  │ 2026-07-28 09:12:03 INFO  user=zhang.wei@example.com action=login ip=10.0.3.44 ok
  │ 2026-07-28 09:12:41 ERROR user=zhang.wei@example.com action=checkout code=PAYMENT_TIMEOUT
  │ 2026-07-28 09:13:02 INFO  user=li.na@example.com action=login ip=10.0.3.51 ok
  │ 2026-07-28 09:14:19 ERROR user=zhang.wei@example.com action=checkout code=PAYMENT_TIMEOUT
  └────────────────────────────────────────────
  ─── 这一轮往上下文里放了什么 ───
  ☠ 真实敏感信息 5 条进入上下文：API 密钥 ×1、银行卡号 ×1、邮箱地址 ×3、电话号码 ×1、内网 IP ×3
```

第 2 轮给出答案（节选）：

> 触发错误最多的用户是 **zhang.wei@example.com**，共 5 次错误，全部是
> action=checkout 的 PAYMENT_TIMEOUT（支付超时）……
>
> 另外发现日志中有敏感信息泄露，需要单独处理：DEBUG 行明文打印了 API key
> （sk-FAKE-… /pay）、未脱敏的银行卡号（card=4111-…，masked_ok=false），
> WARN 行含明文电话号码。**建议立即轮换该 API key**，并修复日志脱敏逻辑。

**注意最后这段——这是本实验最好的一个反讽：**

模型不但把 API key 收进了上下文，还非常专业地建议你「立即轮换」。
**它说得对。** 而它之所以能给出这条建议，正是因为它看到了那个 key。

> 这一段可以直接拿去说服同事：**你能读到的东西，模型也读到了。**

### `redacted` —— 零泄露，但任务死了

```
  [工具] fetch_logs()
  ┌─ 模型看到的日志（前 4 行）─────────────────
  │ 2026-07-28 09:12:03 INFO  user=[已脱敏] action=login ip=[已脱敏] ok
  │ 2026-07-28 09:12:41 ERROR user=[已脱敏] action=checkout code=PAYMENT_TIMEOUT
  │ 2026-07-28 09:13:02 INFO  user=[已脱敏] action=login ip=[已脱敏] ok
  │ 2026-07-28 09:14:19 ERROR user=[已脱敏] action=checkout code=PAYMENT_TIMEOUT
  └────────────────────────────────────────────
  ─── 这一轮往上下文里放了什么 ───
  ✓ 没有任何真实敏感信息进入上下文
```

答案（节选）：

> **无法确定"哪个用户"触发错误最多**——日志中所有 user 字段都被统一替换成了
> `[已脱敏]`，同一个占位符既可能是一个人也可能是多个人，没有任何可区分的标识
> （ip、session id 等也同样脱敏），所以按用户聚合在这批数据上是做不到的。
> **任何"某某用户触发最多"的结论都会是编造。**
>
> 能确定的是错误分布：共 7 条 ERROR。
> - PAYMENT_TIMEOUT，5 条，全部发生在 action=checkout……
> - UPSTREAM_5XX，2 条，均在 action=refund……
>
> 若需要按用户定位，请提供保留了用户标识（**哈希/伪匿名化即可，不必是明文**）的日志。

```
  ─── 任务完成得怎么样 ───
  ✗ 分不清是哪个用户 —— 脱敏脱过头了，任务做不成
```

**三个值得停下来看的点：**

1. **它没有编。** 它明确说了「任何结论都会是编造」。这是好模型的表现，
   但**不能指望**——换个模型、换个措辞，它完全可能随便挑一个 `[已脱敏]` 说
   「就是这个用户」。如果你的运行结果是那样，那不是 bug，那是**更值得记住的一课**：
   *脱敏脱过头，会把「无法回答」变成「幻觉」。*

2. **它退而求其次给出了能给的东西**（按错误码聚合）。这提示了一个真实设计选择：
   如果你的任务只需要「今天有几类错误」，`redacted` 是完全够用的，而且最安全。
   **不是所有任务都需要区分实体。**

3. **它自己提出了解法**：「哈希/伪匿名化即可，不必是明文」。
   这正是 `tokenized` 在做的事。

### `tokenized` —— 两头兼顾

```
  [工具] fetch_logs()
  ┌─ 模型看到的日志（前 4 行）─────────────────
  │ 2026-07-28 09:12:03 INFO  user=USER_1 action=login ip=IP_1 ok
  │ 2026-07-28 09:12:41 ERROR user=USER_1 action=checkout code=PAYMENT_TIMEOUT
  │ 2026-07-28 09:13:02 INFO  user=USER_2 action=login ip=IP_2 ok
  │ 2026-07-28 09:14:19 ERROR user=USER_1 action=checkout code=PAYMENT_TIMEOUT
  └────────────────────────────────────────────
  ─── 这一轮往上下文里放了什么 ───
  ✓ 没有任何真实敏感信息进入上下文
  ┌─ 令牌映射表（只存在你本地，不发给模型）─────
  │ KEY_1  ->  sk-FAKE-9f2b1c4d8e7a6350
  │ CARD_1  ->  4111-1111-1111-1111
  │ USER_1  ->  zhang.wei@example.com
  │ USER_2  ->  li.na@example.com
  │ USER_3  ->  wang.tao@example.com
  └────────────────────────────────────────────
```

答案（节选）：

> 错误最多的用户是 **USER_1**，共 5 次错误，全部是 action=checkout 的
> PAYMENT_TIMEOUT（支付超时），时间集中在 09:12–09:24 之间且反复重试。
> 次之是 **USER_2**，2 次 action=refund 的 UPSTREAM_5XX。**USER_3** 无错误记录。
>
> 判断：这不是单用户的偶发问题，而是支付链路异常——USER_1 连续 5 次同一错误码，
> 加上 09:15 有一条指向 /pay 的 outbound 调用（apikey=KEY_1）……
>
> 另注意两条与错误无关但需关注的记录：09:19 WARN 提示需人工审核联系 PHONE_1；
> 09:23 DEBUG 显示 **CARD_1 的 masked_ok=false**，即卡号脱敏未生效，属于日志
> 合规隐患，建议一并修复。

```
  ─── 任务完成得怎么样 ───
  ✓ 分辨出了具体是哪个用户（答案里出现 USER_1）
```

**这一段是本实验最漂亮的地方，值得逐句看：**

- 它做出了 `raw` 模式下**同样质量的分析**（同样的 5 次、同样的根因判断）
- 它**引用了 KEY_1 和 CARD_1 来做推理**——「有个外呼用了某个 key」「有张卡脱敏失败了」
- 但它**不知道那个 key 是什么，也不知道那张卡是谁的**

> **这就是「同一性 vs 身份」的分离在实战中长什么样。**
>
> 分析这件事从头到尾不需要知道 zhang.wei 是谁，只需要知道
> 「这 5 条是同一个人」。

而映射表在你本地。真要发工单通知 zhang.wei，你在自己的代码里查表即可——
**那一步不发生在上下文里。**

## 四、练习答案

### 练习 1 ⭐ 加一类新的敏感信息

不加规则直接跑：**程序会报「零泄露」，但身份证号明明还在日志里。**

这是本练习真正的教学点：**`count_leaks()` 只能数它认识的东西。**
「零泄露」这个结论，可靠性完全等于你规则表的完备性。

加规则（放在 `USER` 之前，因为它是长的、具体的）：

```python
(r"\b\d{17}[\dXx]\b", "IDCARD", "身份证号"),
```

> 推而广之：**任何「我们的扫描器没报警」都只等于「我们没扫这个」。**

### 练习 2 ⭐⭐ 把电话规则写松一点，再挪到前面

把电话规则换成 `r"\d{3}-\d{4}"` 并移到 `CARD` 之前，实测结果：

```
2026-07-28 09:19:40 WARN  contact phone=+1-PHONE_1 for manual review
2026-07-28 09:23:09 DEBUG card=4PHONE_2-1PHONE_2 masked_ok=false
```

映射表：

```
PHONE_1 -> 555-0142        ← 只吃掉了后半截，+1- 留在了外面
PHONE_2 -> 111-1111        ← 这根本不是电话号，是卡号的中段
```

两处都坏了，而且坏的方式不一样：

1. **电话号只脱了一半**，`+1-` 留在原文里（这次无害，换成完整区号就是泄露）
2. **卡号被从中间切开**：`4111-1111-1111-1111` 里的 `111-1111` 被当成电话吃掉，
   剩下 `4` 和 `-1` 两个碎片留在上下文里

第 2 条真正致命的地方在最后一行输出：

```
leaks reported: []
```

**程序报告「零泄露」。** 因为 `count_leaks()` 的卡号规则要求完整的 4-4-4-4，
碎片它认不出来。你会拿到一份干净的体检报告，而卡号的一部分确实发出去了。

> 两条规律，都不只适用于脱敏：
>
> 1. **先匹配长的、具体的，再匹配短的、宽泛的**——分词、URL 路由、词法分析同理
> 2. **用同一套规则去做「脱敏」和「验证脱敏效果」，等于自己给自己判卷**
>    ——生产环境里这两套规则应该独立编写，最好由不同的人写

### 练习 3 ⭐⭐ 让占位符不稳定

改成每次出现都发新号，实测：

```
2026-07-28 09:12:03 INFO  user=USER_1 action=login ip=IP_1 ok
2026-07-28 09:12:41 ERROR user=USER_2 action=checkout code=PAYMENT_TIMEOUT
2026-07-28 09:13:02 INFO  user=USER_3 action=login ip=IP_2 ok
2026-07-28 09:14:19 ERROR user=USER_4 action=checkout code=PAYMENT_TIMEOUT
...
leaks: []
distinct USER tokens: 11        ← 真实用户只有 3 个
```

- **泄露：还是零。** 真实值一样没进上下文。
- **任务：做不成了。** 3 个真人被打散成 11 个互不相干的占位符，
  和 `redacted` 一个下场：没法聚合。

> 所以「零泄露」根本不是充分条件。`redacted` 零泄露，不稳定令牌化也零泄露，
> 但两个都没用。**真正的判据是：泄露 = 0 **且** 任务 = 成。**

### 练习 4 ⭐⭐⭐ 从黑名单改成白名单

参考实现：

```python
ALLOWED_FIELDS = ["action", "code"]   # 只放行这些字段

def allowlist(text):
    """只保留时间戳、级别、令牌化后的 user，以及白名单字段。"""
    tokenized_text, mapping = tokenize(text)
    out = []
    for line in tokenized_text.split("\n"):
        parts = line.split()
        kept = parts[:3]                       # 日期、时间、级别
        for p in parts[3:]:
            if "=" not in p:
                continue
            key = p.split("=")[0]
            if key == "user" or key in ALLOWED_FIELDS:
                kept.append(p)
        out.append(" ".join(kept))
    return "\n".join(out), mapping
```

实测输出：

```
2026-07-28 09:12:03 INFO user=USER_1 action=login
2026-07-28 09:12:41 ERROR user=USER_1 action=checkout code=PAYMENT_TIMEOUT
2026-07-28 09:13:02 INFO user=USER_2 action=login
2026-07-28 09:15:33 DEBUG                            ← 整行只剩时间和级别
2026-07-28 09:19:40 WARN
2026-07-28 09:23:09 DEBUG
...
leaks: []
```

`ip=`、`apikey=`、`phone=`、`card=` **全都自动没了**——
你一条规则都没为它们写。第 5 / 9 / 13 行直接被清空到只剩时间戳，
因为它们**整行都不在白名单里**。

新增一个 `ssn=` 字段呢？也自动没了。**这才是关键差别：**

| | 你要穷举的东西 | 新字段出现时 |
|---|---|---|
| 黑名单 | 所有风险（无穷、会增长） | **默认泄露** |
| 白名单 | 你的需求（有限、你自己定的） | **默认拦下** |

> 安全设计里叫 **fail-closed**（出错时关闭）。
> 黑名单是 fail-open，这是它的结构性缺陷，和写得好不好无关。

代价：任务需要新字段时你得改代码。**这个代价是对的**——它逼你在加字段时
想一遍「这个该不该给模型看」。

### 练习 5 ⭐⭐⭐ 让 agent 自己申请解码

参考实现：

```python
def reveal(token, mapping, audit_log):
    """agent 申请解码某个令牌。每次都记审计日志。"""
    audit_log.append(token)
    print("  ⚠ agent 申请解码：" + token)
    if token.startswith("KEY_") or token.startswith("CARD_"):
        return {"error": "拒绝：密钥和卡号任何情况下都不解码"}
    return {"value": mapping.get(token, "未知令牌")}
```

**「解决了还是挪了个地方」——两者都是，而这正是答案。**

挪了的部分：真实值一旦解码就进了上下文，泄露照旧发生。

解决了的部分，有三条，每条都是真实收益：

1. **从默认泄露变成了默认不泄露。** 需要才给，而不是先全发再说。
2. **有审计线索了。** 你现在能回答「上周 agent 一共看了几个真实邮箱」——
   `raw` 模式下这个问题连问都没法问。
3. **可以按类型分级。** 上面那段代码里，`KEY_` 和 `CARD_` **永远不解码**，
   因为没有任何日志分析任务需要真实的密钥。

> 真实系统里这一层通常还有第四条：**解码要人工审批**，或者只在
> 「agent 已经给出结论、需要落地执行」时才允许。
>
> 这就是**最小权限原则**在上下文工程里的样子。

## 五、这个实验和 2-2 的关系（想清楚这个，第二章就通了）

第二章三个实验，正好是上下文的三种失效方式：

| 实验 | 失效方式 | 解法的性质 |
|---|---|---|
| 2-1 压缩 | 上下文**装不下** | 工程取舍（省 token vs 丢信息） |
| 2-2 注入 | 上下文**被投毒** | **结构性**防御（声明边界），过滤无效 |
| 2-3 脱敏 | 上下文**装了不该装的** | **过滤有效**（+ 白名单更好） |

2-2 和 2-3 的表面矛盾（「正则没用」vs「正则有用」）是本章最值得带走的一课：

> **有没有一个会适应你规则的对手，决定了你的防御能不能靠枚举。**

- 邮箱格式不会因为你写了正则就变形 → 枚举可行
- 攻击者的措辞会因为你写了正则就变形 → 枚举必败

判断一个安全方案靠不靠谱，第一个该问的问题永远是：**对手会不会适应？**
