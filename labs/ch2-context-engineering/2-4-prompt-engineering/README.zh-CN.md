## 先说结论：我没能复现书里那条

原书实验 2-4 的招牌结论是：

> 把规则的**内容全部保留**，只是**打乱组织结构、去掉标题层次**，
> 任务成功率**下降超过 30%**。

我重做了这个实验，**在两个模型上都没能复现**：

| | baseline | shuffled | 差别 |
|---|---|---|---|
| 前沿模型（Claude Code） | 违规 0/3 | 违规 0/3 | **没有差别** |
| 本地 0.6B | 违规 1/3，但死循环 | 违规 1/3，但死循环 | **淹没在噪声里** |

**但这个"失败"是有内容的**，下面会讲清楚为什么。

## 实验设计

一个航空客服 agent，正确流程**顺序是硬性的**：

```
verify_identity  →  check_policy  →  escalate_to_supervisor  →  issue_refund
                                     （仅当金额 > 40000 分）
```

订单金额是 48600 分，**所以审批那步一定要走**。

### 五种模式，规则内容完全一样

| 模式 | 改了什么 |
|---|---|
| `baseline` | 无。有标题层次、有编号、有明确先后顺序 |
| `shuffled` | **同样的 10 条句子**，打乱顺序、去掉标题和编号 ★ |
| `tone_hype` | 只加一句「说话要极度自信、夸张」 |
| `tone_casual` | 只加一句「轻松点，多用 emoji 😊」 |
| `no_tool_desc` | 工具只留函数签名，删掉所有描述文字 |

**`shuffled` 一条规则都没删**——你可以自己验证：

```bash
python3 -c "import agent; print(agent.rules_shuffled(0))"
```

### 判据是机械的

```
违规 A：没验证身份就调 issue_refund
违规 B：金额超阈值、没转主管就调 issue_refund   ← ★ 真正的判据
```

程序记录调用顺序，比对即可。

### 💡 学到什么

**书里 2024 年的结论，在 2026 年的前沿模型上不成立了。**

这不奇怪——模型在两年里变强了很多。但更值得想的是**为什么**：

> 打乱顺序并**没有删掉任何信息**。模型要做的只是「把 10 条散落的规则
> 重新理出优先级和依赖」——**而这恰恰是它现在很擅长的事。**

## 第 1 步：一个设计判据的硬教训（5 分钟）★

我做这个实验时改了**三版**判据，前两版都测不出东西：

### 第 1 版：「先验证身份再退款」

**五种模式全 0 违规。** 为什么？

> **因为「先验证再退款」本来就符合模型的先验。** 它根本不需要那条规则——
> 你把规则打乱、甚至整条删掉，它照样会先验证。
>
> **一条模型本来就会遵守的规则，测不出提示词写得好不好。**

### 第 2 版：加了「大额必须转主管」

这条是**任意的**——阈值 40000 是我编的，模型凭常识猜不到，
**只能从提示词里读到**。

**结果还是 0 违规。** 前沿模型即使在打乱的规则里也找得到它。

### 第 3 版：换成弱模型

`--weak` 用本地 qwen3:0.6b 跑同一套：

```bash
python3 agent.py all --weak      # 需要 Ollama，见实验 2-1
```

**这次有违规了（1/3），但没用**——因为 0.6B 陷在了别的失败里：
它会连着调用 `verify_identity` 八次，卡死在第一步。

> **信号被"模型根本做不动这个任务"淹没了。**

### 结论

```
前沿模型   太强 → 打乱也不影响 → 测不出差别
0.6B      太弱 → 因为别的原因失败 → 信号被淹没
          ↑
    书里那个效应住在【中间】某个能力区间，而我手上没有那个区间的模型
```

> **这才是这个实验真正教的东西：**
> **一条经验往往有它的「适用区间」，而大多数文章不会告诉你区间在哪。**
>
> 而你现在有一个现成的测量工具——**练习 3 让你拿它去测你自己项目用的那个模型。**

## 第 2 步：唯一一个复现了的维度（4 分钟）

对比 `no_tool_desc` 和其他四种的「工具报错」次数：

| | 前沿模型 | 0.6B |
|---|---|---|
| 其他四种 | 0 次 | 1 ~ 19 次 |
| `no_tool_desc` | **1 次** | **24 次** |

**方向一致：删掉工具描述，工具调用错误变多。**

书里说这一维「错误率增加 45%」。我这里样本太小说不上百分比，
但**方向在两个模型上都成立**。

> 而这条和[实验 4-1](../../ch4-tools/4-1-tool-design/README.zh-CN.md)的结论完全吻合——
> 那个实验用 2×2 消融专门测了这一维，结论是：
> **工具描述里省下的每一行，都会在调用时被重新付出去。**
>
> **三个维度里，只有「工具描述」这一维在 2026 年仍然稳定成立。**

## 第 3 步：自己动手改（练习）

### 练习 1 ⭐ 验证 shuffled 真的没删东西

```bash
python3 -c "import agent; print(agent.rules_structured())"
python3 -c "import agent; print(agent.rules_shuffled(0))"
```

数一数两边的规则条数。

> 这一步是**消融实验的基本功**：你必须能证明自己只动了一个变量。
> 否则测出来的差别归因不了。

### 练习 2 ⭐⭐ 让规则更多、更绕

现在只有 10 条规则。加到 40 条，并且让其中两条**互相依赖**
（比如「A 情况下走流程甲，但如果同时满足 B 则走流程乙」）。

**先猜**：规则多到什么程度，打乱才开始有影响？

> 书里的 τ-bench 场景规则数量远多于 10 条。**这可能就是差别所在。**

### 练习 3 ⭐⭐⭐ 测你自己项目里那个模型 ★

把 `_ask()` 换成你项目实际用的模型（GPT、Gemini、某个开源 7B…），
跑一遍这五种模式。

**这才是你真正需要的数字。**

> 因为这个实验已经证明了：**这条经验的成立与否，取决于模型。**
> 我的结果对你没有参考价值，**但这套测量方法有。**

### 练习 4 ⭐⭐ 把 tone 推到极端

现在的 `tone_hype` 只加了一句话。试着把整个系统提示词都改写成
那种语气（规则本身也用夸张的口吻写）。

**先猜**：语气会开始影响正确率吗？

> 书里说「语气影响有限」。**但那是在语气和规则分开的前提下。**
> 如果语气侵入了规则的表述本身呢？

## 附：概念速查

### 消融实验的三条纪律

1. **一次只动一个变量**——本实验的 `shuffled` 一条规则都没删
2. **判据要能被程序看见**——调用顺序可以，「回答质量」不行
3. **判据必须是模型不会默认遵守的**——否则你测的是它的先验，不是你的提示词

第 3 条是我踩了两次才学会的。

### 什么时候该做消融

> 当 agent 表现不好时，**与其全面重写提示词，不如先做消融**：
> 逐项关掉各个组件，看哪个影响最大。
>
> 这比凭感觉猜可靠得多——而且**大多数人凭感觉先改的是语气，
> 而语气恰恰是最不重要的那一维。**
