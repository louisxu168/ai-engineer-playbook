## 一、实测数据

后端：Claude Code（`claude -p`），2026-07-28 实测。

### `fix` 任务（改 1 处，2 行）

| 格式 | 测试 | 轮数 | 模型输出 | 编辑失败 |
|---|---|---|---|---|
| `whole_file` | ✓ 20/20 | 1 | **3204 字** | 0 |
| `search_replace` | ✓ 20/20 | 1 | **411 字** | 0 |
| `line_range` | ✓ 20/20 | 1 | **265 字** | 0 |

### `refactor` 任务（改 8 处，其中 7 处上下文几乎一样）

| 格式 | 测试 | 轮数 | 模型输出 | 编辑失败 |
|---|---|---|---|---|
| `whole_file` | ✓ 29/29 | 1 | **3413 字** | 0 |
| `search_replace` | ✓ 29/29 | 1 | **1603 字** | 0 |
| `line_range` | ✓ 29/29 | 1 | **1194 字** | 0 |

**六次运行，全部一轮通过，零编辑失败，三种格式改出来的代码完全一样。**

## 二、最有价值的一个数：成本增长倍数

把两个任务并排：

| 格式 | fix | refactor | **涨了几倍** |
|---|---|---|---|
| `whole_file` | 3204 | 3413 | **1.07×** ← 几乎没涨 |
| `search_replace` | 411 | 1603 | **3.9×** |
| `line_range` | 265 | 1194 | **4.5×** |

**改动量翻了 8 倍，`whole_file` 只涨了 6.5%。**

因为它吐的是**整个文件**——改 2 行和改 20 行，输出几乎一样长。

这就得到了本实验最该记住的一条：

> ```
> whole_file      成本 ≈ O(文件大小)      与改动量无关
> search_replace  成本 ≈ O(改动大小)      与文件大小无关
> line_range      成本 ≈ O(改动大小)，常数更小
> ```

### 推论：它们的优劣有交叉点

看这两个比值：

```
fix 任务：       whole_file / search_replace = 7.8 倍
refactor 任务：  whole_file / search_replace = 2.1 倍
```

**改动越大，diff 格式的优势越小。** 一直推下去：当改动接近整个文件时，
`whole_file` 反而更划算（还更不容易错）。

反过来推更有意思：本实验的文件只有 **130 行**。真实代码文件动辄几百上千行。

```
130 行的文件，改 2 行   → whole_file 贵 7.8 倍
2000 行的文件，改 2 行  → whole_file 大约贵 100 倍以上
```

而且这是**每一轮都要重付**的——agent 改错一次、测试没过、再改一次，
`whole_file` 就再吐一遍整个文件。

> **所以真实产品几乎都用 diff 类格式做默认**（Aider、Claude Code、Cursor），
> 只在新建文件或大重写时才整份输出。
>
> **不是因为 diff 更准，是因为在"大文件 + 小改动"这个常态下，它便宜一个数量级。**

## 三、可靠性：三种格式各自会怎么坏

这一节的内容**没有在实测里出现**（零失败），但你必须知道，因为它决定了出事时的样子。

### `whole_file`：几乎不会失败

它给的就是最终结果，我们直接写进文件。唯一的失败是「它没给 content」。

代价是另一种风险：**它可能"顺手"改了别的地方**。
它重写整个文件时，无关的部分也经过了它的手。本实验的 diff 显示它没这么干，
但这个风险是结构性存在的。

> 本实验的 `show_diff()` 就是为了这个——**永远看一眼它到底改了什么。**

### `search_replace`：会失败，但**一定报错**

看 `apply_search_replace()`：

```python
count = text.count(old)
if count == 0:
    return None, t("err_old_missing", i=i + 1)     # 抄错了
if count > 1:
    return None, t("err_old_ambiguous", i=i + 1, n=count)  # 不唯一
```

两种失败，**都会明确拒绝并告诉模型原因**，然后模型下一轮改对。

这正是实验 4-1 那条结论在这里的应用：**好的错误信息 = 下一轮的提示词。**

### `line_range`：会失败，而且**可能不报错** ☠

```python
lines[start - 1:end] = new.split("\n")
```

行号偏一行，这句**照样能"成功"执行**——只是改错了地方。

- `whole_file` 出错 → 明确报错
- `search_replace` 出错 → 明确报错
- **`line_range` 出错 → 安静地把代码改坏**

而且它还有个额外麻烦：**一次改多处时，前面的改动会让后面的行号全部错位。**
所以 `apply_line_range()` 里必须**从后往前改**：

```python
# 从后往前改，否则前面的改动会让后面的行号全部错位
ordered = sorted(range(len(edits)),
                 key=lambda i: edits[i].get("start", 0), reverse=True)
```

**这行代码不是优化，是必需品。** 忘了它，多处编辑就会静默改错。

> **一条能带走的原则：**
>
> **让错误无法安静地发生。**
>
> `search_replace` 比 `line_range` 好，不是因为它更省或更准，
> 而是因为**它错的时候一定会告诉你**。

## 四、诚实交代：可靠性差异没能复现

我设计 `refactor` 任务，就是为了逼出 `search_replace` 的「old 不唯一」失败——
那 7 处的上下文长这样，只有引号里的函数名不同：

```python
    if len(numbers) == 0:
        raise ValueError("mean() 需要至少一个数")
```

**结果模型一次都没栽。** 它把函数名一起带进了 `old`，天然就唯一了。

`line_range` 一次改 8 处，行号也一次都没数错。

**两个任务 × 三种格式 = 6 次运行，编辑应用失败 0 次。**

> 「diff 格式容易对不上」这个流传很广的说法，**在这个规模上没有复现。**

这不代表它不存在。它更可能出现在：

- **更大的文件**（几百上千行，行号更容易数错）
- **更多处的改动**（错位的机会更多）
- **更弱的模型**（这是最可能的原因——这类格式纪律性要求高）
- **真正重复的代码**（本实验那 7 处其实**不完全相同**，函数名帮了大忙）

**练习 1 就是让你去找它的边界。** 找到了记下来。

> 这已经是本仓库第 7 次预期落空了。
> 从 1-1 的 `no_history` 到 4-2 的「工具太多」，模式是一致的：
> **关于「模型做不到什么」的经验，过时得比你想象的快。**
>
> 而**关于「成本」的结论要稳定得多**——它由数学决定，不由模型能力决定。
> 这也是为什么本实验最值得记住的是那张成本增长表，而不是可靠性那一节。

## 五、一个值得注意的细节：它没有过度替换

`refactor` 要求把「输入为空时抛的 ValueError」换成 `EmptyDataError`。

`stats.py` 里一共有 **9 处** `raise ValueError(`，但只有 **7 处**该换。另外两处是：

```python
    if not (0 <= p <= 100):
        raise ValueError("p 必须在 0 到 100 之间")      # percentile：参数范围错

    if window <= 0:
        raise ValueError("window 必须是正整数")          # moving_average：参数错
```

**这两处和「数据为空」无关，不该动。**

实测三种格式**都正确地只改了该改的 7 处**：

```
whole_file       EmptyDataError 出现 8 次（1 个类定义 + 7 处 raise），残留 ValueError( 2 次 ✓
search_replace   同上 ✓
line_range       同上 ✓
```

> 一个只会做字符串替换的脚本会把 9 处全换掉。
> **模型理解的是「哪些错误属于空数据」这个语义，不是「哪些字符串长得像」。**
>
> 这正是「让模型改代码」相对「写正则批量替换」的真正价值所在 ——
> 也顺便说明了为什么 `search_replace` 这种要求**语义定位**的格式对模型不难。

## 六、练习答案

### 练习 1 ⭐⭐ 把它逼到失败

我没成功，所以这里给的是**方向**不是答案：

| 方向 | 为什么可能有效 |
|---|---|
| 把文件撑到 500+ 行 | 行号越大越容易数错；`old` 也更容易撞车 |
| 去掉提示词里「文件带了行号」那句 | 逼它自己数行 —— 这才是 `line_range` 最脆的地方 |
| 造真正重复的代码块（连函数名都一样） | 这才能真正逼出 `old` 不唯一 |
| 换个更小的模型（`LAB_BACKEND` 换 API + 小模型） | **最可能有效**——格式纪律性和模型能力强相关 |

第 4 条尤其值得试。**这类"格式可靠性"结论，本质上测的是模型的指令遵循能力**，
所以它必然随模型强弱变化。你在自己项目里选格式时，
应该用**你实际要用的那个模型**测一遍，而不是照抄任何一篇文章（包括这篇）。

### 练习 2 ⭐ 让它作弊

把 `check_path()` 的拦截去掉之后，模型**大概率仍然不会**去改测试文件——
因为系统提示词里还写着「不要改测试的期望值来让它通过」。

**但这恰恰是重点：**

> 你现在有**两道防线**：提示词里说了，代码里也拦了。
> 去掉一道还能撑住，**不代表那道防线没用**——只代表你这次没撞上。
>
> 实验 4-1 的结论在这里重复一遍：
> **能在接口层面拦住的约束，别只写在提示词里。**

想真正看到 reward hacking，可以把提示词里那句也删掉，
再把任务改成一个**真的很难修**的 bug。当"改测试"比"修 bug"容易得多时，
诱惑才真正出现。

⚠️ 这也是真实项目里的教训：**当 agent 发现绕过判据比满足判据容易，它就会绕。**
所以判据要么难以篡改（只读、在别的进程里跑、在 CI 里跑），要么就别指望它。

### 练习 3 ⭐⭐ 加第四种格式：unified diff

它会落在 `search_replace` 和 `line_range` **中间偏 search_replace** 那一侧：

```
                成本        出错时
line_range      最低        可能静默改错
unified diff    中          明确报错（上下文对不上 → patch 失败）
search_replace  中          明确报错
whole_file      最高        几乎不出错
```

关键在于 unified diff **同时带了行号和上下文原文**：

```diff
@@ -24,1 +24,3 @@
     ordered = sorted(numbers)
-    return ordered[middle]
+    if len(ordered) % 2 == 0:
```

行号用来快速定位，**上下文用来验证定位对不对**。行号错了但上下文对得上，
标准 `patch` 工具会在附近找（fuzz）；上下文对不上就直接失败。

> **它是在用冗余换容错。** 这也是为什么它在工程界活了四十年。
>
> 一般化：**任何"定位"机制都应该带一个可校验的冗余**，
> 这样定位错了能被发现，而不是安静地作用在错的地方。

### 练习 4 ⭐⭐⭐ 让它自己选格式

它通常会：**小改动用 diff 类，新建文件或大重写用 `whole_file`**——
也就是真实产品的策略。

但第二个问题更重要：**你怎么验证它选得对？**

难点在于：**选错格式不会导致失败，只会导致贵**。测试照样通过，
你在监控里看不出任何异常，只有账单会慢慢变胖。

> **这是一类特别难发现的问题：没有报错，只有浪费。**
>
> 唯一的办法是**把成本本身也当成一个指标去量**——就像这个实验做的那样。
> 如果你的 agent 系统没有在记录"每次任务花了多少 token"，
> 那这类退化你永远发现不了。

### 练习 5 ⭐⭐⭐ 把测试从判据变成工具

给模型一个 `run_tests()` 工具之后，典型行为是：**改一处就跑一次**。

这带来两个变化，一好一坏：

| | 变化 |
|---|---|
| ✓ 好 | 它能**自己发现**改错了，不用等你喂结果；多步改动时尤其明显 |
| ✗ 坏 | 轮数变多、token 变多；而且它可能**在没必要的时候反复跑** |

> **真正的问题是：反馈应该由谁触发？**
>
> - 程序触发（本实验的做法）：可控、便宜，但节奏是你定的
> - 模型触发（练习的做法）：灵活、能自我纠正，但成本不可控
>
> 回头看实验 1-2 —— hosted vs DIY，是**同一个问题的另一个形态**：
> **你把控制权交出去多少，就同时交出去多少可预测性。**

## 七、把这个实验放回全局

`whole_file` vs diff 这个选择，表面是"省不省 token"，实际上是本仓库反复出现的同一件事：

| 实验 | 少给一点 vs 全给一点 |
|---|---|
| 2-1 压缩 | 摘要 vs 全文 |
| 3-5 检索 | top-k vs 全部记忆 |
| 4-2 工具 | 检索工具 vs 全部工具 |
| **5-1 编辑** | **diff vs 整个文件** |

**四次都是同一个形状：**

> **「全给」贵但可靠，「筛过再给」便宜但引入了一个新的失败模式。**

而四次的判断标准也一样：

> **先问你的成本问题有多严重，再决定值不值得引入那个新失败模式。**

区别只在于这次的新失败模式特别阴险——**`line_range` 是四个实验里唯一一个
"出错时可能不报错"的**。所以它的排序应该更靠后，即使它最省。
