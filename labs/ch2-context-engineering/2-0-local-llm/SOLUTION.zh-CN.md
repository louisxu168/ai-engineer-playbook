## 一、实测环境和数字

机器：MacBook（Apple **M3**，16GB）
栈：Ollama **0.32.5**（Metal / iGPU，11.8 GiB 可用），模型 **qwen3:0.6b**（522MB）
时间：2026-07-29

| 指标 | 实测 |
|---|---|
| 生成速度 | **113 ~ 131 token/s** |
| TTFT（暖机后） | **120 ~ 200 ms** |
| 预填充（110 token 输入） | **8 ~ 35 ms** |
| 预填充（2050 token 输入，冷） | **≈ 1000 ms** |
| 预填充（2050 token 输入，暖） | **10 ~ 40 ms** |

书上说「在苹果 M2 芯片上超过每秒 100 个 token」——**这条复现了**，
M3 上是 113~131。

## 二、0.6B 的工具调用：比预期好

`raw` 模式一次跑出来的完整输出：

```
[thinking] 好的，用户问温哥华现在几点和天气怎么样。首先，我需要确认温哥华的当前时间。
温哥华是加拿大最大的城市之一，现在的时间可以通过 get_time 工具获取。然后，天气情况
同样需要调用 get_weather 工具。不过用户的问题提到了两个部分，所以可能需要分别调用
两个工具。……因此，正确的做法是先调用 get_time 和 get_weather，然后给出结果。

[content] TOOL: {"name": "get_time", "args": {"city": "Vancouver"}}
          TOOL: {"name": "get_weather", "args": {"city": "Vancouver"}}
```

**六亿参数的模型做到了三件事：**

1. 把一个问题拆成两个子问题
2. 判断出这两个子问题**互不依赖**，因此**一次性发出两个工具调用**
3. JSON 格式一次就对（没有多余的逗号、没有把 `args` 写成 `arguments`）

而在 `react` 模式里它还做到了第四件：

```
[最终回答] 温哥华现在时间是2026年7月29日09:56，天气为小雨，温度14摄氏度。
```

**它把两个工具的返回值合成了一句通顺的话**——这需要它理解每个结果分别是什么。

> **书上那句「模型大小固然重要，但不是唯一的决定因素」，实测成立。**
>
> 但要说清楚**前提**：这个任务的工具只有 2 个、参数只有 1 个、
> 格式在系统提示词里给了完整例子。
> 换成实验 4-2 那种 40 个工具、或者实验 4-1 那种带枚举和单位陷阱的场景，
> 0.6B 大概率就不行了。**「小模型能调工具」是有适用范围的。**

## 三、我没能拿到真正的 `<think>` 标签 ★

这是本实验第一个反直觉的地方，值得完整讲。

### 我本来想做什么

书上说这个实验能让你「**直接观察模型的原始输入输出 token 流**」，
包括 `<think>` 标签这种「在 API 层面不可见的细节」。

于是我想：**本地部署嘛，总能看到原始的吧。**

### 实际发生了什么

**Ollama 在服务端就把标签解析掉了。** 用 `/api/chat` + `think:true`，
返回的是这个形状：

```json
{"message": {"role": "assistant",
             "thinking": "好的，用户问温哥华……",     ← 标签里的内容
             "content": "当前温哥华时间是12:37。"}}    ← 标签外的内容
```

**字段名叫 `thinking` 和 `content`，`<think>` 这三个字符一个都没有。**

### 我试着绕过去，失败了

想拿到真正的原始流，得绕过模板层——Ollama 的 `/api/generate` 有个 `raw: true`，
让你自己拼 ChatML。我试了：

| 尝试 | 结果 |
|---|---|
| `<\|im_start\|>user\n温哥华几点？<\|im_end\|>\n<\|im_start\|>assistant\n` | 正常回答，**没有 `<think>`** |
| 同上，用户消息末尾加 ` /think`（Qwen3 的开关） | **返回空字符串** |
| 再在 assistant turn 后面预填 `<think>\n` | **返回空字符串** |

看了一眼模型的模板才明白：

```
{{- if and $.IsThinkSet (eq $i $lastUserIdx) }}
   {{- if $.Think -}}{{- " "}}/think
   {{- else -}}{{- " "}}/no_think
```

思考模式是靠 `IsThinkSet` 这个**模板变量**驱动的，而 `raw:true` 恰恰**跳过了模板**——
于是那套机制整个失效了。

### 所以结论是

> **「本地部署就能看到原始输出」这个假设，是错的。**
>
> 我原本以为的层级是：
> ```
> 云 API（洗过） →  本地 Ollama（原始）
> ```
> 实际的层级是：
> ```
> 模型生成的 token 序列
>    ↓ llama.cpp 按模板切
> <think>…</think> + 正文 + <tool_call>…
>    ↓ Ollama 服务端解析          ← 我卡在这一层
> {"thinking": ..., "content": ...}
>    ↓ SDK 再包一层
> response.message.content
> ```
>
> **「原始」是分层的。你以为的底层，下面还有一层。**

这个发现**没有推翻**书的观点，反而强化了它：
本地部署确实比云 API 让你多看见一层（你能看到 thinking 和 content 是分开的、
能看到 `TOOL:` 那行原文、能拿到 `prompt_eval_duration`）——
**但它不等于"原始"。** 想真正看 token，得再往下到 llama.cpp 的层面。

💡 `agent.py` 的 `raw` 模式因此改成了**如实标注**：
它把 `[thinking]` / `[content]` 两个标签打出来，并明说**那条线是 Ollama 划的，不是模型划的**。

## 四、KV Cache 实验：从「假成功」到「诚实失败」★★★

这是本实验最重要的一节，讲的是**我差点发表一个错误结论**的完整过程。

### 第一版：看起来完美复现了

最初我用**原来那个 110 token 的短系统提示词**，跑三次：

```
第 1 次  首次（冷）                  预填充 18 ms
第 2 次  重复同一个提示词（应命中）    预填充  8 ms     ← 快了 2.25 倍！
第 3 次  改开头一个字（应失效）        预填充 55 ms     ← 涨回去了！
```

**教科书级别的完美。** 我差点就这么写进文档了。

### 但我多跑了两次

```
复现 1：  27 ms  →  16 ms  →   7 ms     ← 第 3 次【最快】，和预测相反
复现 2：   8 ms  →   8 ms  →  10 ms     ← 三个数一样，什么效应都没有
```

**三次跑出了三种互相矛盾的结论。**

原因很清楚：110 token 的输入，预填充只有 **10ms 上下**——
**这个量级完全淹没在测量噪声里**。第一次那个「完美结果」是**运气**。

> **教训 1：一个只跑了一次的对照实验，什么都证明不了。**
> 而且它**越像教科书，你越应该怀疑**——因为教科书式的干净结果，
> 在有噪声的真实测量里本来就不常见。

### 第二版：把提示词加长到 2050 token

预填充涨到 ~1000ms（冷）之后，噪声就不再是问题了。重新设计成三组：

```
A. 完全固定的系统提示词，连跑 3 次
B. 每次在【开头】塞一个从没出现过的会话 ID
C. 每次在【结尾】塞一个从没出现过的会话 ID
```

实测（2026-07-29，多次一致）：

```
A  预热（冷启动）    1031.1 ms
A  第 1 次             20.7 ms
A  第 2 次             15.5 ms
A  第 3 次             10.1 ms

B  第 1 次            989.2 ms      ← 慢
B  第 2 次             17.6 ms      ← 但第 2、3 次又快了
B  第 3 次             10.1 ms

C  第 1 次            997.4 ms      ← 同样慢
C  第 2 次             37.8 ms
C  第 3 次             29.4 ms
```

### 结论：**B 和 C 没有区别**

书上（以及几乎所有讲 KV Cache 的文章）说：**改动开头会让前缀失效，
所以 B 应该明显比 C 慢**。

**实测不支持这个说法。** B 和 C 的形状**一模一样**：第 1 次约 990ms，
之后掉到 10~40ms。ID 放在开头还是结尾，**没有稳定差别**。

更奇怪的是：B 的第 2、3 次用的是**全新的 ID**（REQ-9001、REQ-9002），
按理说前缀已经不同了，却仍然很快。

### 我不知道确切原因，只能列出几种可能

1. **Ollama / llama.cpp 同时缓存多个前缀** —— 所以交替使用几个提示词时，
   它们可能都在缓存里，看不出失效
2. **`prompt_eval_duration` 是否真实反映重算量，我无法确认** ——
   它可能只统计了实际新算的那部分，也可能有别的口径
3. **效应可能需要更长的上下文、更大的模型、或 vLLM 那类推理栈才显现**

**我没有继续往下挖**，因为再挖就需要读 llama.cpp 的缓存实现，
超出这个教学实验的范围。**练习 4 把它留给你了。**

### 但这次失败量到了真正站得住的东西

```
2050 token 输入，模型冷加载后的第一次调用   ≈ 1000 ms
之后的每一次                                ≈ 10 ~ 40 ms
```

**差两个数量级，每次都复现。**

而这个数才是上下文工程真正的理由：

> **输入越长，预填充越贵，而且缓存没命中时每次请求都要重付。**
>
> 2050 token 要 1 秒。你的 agent 跑 20 轮、每轮上下文越滚越长，
> 这笔钱是**每一轮**都在付的。
>
> **这就是实验 2-1（上下文压缩）存在的原因。**

> **教训 2：一个实验失败了，不代表它没有产出。**
> 我没能复现「前缀位置」的效应，但量到了「冷 vs 暖」差 100 倍——
> 后者对工程决策的指导意义**更大**，因为它更稳、更大、更容易利用。

## 五、练习答案

### 练习 1 ⭐ 换更大的模型

`qwen3:1.7b`（约 1.4GB）通常：token/s 掉到 0.6B 的一半左右，
思考更长更有条理，工具调用在**复杂场景**下明显更稳（简单场景两者都对）。

> 值得你亲手跑一次的原因：**「大模型更好」是个笼统的说法，
> 而你需要的是「在我的任务上，大多少、好多少、慢多少」这三个具体数字。**

### 练习 2 ⭐⭐ 让它做需要依赖的事

换成「温哥华几点？如果过了晚上 8 点就告诉我北京的天气」之后，
一个够聪明的模型应该**先只调 `get_time`**，看到结果再决定要不要调 `get_weather`。

0.6B 在这里**经常做错**——它倾向于把两个都发出去。

> 这正好印证实验 1-1 的结论：**依赖关系是在提示词层面解决的，代码不校验。**
> 而**「能不能正确判断依赖」恰恰是小模型和大模型差距最明显的地方之一** ——
> 因为它要求模型在行动前先做一步条件推理。

### 练习 3 ⭐⭐ 关掉思考

`think=False` 之后速度明显变快（少生成了一两百个 token），
而在这个简单任务上工具调用**通常仍然正确**。

> 结论要说准确：**不是「思考没用」，是「这个任务太简单，用不上」。**
> 思考的价值随任务复杂度增长。用简单任务去证明「思考没用」，
> 是本仓库反复出现的那类错误（见实验 1-3、4-2）。

### 练习 4 ⭐⭐⭐ 把 KV Cache 效应挖出来

我没做到。给你几个我认为最有希望的方向，按推荐顺序：

| 方向 | 为什么可能有效 |
|---|---|
| 上下文加到 8k~16k | 效应随长度线性放大，噪声不变 → 信噪比变好 |
| 每次用**完全不重复**的新前缀 | 排除「多个前缀都被缓存了」这个干扰 |
| 换 vLLM | 它的 PagedAttention / 前缀缓存实现和 llama.cpp 完全不同 |
| 量端到端 TTFT 的**分布**（跑 20 次看中位数） | 绕开 `prompt_eval_duration` 这个我不确定的指标 |

**如果你复现出来了，那是个真发现。**

> 而更值钱的是这个问题：**为什么几乎所有文章都在讲这个效应，
> 而我在一个真实的本地栈上量不出来？**
>
> 可能是我的方法不对，也可能是**这个说法在很多具体栈上并不成立，
> 但它作为「听起来很有道理的技术常识」一直在被转述**。
>
> 本仓库到目前为止已经有 **10 次预期落空**了。
> **技术传言的传播速度，远快于它被验证的速度。**

### 练习 5 ⭐⭐⭐ 用 Ollama 原生 tools 参数

改用原生 `tools` 之后，`TOOL: {...}` 那一行**就看不到了**——
它变成了返回 JSON 里的 `message.tool_calls` 数组。

好处是格式更可靠（服务端保证结构合法），代价是**你少看见了一层**。

> 这正是本实验的主题在自己身上又演示了一遍：
> **每加一层抽象，你就少看见一样东西。**
>
> 而这个交换通常是划算的——**只要你知道自己换掉的是什么。**
> 本实验的全部意义，就是让你**知道**。

## 六、放回全局

这个实验在本仓库里的位置很特殊：**它是唯一一个往「下」看的。**

其他 14 个实验都在问「**我该怎么用**这个模型」，
这一个在问「**这个模型底下是什么**」。

两件事都要知道，但顺序上后者更容易被跳过——
因为不知道也能用，直到你需要优化延迟、需要排查一个奇怪的格式错误、
或者需要判断某条技术传言是不是真的。

**而它接下来直接引出第 2 章的其余部分：**

```
2-0（本实验）  量到：输入越长，预填充越贵      ← 问题
2-1 上下文压缩  →  那就把上下文变短            ← 一种解法
2-2 Prompt 注入 →  但短不等于安全
2-3 日志脱敏    →  也不等于该放的都放了
```
