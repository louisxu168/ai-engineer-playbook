# 实验 3-1：用户记忆 —— 跨会话记住一个人

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. 记忆系统只有两个动作：**写**（存什么）和**读**（拼进上下文）——
>    四种模式的差别 100% 在「写」
> 2. 「全存下来」为什么不行：体积随会话数无限增长，垃圾和过期信息一起留着
> 3. **提取提示词决定记忆质量**——实测发现随便写的提取器**比不提取还大**
> 4. 一个提示词救不了的问题：**事实变了怎么办**（这是记忆系统真正的难点）
>
> **怎么学**：程序把每种模式的记忆写成一个 JSON 文件，你可以直接打开对比。
> 同时自动量出：体积、记住了几条关键事实、混进了几条垃圾、过期事实还在不在。
>
> **需要多久**：20 分钟（不联网）。

---

## 先搞清楚问题是什么

第 2 章讲的都是**一次会话之内**的上下文。但真实产品不是一次会话：

```
周一  用户：我对花生过敏，吃到会送医院。
      ...会话结束，上下文清空...

周五  用户：帮我推荐几家餐厅
      agent：好的！推荐宫保鸡丁……
```

> **上下文是会话级的，人是跨会话的。**

第一反应通常是「把聊天记录全存下来，下次全塞进去」。能用——直到你撞上
第 2 章那面墙：**存了 200 次会话，还塞得进去吗？**

所以真正的问题不是「怎么存」，而是：**存之前，选什么？**

---

## 这个实验的剧本

程序里写死了 6 次会话（写死是为了让四种模式面对完全一样的输入，比较才成立）：

| 第几次 | 用户说了什么 | 这是什么 |
|---|---|---|
| 1 | 我对花生过敏……完全不吃辣 | ✅ **该长期记住** |
| 2 | 我在**北京**国贸上班，做后端开发 | ⚠️ 长期为真——但等一下 |
| 3 | 今天下雨忘带伞，有点感冒，早点睡 | ❌ **当天就过期** |
| 4 | 去了环球影城，人太多排队排到怀疑人生 | 🤔 事件没用，但里面藏着一条偏好 |
| 5 | 更新一下：调岗，以后常驻**上海**浦东 | 💣 **第 2 条作废了** |
| 6 | 我下周要去成都出差三天，住春熙路 | ⏳ 真，但**会过期** |

然后第 7 次会话，你来提问（比如「帮我列一个成都出差期间的餐厅清单」）。

**这 6 条覆盖了记忆系统的全部难点。** 特别是第 5 条——记忆不只要会「加」，
还得会「改」。

## 第 0 步：先看没有记忆是什么体验（3 分钟）

```bash
cd labs/ch3-memory/3-1-user-memory
python3 agent.py no_memory
```

直接回车看例子，输 `1`。

### 👀 你会看到

模型**没法回答**。它反问了你四个问题，其中一个是：

```
3. **吃辣吗？** 出差期间连着吃火锅串串，肠胃扛不扛得住是个现实问题。
```

### 💡 学到什么

**用户已经在第 1 次会话里说过「完全不吃辣」了。**

这就是没有记忆的代价——不是答错，是**让用户把自己重新介绍一遍**。
所有「这个 AI 一点都不懂我」的体验，本质都是这一条。

> 顺便留意：程序判定它「✓ 照顾到了不吃辣」。
> **这是误判**——模型只是顺口说了「辣的和不辣的按 2:1 搭配」，
> 关键词撞上了。自动判分是有限度的，SOLUTION 里会展开讲。

## 第 1 步：把聊天记录全存下来（4 分钟）

```bash
python3 agent.py full_log "（复制同一个问题）"
```

### 🤔 先猜

- 关键事实记住了几条？ ___
- 记忆里会混进多少无用信息？ ___

### 👀 观察什么

盯住这四行：

```
  记忆体积：___ 字  ██████
  关键事实：记住了 ___/2 条
  无用信息：混进了 ___ 条
  过期事实：___
```

### 💡 学到什么

它确实全记住了——**代价是全部的垃圾也留着**。

而且看清楚这一点：`full_log` 的体积 = 所有会话字数之和。
**6 次会话是 199 字，600 次会话就是两万字。** 这条线是直的，不会拐弯。

> 打开 `memory_full_log.json` 看看。这个文件就是 agent 的记忆本体。

## 第 2 步：让模型来提取（6 分钟）★核心

现在换个思路：**会话结束时，让模型自己挑出值得记的**。

跑两遍，区别**只有一段提取提示词**：

```bash
python3 agent.py naive_extract "（同一个问题）"
python3 agent.py extracted     "（同一个问题）"
```

### 🤔 先猜（这题基本所有人都猜错）

`naive_extract` 的提示词只有一句「把这段会话里的信息提取成记忆条目」。

- 它的记忆会比 `full_log` **大**还是**小**？ ___

### 🔧 然后做这件事（本实验最重要的一步）

```bash
# macOS / Linux
diff memory_naive_extract.json memory_extracted.json
```

或者直接用编辑器打开这两个文件并排看。

### 👀 观察什么

一条条对比。特别注意：

1. 第 3 次会话的「下雨/感冒/早睡」，**两个文件里都有吗？**
2. 第 4 次会话的环球影城，两边分别提取出了**什么**？
3. 第 6 次会话的「下周出差」，两边写法有什么不同？

### 💡 学到什么

打开 `agent.py` 看 `update_memory()`——`naive_extract` 和 `extracted`
走的是**同一个函数、同一次模型调用**，唯一的分叉是这两行：

```python
if mode == "naive_extract":
    extract_prompt = t("extract_naive")
else:
    extract_prompt = t("extract_good")
```

`extract_good` 里写清了五条标准，其中最关键的是第 2 条：
**明确告诉它什么该扔**。

> 这和实验 2-9 是同一条规律：
> **压缩质量 ≈ 压缩提示词质量；记忆质量 ≈ 提取提示词质量。**
>
> 你在提示词里没说的判断标准，模型就替你随便定了一个。

## 第 3 步：全量对比 + 那一行你可能会忽略的（5 分钟）

```bash
python3 agent.py all "（同一个问题）"
```

对比表里有一行叫 **「过期事实」**。

用户在第 5 次会话说了「调岗，以后常驻上海，北京这边不去了」。
所以「在北京国贸上班」这条**已经作废了**。

### 🤔 先猜

四种模式里，有几种把北京那条清掉了？

### 💡 学到什么

答案在 SOLUTION，但先自己想一个更重要的问题：

> **提取那一步，看得见已经存下来的记忆吗？**

去 `update_memory()` 里找答案。这一行是关键：

```python
raw_text = complete(t("extract_input") + session_text, extract_prompt, ...)
```

发给模型的只有 **这一次会话的原文**。它压根不知道两个月前存过什么。

**所以这不是提示词能解决的问题，是架构问题。** 练习 3 会让你动手改。

## 第 4 步：自己动手改（练习）

### 练习 1 ⭐ 给剧本加一次会话

在 `TEXT["zh"]["sessions"]` 里加一句用户的话，比如「我最近在减脂，晚上不吃主食」。

**先猜**：四种模式分别会怎么处理它？跑一遍验证。

### 练习 2 ⭐⭐ 改坏 `extract_good`

把第 2 条（「明确扔掉当下状态」）删掉，重跑 `extracted`。

**先猜**：无用信息会从 0 变成几条？

> 这道题做完你就知道：那五行提示词里，哪一行在真正干活。

### 练习 3 ⭐⭐⭐ 让记忆能「改」，不只能「加」

改 `update_memory()`：提取之前，**先把已有的记忆一起发给模型**，
让它输出的不是「新增哪些」，而是「更新后的完整记忆列表」。

提示词大意：

```
这是你已经记住的：{已有记忆}
这是最新一次会话：{本次会话}
请输出**更新后的完整记忆列表**。如果新会话推翻了旧记忆，删掉旧的。
```

**先猜**：北京那条会被清掉吗？跑一遍看。

> 这就是 mem0、Memobase 这类记忆框架在做的事：不是 append，
> 是 **add / update / delete 三选一**。

### 练习 4 ⭐⭐⭐ 记忆多了之后怎么办

假设记忆涨到 500 条，还能全塞进上下文吗？

**先想清楚**：这时候你需要的是压缩（第 2 章），还是**检索**（下一个实验）？

> 这两个问题的分界线是：**你能不能提前知道这次用得上哪几条。**

### 练习 5 ⭐⭐ 给记忆加时效

第 6 次会话的「下周去成都出差」，出差结束后就该失效了。

给记忆条目加一个 `expires` 字段，读取时过滤掉过期的。

**先想清楚**：这个「过期」是谁判断的——写的时候，还是读的时候？

## 附：概念速查

### 记忆系统的两个动作

```
写：会话结束 → 决定留下什么 → 存进文件/数据库
读：新会话开始 → 取出来 → 拼进上下文
```

本实验只做了最简单的「读」：**全部取出来**。
等记忆多到全取不动了，「读」就变成检索问题——那是下一个实验。

### 四种策略

| 策略 | 体积随会话数 | 垃圾 | 能改旧记忆 | 什么时候用 |
|---|---|---|---|---|
| 不记 | 0 | 无 | — | 一次性工具，无需个性化 |
| 全存 | **线性增长** | 全留 | ✗ | 会话很少、且要求零信息损失 |
| 随便提取 | 增长（可能比全存还快） | 全留 | ✗ | 不建议 |
| 好好提取 | 增长慢 | 少 | ✗ | **默认选它** |
| 提取 + 更新（练习 3） | 趋于平稳 | 少 | ✓ | 真实产品 |

### 一条工程原则

> **记忆系统的质量，取决于它拒绝记住什么。**
>
> 一个什么都记的系统，和一个什么都不记的系统，
> 在「找不到有用信息」这件事上是一样的。
