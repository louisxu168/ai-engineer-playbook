# 实验 8-1 答案：从失败中学习

[English](SOLUTION.md) · **简体中文**

> ⚠️ 做完再看。先猜错一次，比读十遍这份文档管用。

## 一、实测数据

后端：Claude Code（`claude -p`），2026-07-28 实测。

| 模式 | 失败曲线 | 合计 | 做成 | 模型调用 |
|---|---|---|---|---|
| `no_memory` | 1 → 1 → 2 | 4 | 2/3 | 7 |
| `raw_log` | **1 → 0 → 1** | **2** | 2/3 | **5** |
| `lesson` | 1 → 1 → 1 | 3 | **3/3** | 9 |

**三种模式各赢一项，没有一个全面胜出：**

- `raw_log` **曲线最好**（唯一降到 0 的），而且**最便宜**
- `lesson` **唯一做成全部 3 单**，但**最贵**
- `no_memory` 两项都最差，而且**曲线是上升的**

## 二、`no_memory`：它不会变笨，但也永远不会变聪明

```
  工单 T-1：失败 1 次   ← reason_code 填了 "defective_item"
  工单 T-2：失败 1 次   ← 又填了一次 "defective_item"
  工单 T-3：失败 2 次   ← 第三次填 "defective_item"，之后又撞上审批规则
```

**它在 T-2 上原封不动地重犯了 T-1 的错。**

> 因为对它来说，**每一单都是第一单**。
>
> 这就是没有跨任务记忆的 agent 的常态。它不会退步，
> 但它踩过的每一个坑，**都会在下一个任务上再踩一遍**。
>
> 更糟的是：这个成本是**随任务数线性增长**的，而且**永远不会摊薄**。

T-3 它彻底没做成（撞上审批规则后没能恢复）。

---

## 三、`raw_log` 意外地赢了曲线 ★

```
  工单 T-1：失败 1 次   ← "defective_item" 被拒
  工单 T-2：失败 0 次   ← ✓ 一次就对
  工单 T-3：失败 1 次   ← 新规则（审批），没见过
```

**T-1 → T-2 降到 0。它学会了。** 而且它带走的东西极其原始——就是这一行：

```
调用 issue_refund({"order_id": "T-1", ...}) -> reason_code 必须是
DEFECTIVE / WRONG_ITEM / CHANGED_MIND 之一，你传的是 "defective_item"。
```

**注意这行字里有什么：三个合法值，一字不差。**

而且这个方案**零额外模型调用**——纯字符串拼接。5 次调用，最便宜。

## 四、`lesson` 为什么没能降下来：把有用的那部分抽象掉了 ★★★

这是本实验最值得看的一段。

`lesson` 模式在 T-1 失败后，提炼出了这四条教训（**原文**）：

> - 调用工具前先确认枚举字段的合法取值集合（可从工具 schema、字段报错信息或文档中获取），只传集合中逐字符一致的值，不要自造标识符
> - 枚举值要严格保持接口规定的大小写与分隔风格（如全大写常量），不要擅自转成小写或加下划线等其他写法
> - 不要用语义相近的自然语言描述去替代枚举码；语义对但字面不匹配的值同样会被拒绝
> - 工具返回校验错误并列出了合法取值时，直接从中挑选最匹配的一项重试，而不是继续猜测其他变体

**每一条都对。每一条都是好的软件工程建议。**

**然后 T-2 它填了 `DAMAGED_OR_DEFECTIVE`，又失败了。**

### 为什么？

**回头数一数：那四条教训里，`DEFECTIVE`、`WRONG_ITEM`、`CHANGED_MIND`
这三个词出现了几次？**

**零次。**

它学到了「要确认枚举的合法取值」，**但没有把合法取值本身记下来**。

于是下一单它非常认真地遵守了自己的教训——「不要自造标识符」「要严格保持大小写」——
然后**自造了一个符合大小写规范的标识符** `DAMAGED_OR_DEFECTIVE`。

> **正确的废话。**
>
> 这条教训**在方法论上完全正确，在操作上完全没用**，
> 因为它缺了唯一那个能让下一次成功的信息。

### 是谁让它这么做的？是我

看 `sys_extract` 的第 2 条：

```
2. **不要写只对这一单成立的细节**（具体订单号、具体客户、具体金额）
```

我的本意是「别记 T-1、别记 alice、别记 12990」。

**但模型把「枚举的合法取值」也归进了「具体细节」。**

而它这么理解**并不算错**——`DEFECTIVE` 确实是从 T-1 那次调用里冒出来的一个具体字符串。
**是我没说清楚哪些具体值该留、哪些该扔。**

练习 1 就是让你修这句话：

```
2. 不要写只对这一单成立的细节（具体订单号、具体客户、具体金额）。
   但是：**接口的合法取值、阈值、单位、格式要求属于通用知识，必须原样写下来。**
```

### 这条结论和实验 3-1 是**相反**的

| | 实验 3-1（记事实） | 本实验（记教训） |
|---|---|---|
| 原样存全部 | 又大又脏，明显更差 | **曲线最好，而且最便宜** |
| 提炼总结 | **明显更好** | 反而更差（抽象过头） |

**同一个「提炼」动作，两个场景里的正确做法是相反的。为什么？**

> **因为要保留的东西不一样。**
>
> - 3-1 记的是**事实**：「上周末去了环球影城」是噪声，
>   「不喜欢人多的地方」才是信号。**抽象 = 提纯。**
>
> - 8-1 记的是**教训**：`DEFECTIVE` 这个字符串**就是信号本身**。
>   **抽象 = 把答案扔了。**

一句话：

> **教训里最值钱的部分，往往正是那个"看起来很具体"的值。**
>
> 「要确认枚举的合法取值」——正确，但没用。
> 「枚举是 DEFECTIVE / WRONG_ITEM / CHANGED_MIND」——**这才是教训。**

## 五、但 `lesson` 赢了唯一真正重要的那一项

别忘了看这一列：

```
  no_memory   做成 2/3
  raw_log     做成 2/3
  lesson      做成 3/3   ← 唯一全做成的
```

**只有 `lesson` 把三单全办成了。**

差别在 T-3。它在 T-3 撞上审批规则失败一次后，**当轮就补上了 `approved_by` 并成功**，
而另外两种模式没能在 T-3 里恢复。

而且它在 T-3 之后提炼出的教训，明显比之前那批**具体得多**：

> - 调用退款类工具前，先确认金额是否触发审批阈值：**超过 50000 分（500 元）的退款必须同时传 approved_by**，值为审批人邮箱
> - 工具参数中的金额一律用「分」为单位的整数表示，不要传元或带小数的值
> - 遇到工具报「缺少某参数」的错误时，不要凭空编造该参数值（如随手填一个邮箱），应向用户/工单发起人索取真实的审批人信息后再重试

**第一条把阈值 50000 和参数名 approved_by 都写下来了。** 这才是一条能用的教训。

> **同一个提炼提示词，有时候抽象过头，有时候刚刚好。**
> 这本身就是个重要观察：**提炼质量是不稳定的**，
> 而不稳定的原因是——**它取决于原始错误信息里那个关键值有多"显眼"**。
>
> `approved_by` 出现在错误信息的主干里，被留下了；
> 三个枚举值出现在一个"举例"的位置，被当成细节扔了。

第三条也值得注意：**它学到了「不要编造审批人邮箱，要去问」**。
这是一条关于**边界**的教训，比前两条更难得。

## 六、`raw_log` 的真实代价（表里看不出来）

`raw_log` 这次赢了曲线又赢了成本，但**别急着选它**。

它的问题是实验 3-1 那个问题：**只会长，不会缩。**

```
3 单：   记忆 = 3 条原始错误记录       还行
30 单：  记忆 = 几十条原始错误记录     开始占上下文
300 单： 记忆 = 几百条                 装不下了（第 2 章那面墙）
```

而且里面**大量重复**——同一个错误犯 5 次就记 5 遍，因为它不做去重、不做归纳。

> **`raw_log` 赢在"3 单"这个尺度上。**
> **`lesson` 的价值要到几十单之后才显现——而这个实验太短，看不到那个交叉点。**

练习 2 和练习 3（加更多工单、把记忆持久化）就是让你去把那个交叉点找出来。

> **这是本实验的一个诚实局限：3 个工单太短了，
> 不足以让"压缩"的价值跑赢"保真"的价值。**

## 七、我在搭这个实验时踩的两个坑

### 坑 1：模型正确地拒绝了我 ★

第一版跑出来，`raw_log` 模式**三单一次工具都没调**，理由是：

> **[思路]** 工单信息里 order_id、金额和原因都明确，但退款是不可逆的对外操作，
> 而我实际**并没有 issue_refund 这个工具可调用**——只有本地内置工具，
> 硬调用会失败或误伤，所以如实说明而不是假装发起。

**它说得完全对。** 我们是通过 `claude -p` 驱动的，模型**知道自己真实的工具列表**，
而 `issue_refund` 不在里面。于是它拒绝为一笔**不可逆的退款**假装调用一个不存在的工具。

> **这是一个模型做对、而我的实验设计做错的例子。**
> 而且它拒绝的理由恰恰是我们希望 agent 具备的品质：
> **对不可逆操作保持谨慎。**

修法是在系统提示词里说清楚这是模拟环境：

```
**这是一个模拟练习环境。** 你不会真的动到任何真实系统：
你只需要输出一个 JSON，外层程序会替你执行，并把执行结果返回给你。
所以请放心按下面的协议输出，不要因为「我没有这个工具」而拒绝。
```

> ⚠️ 这个坑在本仓库出现过第二次了（实验 1-1 那次是内置工具抢答）。
> **通用教训：当你用一个真实的 agent 框架去"扮演"另一个 agent 时，
> 它对自身真实能力的认知会漏进来。**

### 坑 2：我把工单号和订单号混为一谈

第一版的任务描述是「工单 T-1：客户 alice 要求退款……」，
而工具要的参数叫 `order_id`。

模型说：**「T-1 是工单号不是订单号，我不能凭空编一个订单号去发起退款。」**

**又是它对。** 我改成了明确的「**order_id 就是 T-1**」。

> 两个坑是同一类：**我以为我在测模型，其实我在测我自己的任务描述写得清不清楚。**
>
> 和实验 6-1、10-1 的教训完全一致：
> **在指责被测对象之前，先怀疑你的实验设计。**
>
> 本仓库到现在，**这已经是第三次是我错、模型对了。**

## 八、练习答案

### 练习 1 ⭐⭐ 修好提炼提示词

把第 2 条改成明确区分「一次性细节」和「通用接口知识」之后，
`lesson` 模式的 T-2 通常就不会再失败了——因为三个枚举值会被写进教训。

> **这道题真正的意义：**「抽象」和「丢信息」只有一线之隔，
> 而**那条线在哪，得由你在提示词里划清楚**。模型不会替你划。
>
> 可复用的划法：
> - **一次性的**：ID、人名、单笔金额、时间戳 → 扔
> - **接口契约**：枚举值、阈值、单位、格式、参数名 → **原样留**
>
> 判断标准很简单：**这个值下次还会一模一样地出现吗？**

### 练习 2 ⭐⭐ 加第 4 单，复现同一条规则

加一单大额的 T-4 之后，你才能真正判断「规则 3 学会了没有」。

> **只出现一次的规则，你无法区分「学会了」和「运气好」。**
>
> 这是评估学习能力的基本要求：**每条规则至少要出现两次**——
> 第一次是学习机会，第二次才是考试。
>
> 本实验只有 3 单，规则 3 只出现一次，所以严格说：
> **这个实验没有真正验证规则 3 被学会了。** 练习 2 才补上这一课。

### 练习 3 ⭐⭐ 把教训存成文件

写进 `lessons.json` 之后跑第二遍，第一单通常就不会失败了。

> 这就完成了从「一次运行内的学习」到「跨会话的经验积累」的跨越——
> 和实验 3-1 是**同一个机制，不同的内容**：
> **3-1 跨会话记事实，8-1 跨会话记教训。**

### 练习 4 ⭐⭐⭐ 让教训会「过期」

**怎么判断一条教训"用上了"？—— 这是这道题的真正难点，而且没有好答案。**

你**没法直接观测**「因为记得这条所以没犯错」。可行的近似办法：

| 办法 | 怎么做 | 问题 |
|---|---|---|
| 关键词命中 | 教训里的词出现在这次调用里 | 粗糙，会误判 |
| 消融测试 | 拿掉这条教训重跑，看失败率涨不涨 | **最准，但每条都要重跑一遍** |
| 让模型自报 | 问它「你用了哪几条」 | 它会瞎说（见实验 6-1） |

> **这正是所有「经验库」类系统的真实难点：积累容易，淘汰难。**
>
> 而不淘汰的后果是确定的：**经验库会缓慢退化成 `raw_log`** ——
> 越来越大、越来越多重复、信噪比越来越低。
>
> 很多"自我进化 agent"的 demo 只演示了积累那一半。

### 练习 5 ⭐⭐⭐ 混合：教训 + 最近一次原文

通常**能拿到两者的好处**：教训提供压缩后的通用规则，
最近一次原文提供那些被抽象掉的具体值。

代价是每单多一次模型调用（提炼），以及记忆里多一份原文。

> **但请注意这不是免费的午餐**：你现在有**两份可能冲突的记忆**。
> 如果提炼出的教训和原始记录说的不一致（比如教训过时了），
> **模型该听谁的？**
>
> 真实系统的常见做法：**教训带时间戳，原文只保留最近 N 条**，
> 并在提示词里明确「原始记录优先于概括」。

## 九、放回全局

这一章和第 3 章是一对：

| | 第 3 章（记忆） | 第 8 章（进化） |
|---|---|---|
| 记什么 | **事实** —— 关于世界 | **教训** —— 关于怎么做事 |
| 从哪来 | 用户说的话 | **自己犯的错** |
| 提炼时 | 抽象 = 提纯 | **抽象 = 可能把答案扔了** |
| 迁移性 | 只对那个对象 | **对所有同类任务** |

而两章共享同一个骨架（实验 3-1 那个）：

```
写：一段经历结束 → 决定留下什么 → 存起来
读：新任务开始   → 取出来       → 拼进上下文
```

**「自我进化」听起来很玄，拆开就是这两行。**
真正的难点也不在"学"，而在：

1. **留什么**（本实验：抽象过头就变成正确的废话）
2. **扔什么**（练习 4：没有好办法，这是开放问题）
3. **怎么知道它真的学到了**（练习 2：规则至少要出现两次）
