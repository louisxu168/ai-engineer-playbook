# 实验 2-4：五种常见的错误上下文管理模式

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. **KV Cache 效应干净复现**：稳定前缀第 2 次快 **19 倍**；系统提示词开头塞时间戳 → **永远不命中**
> 2. 五种错误模式要分成**两类**看：一类只烧钱，一类**直接给你错答案**
> 3. 滑动窗口是唯一**两类都占**的——它是这五种里最贵的
> 4. 一个方法论细节：**为什么实验 2-0 没能复现，而这里能**（差别只在对照组设计）
>
> **怎么学**：历史是**程序化写死**的 12 条消息，五种策略处理**完全一样**的输入，
> 正确答案写死，判分是机械的。每种策略只花 2 次调用，跑一遍不到一分钟。
>
> **需要多久**：20 分钟。
>
> ⚠️ 需要本地 Ollama（和实验 2-0 同一套环境）。

---

## 先搞清楚为什么必须用本地模型

这个实验要量的是 **prefill（预填充）耗时**——处理**输入**花的时间。

**云端 API 不暴露这个数字。** OpenAI / Anthropic 会告诉你「缓存命中了多少 token」，
但不会告诉你「省了多少毫秒」。想亲眼看到缓存效应，只能用本地栈。

---

## 实验设计（这部分值得先读）

**不让模型生成历史**，而是**程序化构造**一段固定的 12 条消息：

```
assistant: {"tool": "read_sensor", "args": {"id": 1}}
user:      工具返回：{"sensor": 1, "value": 37}      ← 这个 37 是关键
assistant: {"tool": "read_sensor", "args": {"id": 2}}
user:      工具返回：{"sensor": 2, "value": 12}
...（读到 5 号）
assistant: 好的，5 个传感器都读完了。
user:      收到，先放着，我等下要用。
```

然后对**同一份历史**施加五种策略，问**同一个问题**：

> 「你之前读到的 1 号传感器的读数是多少？」

**正确答案写死是 37。**

> 💡 为什么问「检索一个数」而不是「求和」？
> 我第一版用的是求和，结果 0.6B **把 5 个数都列对了却加错了**——
> 于是我测到的是它的算术能力，不是上下文管理策略。**变量混了。**
> 换成检索之后，判据才干净。

---

## 五种模式

| 模式 | 干了什么坏事 | 预期破坏 |
|---|---|---|
| `good` | 无（基线） | — |
| `dynamic_prompt` | 系统提示词**开头**塞一个每次都变的时间戳 | 缓存 |
| `shuffled_tools` | 每次请求打乱工具定义顺序 | 缓存 |
| `sliding_window` | 只保留最近 6 条，更早的丢掉 | 缓存 **+ 能力** |
| `flattened` | 拍平成 `USER: … ASSISTANT: …` 一整段纯文本 | 能力 |

## 第 0 步：先跑基线（3 分钟）

```bash
cd labs/ch2-context-engineering/2-4-bad-context-patterns
python3 agent.py good
```

### 👀 你会看到

```
  上下文：14 条消息 → 409 个输入 token
  第 1 次：预填充 148.9 ms   TTFT ...
  第 2 次：预填充   7.9 ms   ← 第 2 次快了 19 倍
  [回答] 37
  ✓ 答对了（37）
```

### 💡 学到什么

**第 2 次快 19 倍，因为前缀完全没变，KV 可以直接复用。**

这就是「保持前缀稳定」这条建议的**具体价值**——不是抽象的最佳实践，
是每次请求省下的那 140 毫秒。

---

## 第 1 步：把时间戳塞进系统提示词开头（4 分钟）★

```bash
python3 agent.py dynamic_prompt
```

这是书里点名的**最常见的错误**：为了让 agent「知道现在几点」，
在系统提示词里写 `Current time: 2026-07-29 10:30:45.123456`。

### 🤔 先猜

第 2 次还会快吗？

### 👀 观察什么

**两次的预填充耗时。**

### 💡 学到什么

**它永远不会快。** 因为时间戳带微秒——**每一次请求的前缀都是全新的**，
缓存**一次都命不中**。

而代价是**每一次请求都在付**：

```
good            第 2 次起   7.9 ms
dynamic_prompt  每一次    ~176 ms      ← 贵 22 倍，而且永远这样
```

> **一行看似无害的代码，让整条链路的预填充贵了一个量级。**
>
> 正确做法：时间戳要放就放在**对话末尾**（用户消息里），
> 或者干脆做成一个工具让模型需要时再查。
> **系统提示词的开头是最不该放动态内容的地方**——
> 因为缓存是**按前缀**匹配的，最前面的东西一变，后面全废。

## 第 2 步：滑动窗口（5 分钟）★★

```bash
python3 agent.py sliding_window
```

只保留最近 6 条消息。这是「省 token」最常见的做法。

### 🤔 先猜

它还答得出 1 号传感器的读数吗？

### 👀 观察什么

程序会明确告诉你窗口丢了什么，然后看答案。

### 💡 学到什么

```
  ☠ 注意：窗口滑掉了前 6 条，模型根本看不到前几个读数了
  [回答] 21
  ✗ 答错了：说的是 21，正确答案是 37
```

**它没有说「我不知道」，它给了一个看起来很像答案的数字。**
21 是它**还能看到**的某个读数——它拿了个手边有的数糊弄过去了。

> **这才是滑动窗口真正的危险：它不报错，它编。**
>
> 而且**这个模式同时属于两类破坏**：
> - 窗口滑动 → 前缀在变 → **缓存也废了**
> - 早期信息丢失 → **答案错了**
>
> **五种模式里，它是唯一两头都占的。** 而它偏偏是最流行的那个，
> 因为「省 token」听起来太合理了。

## 第 4 步：自己动手改（练习）

### 练习 1 ⭐ 把时间戳挪到末尾

改 `build_messages`，把 `dynamic_prompt` 的时间戳从系统提示词开头
挪到**最后一条用户消息**里。

**先猜**：缓存会命中吗？

> 这就是书里给的正确做法。做完你会明白：**问题不在"有动态内容"，
> 在"动态内容放在了前缀里"。**

### 练习 2 ⭐⭐ 让工具定义变大

现在 5 个工具只有 5 行。把每个工具的描述扩到 50 行（模拟真实的
JSON Schema），再跑 `shuffled_tools`。

**先猜**：效应会变明显吗？

> 本实验里 `shuffled_tools` 的效应很弱，因为工具定义只占很小一部分。
> 书里说「工具定义通常占上下文很大一部分（每个工具几百 token）」——
> **把条件补上，效应才显现。这也是为什么读实验结论要连着读它的前提。**

### 练习 3 ⭐⭐ 给滑动窗口打个补丁

改成：**丢消息，但把丢掉的工具结果先摘要成一条**塞在窗口最前面。

**先猜**：答案能救回来吗？缓存呢？

> 提示：摘要那条只要**内容稳定**，前缀就是稳定的。
> 这正是实验 2-1（上下文压缩）在做的事——**你刚刚自己推导出了它的动机。**

### 练习 4 ⭐⭐⭐ 换个更大的模型再跑 flattened

`flattened` 在本实验里**没有**破坏能力（0.6B 照样答对了 37）。
换 `qwen3:1.7b` 或更大的试试，再设计一个更复杂的任务。

**先猜**：什么样的任务才会让"拍平"真正出问题？

> 提示：书里说拍平的问题是「模型要额外花注意力推断角色边界」。
> 那么**角色边界越重要的任务，受影响越大**——比如需要区分
> 「谁说的话可信」的任务（回想实验 2-2 的 prompt 注入）。

## 附：概念速查

### 两类破坏，两种代价

| | 症状 | 你会发现吗 | 代价 |
|---|---|---|---|
| **破坏缓存** | 每次都慢、都贵 | 会（看账单/延迟） | 钱 |
| **破坏能力** | 偶尔给错答案 | **常常不会** | 正确性 |

> **后者更危险，因为它不报错。**

### 前缀稳定性的实操规则

```
系统提示词    ← 最稳定：只放永不变的东西
工具定义      ← 次稳定：顺序固定，内容固定
历史消息      ← 只追加，不修改、不删除
最新用户消息  ← 动态内容（时间戳、状态）放这里
```

**动态的东西越靠后越好。** 这一条就能避开本实验里的大部分坑。
