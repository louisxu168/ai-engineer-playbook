---

## 什么是渐进式披露

Agent Skills 把每个 Skill 拆成三层：

```
第 1 层  metadata   一行话        ← **永远**在上下文里
第 2 层  SKILL.md   核心流程      ← 需要时才加载
第 3 层  detail     细节参数      ← 真要用某个细节时才加载
```

模型先在清单里看到「pptx —— 生成和编辑 PowerPoint 演示文稿」，
判断这次任务要用它，**再去加载**它的详细文档。

---

## 这个实验怎么设计的

12 个 Skill。任务问的是：

> 「我要生成一份 16:9 的演示文稿。`slide_size` 这个参数应该怎么填？
>  请给出**确切的字符串**。」

**正确答案 `13.333x7.5@96` 只写在 pptx 的第 3 层 detail 文档里。**
第 1 层和第 2 层都没有——你可以自己验证：

```bash
python3 -c "
import skills
for n,meta,md,d in skills.SKILLS:
    if skills.CORRECT_FORMAT in meta: print('在 metadata:', n)
    if skills.CORRECT_FORMAT in md:   print('在 skill_md:', n)
    if skills.CORRECT_FORMAT in d:    print('在 detail:', n)"
```

### 三种模式

| 模式 | 上下文里有什么 |
|---|---|
| `all_loaded` | 12 个 Skill 的**全部三层**，一次性全塞进去 |
| `metadata_only` | 只有一句话清单，**没有加载工具** |
| `progressive` | 一句话清单 + `load_skill(name, level)` 工具 ★ |

### 🤔 先猜

- `progressive` 要加载几份文档才能答对？

### 👀 你会看到

三种模式画出一条清楚的取舍曲线（具体数字见 SOLUTION）。

### 💡 学到什么

**`metadata_only` 答不出来，而且它诚实地说了为什么：**

> 「我现在只能看到 pptx skill 的一句话说明，没有任何工具能加载它的详细文档。
> 所以我不知道 slide_size 的合法取值到底是……任何猜测都可能让你的调用直接失败。」

**这证明了那个信息确实不在上下文里**——不是模型不会，是它看不见。

而 `progressive` **一次就直奔 `pptx / detail`**，没有先加载 md 层，
也没有加载其他 11 个 Skill。

## 第 1 步：和检索对照着看（5 分钟）★

这个实验和前面两个是**同一个形状**：

| 实验 | 候选太多 | 怎么筛 |
|---|---|---|
| 3-2 检索 | 36 条记忆 | **BM25** 替模型筛 |
| 4-2 工具 | 40 个工具 | **BM25** 替模型筛 |
| **2-7 本实验** | 12 个 Skill | **模型自己**筛（它调 load_skill）|

**关键区别就在最后一列。**

### 为什么这个区别重要

回想[实验 4-2](../../ch4-tools/4-2-tool-selection/README.zh-CN.md) 那个失败：

> BM25 把正确的工具排在**第 9 名**，而切线在**第 8 名**。
> 模型**根本没机会看见它**，于是只能说「没有合适的工具」。

**渐进式披露没有这个失败模式**，因为筛选是模型自己做的——
它不会把自己需要的东西筛掉。

> **代价是什么？多一轮模型调用。**
>
> BM25 是「你替它决定」——快、便宜，但**可能决定错**。
> 渐进式披露是「它自己决定」——多一次往返，但**它不会漏掉自己知道要什么的东西**。
>
> ⚠️ 注意后半句的限定：「**自己知道要什么**」。
> 如果模型连「这事该用 pptx」都判断不出来，那清单再全也没用——
> 这时候瓶颈就回到了 metadata 那一行写得好不好。

## 第 2 步：自己动手改（练习）

### 练习 1 ⭐ 把 metadata 写烂

把 pptx 的 metadata 从「生成和编辑 PowerPoint 演示文稿」
改成含糊的「文档处理相关」，重跑 `progressive`。

**先猜**：它还找得到 pptx 吗？

> 这测的是渐进式披露的**真正瓶颈**：第 1 层那一行。
> 三层里只有它是永远在上下文里的，**也只有它决定模型会不会想到去加载。**
>
> 这条直接对应[实验 4-1](../../ch4-tools/4-1-tool-design/README.zh-CN.md)：
> **工具描述写不好，后面全白搭。**

### 练习 2 ⭐⭐ 让 Skill 变多、变大

把 12 个 Skill 复制到 100 个，每个 detail 文档扩到几千字。

**先猜**：`all_loaded` 和 `progressive` 的上下文差距会拉到多少倍？

> 本实验的规模很小（12 个 Skill，全量才 ~1900 字），所以差距只有约 2 倍。
> **真实的 Skill 库动辄几十上百个、每个几千 token** ——
> 那时候 `all_loaded` 根本不是一个选项。
>
> **本实验测到的比例是被规模压扁的，看趋势不看倍数。**

### 练习 3 ⭐⭐ 让任务需要两个 Skill

改成「把这份 Excel 里的数据做成 16:9 的演示文稿」——需要 xlsx **和** pptx。

**先猜**：它会加载几份？会不会漏掉一个？

> 多跳加载是渐进式披露最容易出问题的地方，
> 和[实验 3-2 练习 5](../../ch3-memory/3-2-retrieval/README.zh-CN.md)的多跳检索是同一个难点。

### 练习 4 ⭐⭐⭐ 混合：先检索再让它自己加载

用 BM25 从 100 个 Skill 里筛出 20 个的 metadata，再让模型在这 20 个里
用 `load_skill` 按需加载。

**先想清楚**：这样做，实验 4-2 那个「排第 9 被切掉」的风险回来了吗？

> 回来了——只是从「筛工具」变成了「筛 metadata」。
> **但代价小得多**：metadata 只有一行，你可以放心多留一些（比如 top-30）。
>
> **这就是真实系统的做法：在便宜的那一层做粗筛，在贵的那一层交给模型。**

## 附：概念速查

### 三种「候选太多」的解法

| 做法 | 谁来筛 | 失败模式 | 代价 |
|---|---|---|---|
| 全给 | 不筛 | 无（但可能装不下） | token |
| 检索（3-2 / 4-2） | **你的代码** | **筛错了模型看不见** | 召回风险 |
| 渐进式披露（本实验） | **模型自己** | 它想不到要加载什么 | **多一轮调用** |

### 一条工程原则

> **能让模型自己决定的筛选，就别替它决定——
> 除非候选多到连清单都放不下。**
>
> 因为你替它筛，错了它无从知道；它自己筛，至少知道自己在找什么。

## 卡住了？

| 你看到的 | 怎么办 |
|---|---|
| `progressive` 加载了好几份文档 | **正常**，模型可能先看 md 再看 detail。看它最终答对没有 |
| `metadata_only` 居然蒙对了 | 那说明这个参数格式在训练数据里很常见——**换一个更冷门的事实再试** |
| 想看真正发出去的提示词 | 把 `SHOW_PROMPT` 改成 `True` |
