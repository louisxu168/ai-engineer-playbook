# 实验 2-1 参考答案

[English](SOLUTION.md) · **简体中文**

> 自己跑过、预测错过之后再读。
> **不想跑命令也没关系** —— 下面全是真实运行输出，看着就能懂。

实测环境 `LAB_BACKEND=claude`，任务：

> 依次查这 5 座建筑的高度：Burj Khalifa、Shanghai Tower、Ping An Finance Centre、
> Merdeka 118、The Clock Towers。全部查完后，告诉我第一座比最后一座高多少米。

正确答案：**829.8 − 601 = 228.8 米**（若按屋顶高 828 算则是 227 米，两个都对，
取决于用哪个口径）。

---

## 一、四种模式，一张表看完

| 模式 | 提示词峰值 | 工具调用 | 压缩次数 | 答案 |
|---|---|---|---|---|
| `full` | **11,649 字符** | 较少 | 0 | ✅ 228.8 米 |
| `truncate` | 3,677 字符 | **29 次** ← 贵在这 | 0 | ✅ 但重查了一遍 |
| `compact` | 7,546 字符 → 压到 2,412 | 较少 | 2 | ✅ 228.8 米 |
| `compact_tiny` | 4,261 → 282 字符 | 较少 | 2 | ✅ 227 米 |

**一句话读懂这张表**：
`full` 上下文最大，`truncate` 上下文最小**但工具调用最多**，
`compact` 两头都不极端 —— 这就是三条路的取舍。

```
  提示词 7548 字符  █████████████████████████ +3714
  提示词 8536 字符  ████████████████████████████ +988
  提示词 8939 字符  █████████████████████████████ +403
  提示词 9750 字符  ████████████████████████████████ +811
  提示词 10189 字符 █████████████████████████████████ +439
  提示词 11337 字符 █████████████████████████████████████ +1148
  提示词 11649 字符 ██████████████████████████████████████ +312
```

从 140 涨到 11,649 —— **83 倍**。答案是对的，但每一轮你都在为前面所有轮的
内容重新付费（时间 + token）。

任务再长一点，这条线就会撞上窗口上限。**这就是需要压缩的原因。**

---

## 三、`compact`：★ 本实验的核心

```
  提示词 7546 字符  █████████████████████████ +3712
  ⟳ 压缩完成：7406 字符 → 1392 字符（省了 81%）
  提示词 2412 字符  ████████ -5134        ← 掉下来了
```

**条子肉眼可见地缩回去了。** 这就是压缩和裁剪最直观的区别。

而更值得看的是**它压出来了什么**（这段是模型自己写的，原样贴出）：

```
  ┌─ 压缩出来的摘要 ─────────────────────
  │ 任务：查询 5 座建筑的高度（Burj Khalifa、Shanghai Tower、
  │ Ping An Finance Centre、Merdeka 118、The Clock Towers）。
  │
  │ 已确认的高度数据：
  │ - Burj Khalifa（迪拜）：总高 829.8 m，屋顶高度 828 m
  │ - Shanghai Tower（上海陆家嘴）：632 m，128 层
  │ - Ping An Finance Centre（深圳）：599.1 m，115 层
  │ - Merdeka 118（吉隆坡）：678.9 m，118 层
  │ - The Clock Towers（麦加）：**正文未给出具体高度数字**
  │
  │ 还没做的事：
  │ 1. 获取 The Clock Towers 的确切高度（这是唯一缺失的高度）
  │ 2. 汇总 5 座建筑高度并按要求输出最终结果
  └──────────────────────────────────────
```

**注意三件事**：

1. **每个数字都保住了** —— 829.8、632、599.1、678.9 一个没丢
2. **它明确标出了「哪个还没拿到」** —— 这样下一轮才知道该干嘛
3. **过程被扔掉了** —— 搜了几次、读了哪些词条，全没了。这正是压缩的本意：
   **保留结论，丢掉过程。**

这三条不是自动发生的，是 `compact_prompt` 里那四条要求逼出来的：

```
1. **所有具体数字、名称、单位一个都不能丢** —— 这是它后面要用的
2. 已经做完的事写成结论，不要复述过程
3. 明确写出「还没做的事」
4. 不要加任何原文里没有的信息
```

> **压缩的质量，几乎完全取决于这段提示词。** 把第 1 条删掉再跑一次
> （练习 2），你会看到摘要变得很"通顺"但数字没了 —— 然后任务就崩了。

---

## 四、`truncate`：省了上下文，赔了重做

上下文确实压得最低（峰值只有 3,677 字符）。但看它第 5 轮说了什么：

```
  （丢弃 3 步，保留最近 1 步）
  [思考] 正文没给高度数字，而**前 3 步的结果已丢失**，所以我把 4 座塔的词条
         和 Clock Tower 的确切高度**一次性重新查回来**，不凭印象写数字。
  [工具 1/5] read({'title': 'Burj Khalifa'})     ← 重查
  [工具 2/5] read({'title': 'Shanghai Tower'})   ← 重查
  ...
```

**它把前面查过的全部重查了一遍。** 最终工具调用数：**29 次**，
远高于 `full` 和 `compact`。

> **裁剪不是免费的。** 你省下的是单轮的上下文长度，
> 付出的是「重新做一遍已经做完的事」—— 而重做同样要花时间和 token。

**顺带一个好消息**：它**没有编数字**，而是老老实实重查。这是因为系统提示词里
有这么一句：

```
绝对不要猜数字。数据不在上下文里就重新查，不要凭印象写。
```

把这句删掉再跑（练习 3），你大概率会看到它直接从记忆里报数 —— 那才是真正
危险的失败：**它看起来答对了，但那个数根本不是查来的。**

---

## 五、`compact_tiny`：压过头会怎样

摘要被限制成一句话，压缩率高达 **93%**（4,261 → 282 字符）：

```
  ⟳ 压缩完成：4261 字符 → 282 字符（省了 93%）
  │ 已确认高度：Shanghai Tower 632 米、Ping An Finance Centre 599 米；
  │ Burj Khalifa、Merdeka 118、The Clock Towers 三者仅有搜索摘要、
  │ 尚无精确高度，对这三条的 read 调用全部返回 HTTP 429，待重试读取后完成。
```

**这次它侥幸没崩**，因为一句话恰好塞得下当时仅有的两个数字。但注意：
`599.1` 变成了 `599`，**精度已经开始丢了**。最终答案用的是 828 而非 829.8，
算出 227 米。

数字再多几个，一句话就装不下了 —— **那时压缩就退化成了裁剪。**

> **压缩比例是个旋钮，不是越高越好。** 压到信息装不下的那一刻，
> 你付的钱（多一次模型调用）就白花了 —— 效果和直接裁剪一样，还更慢。

---

## 六、⚠️ 一个真实踩到的坑：HTTP 429

上面 `compact_tiny` 那次输出里有这么一句：

```
对这三条的 read 调用全部返回 HTTP 429 Too Many Requests
```

这是我连续跑了十几次实验，**把维基百科的限流撞出来了**。

代码里已经加了退避重试（2 秒 / 4 秒 / 6 秒），你正常做实验碰不到。
但这件事本身值得记住：

> **工具会失败，而且是以你没预料到的方式失败。**
> 更糟的是 —— 如果不重试、直接把 429 当错误传给模型，
> 它会以为「这个词条查不到」，然后**去编一个数字**。
>
> 工具层的健壮性，直接决定了 agent 会不会胡说。

---

## 七、练习答案

**1. 把 `KEEP_RECENT` 调大** —— 保留越多，重查越少、上下文越大。
你会发现它就是一个连续旋钮：`KEEP_RECENT = ∞` 就是 `full`，
`= 0` 就是最激进的裁剪。**没有最优值，只有权衡。**

**2. 删掉压缩提示词里「数字一个都不能丢」那条** —— 摘要会变得更"通顺"、
更像人写的，但数字开始消失。然后任务崩掉：模型发现数据没了，
要么重查（变慢），要么编（变错）。
**这题证明了压缩质量 ≈ 压缩提示词质量。**

**3. 删掉系统提示词里「不要猜数字」那句，再跑 truncate** ——
它大概率不再重查，而是直接从记忆里报数。**这是最危险的失败模式**：
答案看起来是对的，但它不是查来的，你也不知道它不是。

**4. 数一下 `truncate` 和 `full` 的工具调用差** —— 实测 29 次 vs 明显更少。
把这个差值乘以你的 API 单价，就是"裁剪"的真实成本。

**5. 让任务再长一倍**（比如查 10 座建筑）—— `full` 的曲线会继续往上走，
而 `compact` 会呈锯齿形（涨-压-涨-压）稳定在某个水平。
**那个锯齿就是生产环境里 agent 的真实样子。**

---

## 八、一句话总结

| | 上下文大小 | 额外成本 | 信息保留 |
|---|---|---|---|
| `full` | 一路涨，迟早爆 | 无 | 全部 |
| `truncate` | 最小 | **重做已完成的工作** | 丢掉的找不回来 |
| `compact` | 锯齿形，有界 | **每次压缩多一次模型调用** | 取决于压缩提示词 |

**没有免费的午餐 —— 你只能选择在哪里付钱。**

而最容易被忽略的一点：**压缩的质量几乎完全由那段压缩提示词决定。**
代码只有十几行，真正干活的是那四条要求。这和实验 1-1 的结论是同一件事：
**你调教 agent 的主要手段不是写 Python，而是改那段文字。**
