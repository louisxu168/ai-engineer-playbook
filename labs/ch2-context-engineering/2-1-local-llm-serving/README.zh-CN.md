# 实验 2-1：本地小模型 —— 看清楚 API 底下到底发生了什么

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. **0.6B 的模型也能可靠地调工具**——而且一次发两个并行调用（实测）
> 2. 在自己机器上量到真实的 **TTFT / tokens 每秒 / 预填充耗时**
> 3. 一个反直觉的发现：**本地部署一样会把「原始输出」洗干净**，
>    只是洗它的从云厂商变成了你机器上的 Ollama
> 4. **一个我没能复现的经典说法**——以及那次失败测出来的、真正站得住的数
>
> **怎么学**：全程在你自己的机器上跑，不联网、不花钱、不需要 API key。
>
> **需要多久**：25 分钟（含安装）。
>
> ⚠️ 这是本仓库**唯一**需要额外安装的实验（Ollama + 一个 500MB 的模型）。

## 先说这个实验为什么特别

前面所有实验都是通过 Claude Code / Codex / API 去问一个**很大的、别人家的**模型。
那些接口很贴心——它们把模型的原始输出**洗干净**了才给你：思考标签剥掉了、
特殊 token 去掉了、工具调用解析成结构化字段了。

这个实验把那层洗掉的东西**尽量**拿回来，方式是：**在你自己的机器上跑模型**。

而且是个 **0.6B（六亿参数）** 的模型。作为对照，你平时用的模型大概是它的
**几百到上千倍**。

## 第 0 步：装环境（5 分钟，一次性）

```bash
# 1. 装 Ollama
brew install ollama                 # macOS；其他系统见 https://ollama.com/download

# 2. 起服务（另开一个终端窗口，让它一直跑着）
ollama serve

# 3. 下模型（约 500MB，只需一次）
ollama pull qwen3:0.6b
```

**不需要独立显卡、不需要 CUDA。** 在 Apple Silicon 上 Ollama 会用 Metal
（也就是芯片里的 GPU）；实测 M3 上生成速度 **113~131 token/s**。

Python 这边**没有任何依赖**——只用标准库。这是故意的：用官方 SDK 的话，
流式解析和计时全被它包起来了，而那正是本实验要看的东西。

```bash
cd labs/ch2-context-engineering/2-1-local-llm-serving
python3 agent.py                    # 先看用法
```

> 不想装？本章其他三个实验（2-1 / 2-2 / 2-3）都不需要它。

## 第 1 步：看「原始」输出（5 分钟）★

```bash
python3 agent.py raw
```

### 👀 你会看到

```
  ┌─ 模型吐出来的原始文本 ───────────

  │ [thinking] 好的，用户问温哥华现在几点和天气怎么样。首先，我需要确认温哥华的
  │ 当前时间…… 因此，正确的做法是先调用 get_time 和 get_weather，然后给出结果。
  │
  │ [content] TOOL: {"name": "get_time", "args": {"city": "Vancouver"}}
  │ TOOL: {"name": "get_weather", "args": {"city": "Vancouver"}}
  └──────────────────────────────────

  TTFT 197 ms   ·   生成 205 token   ·   131.1 token/s   ·   输入 110 token
```

### 💡 学到什么

**两件事。**

**① 0.6B 真的能调工具，而且一次发了两个。** 它自己判断出「时间」和「天气」
互不依赖，所以一次性把两个调用都发了出来——这正是并行执行的前提。

**② 但你看那个 `[thinking]` / `[content]` 标签——那条线不是模型划的。**

模型生成的本来是**一整段**带 `<think>…</think>` 的连续文本。
**是 Ollama 在服务端把标签剥掉、拆成两个 JSON 字段才发给你的。**

> **这是本实验第一个反直觉的地方：**
> 我本来想让你看到「API 看不到的原始 token 流」，
> 结果发现**本地部署一样会洗**——只是洗它的从云厂商变成了你自己机器上的进程。
>
> 我试过绕过模板层（`/api/generate` 的 `raw:true`）去拿真正的 `<think>` 三个字符，
> **没成功**，具体过程见 SOLUTION 第 2 节。

**「原始」这件事是分层的。你以为的底层，下面还有一层。**

---

## 第 2 步：看解析（3 分钟）

```bash
python3 agent.py parsed
```

同一段输出，切成三段：思考 / 给用户的话 / 工具调用。

### 💡 学到什么

打开 `agent.py` 看 `split_output()`——**那三段是我用正则切出来的**，
不是模型分三个字段给你的。

云端 API 之所以能给你结构化字段，做的是同一件事，只是做在服务端。

> **注意这三段的顺序：先思考 → 再说话 → 最后发工具调用。**
>
> 这个顺序是固定的，也是流式 UI 能做「思考中…」的原因：
> 看到 thinking 就切状态，第一个工具调用一解析完就可以**立刻开始执行**，
> **不用等模型把话说完**。这是流式带来的真实延迟收益。

## 第 3 步：完整 ReAct 循环（4 分钟）

```bash
python3 agent.py react
```

### 👀 你会看到

```
  ── 第 1 轮 ──
  ★ 这一轮它一次发了 2 个工具调用 —— 两件事互不依赖，可以并行执行
  [调用] get_time({"city": "Vancouver"})     → {"time": "2026-07-29 09:56"}
  [调用] get_weather({"city": "Vancouver"})  → {"weather": "小雨", "celsius": 14}

  ── 第 2 轮 ──
  [最终回答] 温哥华现在时间是2026年7月29日09:56，天气为小雨，温度14摄氏度。
```

### 💡 学到什么

**这就是实验 1-1 那个循环**，一个字都没变：

```
llm(messages) → 工具调用 → 你的代码执行 → 结果拼回去 → 再来
```

唯一的区别是模型从云端换成了你机器上的 0.6B。**循环本身和模型大小无关。**

> 它还正确地把两个工具的结果**合成了一句话**——这需要它理解两个结果分别是什么。
> 六亿参数做到了这件事。

## 第 4 步：量延迟，以及一个没能复现的说法（8 分钟）★★

```bash
python3 agent.py cache
```

这个模式用一个约 **2000 token** 的长系统提示词，量三组的**预填充耗时**
（`prompt_eval_duration`，也就是处理**输入**花的时间）：

| 组 | 做什么 |
|---|---|
| **A** | 完全固定的系统提示词，连跑 3 次 |
| **B** | 每次在**开头**塞一个从没出现过的会话 ID |
| **C** | 每次在**结尾**塞一个从没出现过的会话 ID |

### 🤔 先猜

书上（以及几乎所有讲 KV Cache 的文章）说：**改动开头会让前缀缓存失效**。

所以 **B 应该明显比 C 慢**。你觉得呢？

### 👀 观察什么

**三组的预填充耗时，尤其是 B 和 C 的差别。**

### 💡 学到什么

**我没能复现那个说法。** B 和 C **没有稳定差别**——两组都是
「第一次很慢、之后就快了」，和 ID 放在开头还是结尾无关。

但这次失败量到了一个**非常站得住**的数：

```
模型冷加载后的第一次调用   ≈ 1000 ms
之后的每一次调用           ≈ 10~40 ms
```

**差了大约两个数量级，而且每次都复现。**

> ⚠️ 我第一次做这个实验时用的是 110 token 的短提示词，预填充只有 10ms 左右，
> **完全淹没在噪声里**——三次跑出了三种互相矛盾的结论。
>
> **这本身就是一课：要测一个效应，先确认它大到能被测出来。**
> 具体过程和全部数字见 SOLUTION 第 4 节。

而下面这条，才是**上下文工程真正的理由**：

> **2050 token 的输入，冷启动预填充要 1 秒。**
> 输入越长这个数越大，而且缓存没命中的话**每次请求都要付**。
>
> **这就是实验 2-9（上下文压缩）存在的原因。**

## 第 5 步：自己动手改（练习）

### 练习 1 ⭐ 换个更大的模型

改 `agent.py` 开头的 `MODEL`：

```bash
ollama pull qwen3:1.7b     # 约 1.4GB
```

**先猜**：token/s 会掉多少？工具调用会更准吗？思考会更长吗？

> 这道题让你对「模型大小 ↔ 速度 ↔ 质量」建立**第一手**的直觉，
> 而不是从别人的 benchmark 里读来的。

### 练习 2 ⭐⭐ 让它做一件需要**依赖**的事

现在的问题（时间 + 天气）两件事互不依赖，所以能并行。
换一个**必须串行**的问题，比如：

> 「温哥华现在几点？如果那边已经过了晚上 8 点，就告诉我北京的天气。」

**先猜**：它还会一次发两个工具调用吗？还是会先调一个、看结果再决定？

> 这正好对照实验 1-1 里那个结论：**依赖关系是在提示词层面解决的，
> 不是靠代码校验。** 现在你可以在一个 0.6B 上验证它。

### 练习 3 ⭐⭐ 关掉思考

给 `chat_stream` 传 `think=False`，重跑 `raw`。

**先猜**：速度会快多少？工具调用还对吗？

> 思考是**要花 token 的**。看看这个任务上那些 token 买到了什么。

### 练习 4 ⭐⭐⭐ 把 KV Cache 那个效应挖出来

我没复现出「开头 vs 结尾」的差别。**你来试试**，几个方向：

- 把系统提示词加长到 8000 甚至 16000 token（效应应该随长度放大）
- 每次都用**全新的随机前缀**，且**不重复**（避免命中之前缓存的那一份）
- 换 vLLM 试试——它的前缀缓存实现和 llama.cpp 不同
- 别看 `prompt_eval_duration`，直接量**端到端 TTFT** 的分布

**如果你复现出来了，那是个真发现，记下来。**

> 顺带一个更值钱的问题：**为什么几乎所有文章都在讲这个效应，
> 而我在一个真实的本地栈上量不出来？**
> 这是个很好的提醒——**技术传言的传播速度，远快于它被验证的速度。**

### 练习 5 ⭐⭐⭐ 用 Ollama 原生的 tools 参数

本实验故意用**文本协议**（`TOOL: {...}`），就是为了让你**看见**工具调用长什么样。
改成 Ollama 原生的 `tools` 参数试试。

**先猜**：你还能在输出里看到那一行吗？

> 答案会让你再一次体会本实验的主题：**每加一层抽象，你就少看见一样东西。**

## 附：概念速查

### 延迟到底花在哪

一次生成分两段，它们的成本模型完全不同：

| 阶段 | 干什么 | 快慢取决于 | 本实验实测 |
|---|---|---|---|
| **预填充**（prefill） | 把**输入**过一遍，算出 KV | **输入有多长** | 2050 token 冷启动 ≈ 1000 ms |
| **解码**（decode） | 一个一个吐**输出** token | **输出有多长** | ≈ 131 token/s |

> **上下文工程优化的是第一段。** 你的对话历史每长 1000 token，
> 每一次请求的预填充就多付一次。

### 「原始输出」是分层的

```
模型真正生成的 token 序列
   ↓  推理引擎（llama.cpp）按模板切
<think>…</think> + 正文 + <tool_call>…
   ↓  Ollama 服务端解析
{"thinking": "...", "content": "...", "tool_calls": [...]}
   ↓  SDK 再包一层
response.message.content
```

**你在哪一层，就只能看见那一层以下被打包好的东西。**
本实验让你往下走了两层，但**没能走到最底下**。
