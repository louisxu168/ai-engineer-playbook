# 实验 10-1：单 agent vs 多 agent —— 多几个到底换来了什么

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. 实测：**单 agent 完胜** —— 8/8 全找到、0 误报、1 次调用。多 agent 一个都没赢
> 2. 三种多 agent 模式各自的**特征性失败**：切数据丢上下文、专家过度上报、复核员过度删除
> 3. 加 agent 之前必须先问的一个问题：**单 agent 到顶了吗？**
> 4. 一个我自己踩的坑：**模型报的"误报"，其实是我的标准答案错了**
>
> **怎么学**：判据是机械的——标准答案是写死的 8 个编号，召回和误报都是集合运算。
> 和实验 3-2 一样，是本仓库最可靠的那一类判据。
>
> **需要多久**：25 分钟。

---

## 先说结论，因为它可能和你预期相反

「多 Agent 协作」是这两年最容易被神化的词。这个实验用**同一个任务、同一个模型**
把它拆成四种具体做法量了一遍，结果是：

| 模式 | 找到 | 误报 | 调用 |
|---|---|---|---|
| **single**（1 个 agent） | **8/8** | **0** | **1** |
| chunked（4 个，按数据切） | 8/8 | 0 | 4 |
| specialists（4 个，按关注点切） | 8/8 | **2** | 4 |
| critic（找 + 复核） | **7/8** | 0 | 2 |

**单 agent 在每一列上都不输，而且便宜 2~4 倍。**

这不是说多 agent 没用。是说：

> **多 agent 买的是「headroom」（单 agent 够不着的那部分），
> 而你得先确认那部分**存在**。**

这个实验的价值就在于教你**怎么确认**。

---

## 任务

审查 24 段代码，找出有安全问题的。**恰好 8 段有问题**：

| 类别 | 明显的 | 隐蔽的 |
|---|---|---|
| SQL 注入 | S01 字符串拼接 | S09 f-string 拼接 |
| 硬编码密钥 | S03 明文 API key | S11 默认参数里的 admin token |
| 路径穿越 | S05 直接拼路径 | S14 `normpath` 但没校验前缀 |
| 未校验输入 | S07 直接 `int()` | S15 表名来自请求体 |

**每类都有一段明显、一段隐蔽**——因为明显的谁都能找到，
**多 agent 的价值只可能体现在隐蔽的那 4 个上**。

## 第 0 步：先测天花板（4 分钟）

```bash
cd labs/ch10-multi-agent/10-1-single-vs-multi
python3 agent.py single
```

### 🤔 先猜

一个 agent 看 24 段，能找到几个？隐蔽的那 4 个能找到几个？

### 👀 你会看到

```
  ✓ 找到：S01, S03, S05, S07, S09, S11, S14, S15
  ✗ 漏掉：—
  ✓ 无误报
  召回率：8/8    其中：明显的 4/4，隐蔽的 4/4
  模型调用：1 次
```

### 💡 学到什么

**满分。** 而这恰恰是最重要的一步：

> **在加 agent 之前，先测单 agent 到顶了没有。**
>
> 如果单 agent 已经 8/8，那么无论你加多少个、怎么组织，
> **召回率最多也只能是 8/8** —— 你花的每一分钱都买不到任何东西。

这一步在真实项目里几乎总是被跳过。大家直接上多 agent，
然后把「效果不错」归功于架构，其实单 agent 本来就能做到。

## 第 1 步：按【数据】切 —— 最直觉的那种多 agent（5 分钟）

```bash
python3 agent.py chunked
```

把 24 段切成 4 份，4 个 agent 各看 6 段，结果取并集。

### 🤔 先猜

会比 single 好吗？

### 💡 学到什么

**一样是 8/8，但花了 4 倍的钱。**

而且请注意它**结构性地丢掉了什么**：每个 agent 只看到 1/4 的代码。

> 在这个任务里无所谓，因为每段代码是**独立**的。
> 但如果问题需要**跨段推理**呢？——比如「S03 定义的 key 在 S22 里被打进了日志」。
> **切数据的那一刀，直接切断了这种发现的可能。**

这是 chunked 模式的特征性失败：**它假设问题是局部的。**

---

## 第 2 步：按【关注点】切 —— 成本一样，切法不同（5 分钟）★

```bash
python3 agent.py specialists
```

同样 4 个 agent、同样 4 次调用，但这次每个 agent **看全部 24 段，只找 1 类问题**。

### 🤔 先猜（本实验最值得猜的一题）

`chunked` 和 `specialists` **成本完全一样**。哪个效果更好？

### 👀 观察什么

**盯住误报那一行。**

### 💡 学到什么

结果可能和你想的相反（见 SOLUTION）。

原因值得琢磨：**你告诉一个 agent「你只负责找 X」，它就会去找 X。**
哪怕这批代码里根本没有 X，它也倾向于交出点什么。

> **专家模式的特征性失败：过度上报。**
> 手里拿着锤子，看什么都像钉子——这句话对 agent 一样成立。
>
> 而且这个失败**是被你的提示词制造出来的**：
> 「这一轮只找路径穿越」本身就在暗示「这里有路径穿越」。

## 第 3 步：加一个复核员（5 分钟）★★

```bash
python3 agent.py critic
```

先用 single 找一遍，再让**另一个 agent 逐条判**哪些是真问题、哪些是误报。

### 🤔 先猜

复核员能提高什么？会不会损失什么？

### 👀 观察什么

**逐条读复核员给出的判断和理由。** 特别是它判为「误报」的那条。

### 💡 学到什么

先想清楚一个结构性的事实：

> **复核员只能删，不能加。**
> 第一阶段漏掉的，第二阶段**永远**找不回来。
> 所以它买的是**精确率**，不可能是召回率。

然后看实测结果——**它删错了**。而更值得看的是它给出的理由：
它写下的理由**恰恰论证了这条应该保留**，然后它标了「误报」。

> **推理是对的，结论是反的。** 详见 SOLUTION，这是本实验最好的一段。

## 第 5 步：自己动手改（练习）

### 练习 1 ⭐⭐ 制造 headroom

单 agent 已经满分，所以这个实验里多 agent 无处可赢。**给它造点难度**：

- 把片段数量从 24 加到 100（复制那些干净的，改改变量名）
- 或者加入更隐蔽的第 5 类问题

**先猜**：到多少段的时候，single 开始漏？那个点就是**多 agent 开始有意义的点**。

> 这才是这个练习真正要教的：**多 agent 的收益是有前提的，
> 而那个前提可以被测量。**

### 练习 2 ⭐⭐ 造一个需要跨段推理的问题

加两段代码：一段定义了硬编码 key，另一段把它写进了日志。
**单独看每一段都不算严重，合起来才是事故。**

**先猜**：`chunked` 模式（把这两段分到不同 agent）还找得到吗？

> 这是 chunked 的**结构性盲区**，不是它的运气问题。

### 练习 3 ⭐⭐ 给专家加一句「可以什么都不报」

在 `sys_specialist` 里加一句：「**如果这一类问题一个都没有，就返回空列表——
这是完全正常的结果**」。

**先猜**：误报会降下来吗？

> 这条如果有效，它说明的事情很重要：**专家的过度上报，
> 是被提示词的隐含预期制造出来的，不是模型的固有缺陷。**

### 练习 4 ⭐⭐⭐ 让复核员只能降级不能删除

改 `run_critic`：把 keep/drop 换成「高置信 / 低置信」，**两种都保留**，
只是标注不同。

**先猜**：召回还会掉吗？

> 这是真实系统的常见做法：**不可逆的删除交给人，agent 只负责排序。**
> 想想为什么——回头看实验 4-1 的幂等键那一节，是同一个思路。

### 练习 5 ⭐⭐⭐ 把三种组合起来

specialists 找 → 合并 → critic 复核。

**先猜**：召回和误报分别会怎么变？花几次调用？

> 做完请对着 single 那一行看：**你花了 6 倍的钱，买到了什么？**
> 如果答案是「什么也没买到」，那就是本实验最重要的一课。

## 附：概念速查

### 三种多 agent 模式的特征性失败

| 模式 | 它假设了什么 | 特征性失败 |
|---|---|---|
| 按数据切（chunked） | 问题是**局部**的 | 跨片段的问题**结构性**看不见 |
| 按关注点切（specialists） | 每类问题**都存在** | **过度上报**（手里有锤子） |
| 复核（critic） | 第一遍**召回够了** | **过度删除**，且只能删不能加 |

### 加 agent 之前的三个问题

1. **单 agent 到顶了吗？** 没测过就加，等于买你不知道有没有的东西
2. **我按什么维度切？** 数据？关注点？阶段？——切错维度 = 纯增成本
3. **每个 agent 看到的信息变少了吗？** 如果是，你在用召回换并行

### 一条工程原则

> **多 agent 不是"更强"，是"用成本换 headroom"。**
> **没有 headroom 的时候，你买到的只有成本。**

这和实验 4-2（工具检索）、5-1（编辑格式）是同一个形状：
**先量清楚你的问题有多严重，再决定值不值得引入新的复杂度和新的失败模式。**
