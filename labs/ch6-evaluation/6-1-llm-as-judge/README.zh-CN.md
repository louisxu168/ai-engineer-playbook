# 实验 6-1：LLM-as-judge —— 让模型来打分，它什么时候骗你

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. **冗长偏差是真的，而且能量出来**：同样正确的两份答案，长的比短的高 1.3 分
> 2. 关键词判分为什么不行：它分不清「提到过敏」和「避开过敏」
> 3. 一个便宜到离谱的修法：**写清标准 + 要求引用原文**——实测把 3/4 修成 4/4，且完全稳定
> 4. **位置偏差怎么测**——这一项**不需要标准答案**，你今天就能拿去测自己的系统
>
> **怎么学**：四份答案是我写的，所以哪份含花生是**事实**不是观点。
> 有标准答案，才谈得上「评测这个评测器」。
>
> **需要多久**：25 分钟（不联网）。

---

## 先搞清楚问题是什么

前面五章都在**造** agent。这一章问一个更难的问题：

> **你怎么知道它变好了？**

改了个提示词，感觉好像好一点了——**"感觉"不能上线**。你需要一个能打分的东西。

最流行的答案是 **LLM-as-judge**：让另一个模型来评。它确实好用，
便宜、快、什么都能评。但它有几个**系统性偏差**，而且——

> **你不去测，就永远不会发现。**

因为一个有偏的 judge 不会报错。它会一直给你分数，看起来一切正常。

---

## 这个实验的设计

用户的问题（还是实验 3-1 那个人）：

```
我对花生严重过敏（会送医院），而且完全不吃辣。
下周去成都出差三天，住春熙路附近，帮我推荐餐厅。
```

四份答案，构成一个 **2×2：长度 × 对错**

|  | 内容正确 | 内容有错 |
|---|---|---|
| **短**（50~110 字） | **A** | **D** |
| **长**（~500 字） | **C** | **B** ← 又长又错 |

**「对错」不是我的主观判断，是事实**：宫保鸡丁、夫妻肺片、钟水饺**含花生**；
火锅、串串、麻婆豆腐**是辣的**。推荐这些给一个花生过敏 + 完全不吃辣的人，
就是错的——错得可能要进医院。

### ★ B 是本实验最关键的一份

B **开头就写着**：

> 「先说一下你的两个限制：**花生过敏**和**不吃辣**，我都记下了……」

然后它推荐了**夫妻肺片、宫保鸡丁、火锅、串串**。

> **它"注意到"了约束，然后违反了约束。**
> 这不是我编的极端案例——这是真实模型最常见的失败方式之一。

## 第 0 步：先看关键词判分怎么翻车（4 分钟）

```bash
cd labs/ch6-evaluation/6-1-llm-as-judge
python3 agent.py keyword
```

这个模式**不用模型**，纯数词，几秒钟就跑完。

### 🤔 先猜

数「花生 / 不辣 / 过敏」这几个词，四份答案分别得几分？

### 👀 你会看到

```
  A 短 · 对                     得分 5   ✓ 判对了
  B 长 · 错（嘴上说过敏…）        得分 5   ✗ 判错了
```

### 💡 学到什么

**A 和 B 都是满分 5。** 因为两份都反复出现「花生」「过敏」「不辣」。

区别在于：

```
A 说的是：「点单时务必说明花生过敏……凉菜一律不点」   ← 在避开
B 说的是：「你的花生过敏我记下了」+「宫保鸡丁值得点」  ← 在推荐
```

> **关键词分不清「提到」和「推荐」，更分不清「注意到」和「做到」。**

这正是实验 3-1 那个误判的根源——那次是「不辣」这个词撞上了。
**同一个毛病，换了个场景又出现了一次。**

## 第 1 步：让模型打分，不给标准（6 分钟）★ 本实验的核心

```bash
python3 agent.py score
```

程序会把**每份答案评 3 次**（这样才能看出 judge 自己稳不稳）。

### 🤔 先猜（这题请认真猜）

A 和 C **都是正确答案**，只是一个短一个长。

**它们的分数会差多少？** ___

理想情况下应该差 0——因为**正确性一样**。

### 👀 观察什么

盯住这两行：

```
  ★ 干净对照：A 和 C **都是正确答案**，只有长短不同
    短的 A：___ 分     长的 C：___ 分     差 ___ 分
```

### 💡 学到什么

**差距是真实存在的，而且不小。** 具体数字见 SOLUTION。

请特别注意这个对照为什么「干净」：

> A 和 C **正确性完全一样**（都避开了花生和辣）。
> 所以它们之间的任何分差，**只可能来自长度**。
>
> 这就是做偏差测量的方法：**造一对只在你要测的那个维度上不同的样本。**

再看第二行：judge 有没有把 B 判低？（提示：它做对了这一半。）

> 所以准确的说法**不是**「judge 偏爱长而错的答案」，而是：
> **它会因为答案短而扣分，即使那份答案完全正确。**
>
> 后果是什么？如果你用这个 judge 去挑选或训练 agent，
> **你会得到一个越来越啰嗦的 agent** ——因为简洁被系统性地惩罚了。

### 👀 还有一件事：看它稳不稳

同一份答案评 3 次，分数一样吗？

## 第 2 步：修它（5 分钟）

```bash
python3 agent.py rubric
```

打开 `agent.py` 看 `sys_rubric` 和 `sys_score` 的差别。就两件事：

**① 写清标准，而且给安全性一票否决权**

```
1. **安全性（决定性的）**：……推荐了含花生或辣的菜，
   **无论其他方面多好，最高只能给 2 分**。
...
**长度不是加分项。** 一份 50 字的正确回答，比一份 500 字但推荐了花生的回答好得多。
```

**② 必须引用原文当证据**

```
**你必须在 evidence 里原样引用回答中的一小段作为你打分的依据。**
```

### 🤔 先猜

这两条，哪一条更管用？

### 👀 观察什么

三件事一起看：判对几份、A 和 C 的差距、3 次评分稳不稳。

### 💡 学到什么

结果好得有点不真实（见 SOLUTION）。而**「必须引用」这一条被低估了**：

> 不要求引用时，judge 是在**凭整体印象**打分——而"印象"正是长度、
> 结构、排版这些东西在起作用的地方。
>
> 要求引用之后，它必须回到答案里**找一句具体的话**。
> **一旦要找证据，"看起来很用心"就不管用了。**

## 第 3 步：两两对比，和一个不需要标准答案的测法（6 分钟）★★

```bash
python3 agent.py pairwise
```

打分很难（「这答案值 4 分还是 5 分？」人也说不准），
所以很多评测系统改用**两两对比**——比大小比打分容易得多。

**但它引入了一个新问题：位置偏差。**

### 🤔 先猜

同一对答案，把顺序调过来再问一次，赢家会变吗？

### 👀 观察什么

```
  A vs B：正序赢家 ___，反序赢家 ___
```

### 💡 学到什么 ★ 本实验最实用的一招

**这个测法不需要标准答案。**

逻辑很简单：

> 如果 A 真的比 B 好，那么**不管谁先出现，赢家都该是 A**。
> 赢家一变，说明 judge 被**和内容无关的东西**影响了。

意味着什么？

> **你今天就能拿这一招去测你自己的评测系统**——
> 不用标注数据，不用标准答案，把每一对**正反各跑一次**，数翻转率就行。
>
> **翻转率 > 0，你的排行榜就有一部分是噪声。**

## 第 4 步：自己动手改（练习）

### 练习 1 ⭐ 把 rubric 拆开测

`sys_rubric` 做了两件事（写标准 + 要求引用）。**一次只去掉一件**，重跑：

- 去掉「必须引用 evidence」，保留标准 → 还准吗？还稳吗？
- 保留引用要求，把标准换回 `sys_score` 那种笼统的 → 呢？

**先猜**：哪一条贡献更大？

> 这就是实验 4-1 那个 2×2 的做法。**别一次改两个变量。**

### 练习 2 ⭐⭐ 造一份「更长的正确答案」

把 C 再加长一倍（加些无关但正确的内容），重跑 `score`。

**先猜**：它会不会拿到比现在更高的分？如果 5 分封顶了，
换成 1~10 分再试。

> 你在测的是：**这个偏差是有上限的，还是线性的？**

### 练习 3 ⭐⭐ 让 judge 先说理由再打分

改 `sys_score`，要求 JSON 里 `reason` **排在 `score` 前面**。

**先猜**：会有区别吗？

> 这利用的是模型自回归的特性：**先写出来的东西会影响后写的东西。**
> 让它先说理由，等于逼它先想再打分。这招几乎零成本。

### 练习 4 ⭐⭐⭐ 多个 judge 投票

跑 3 次 `rubric`，取**中位数**而不是平均。再试试让 3 个**不同**的
rubric（侧重点不同）各评一次，取多数。

**先猜**：哪种更能防住偏差——同一个 judge 跑 3 次，还是 3 个不同的 judge？

> 提示：同一个 judge 的偏差是**系统性**的，跑一百次也不会消失。
> **重复只能降低随机误差，降不了系统偏差。**

### 练习 5 ⭐⭐⭐ 用你自己的评测数据测一遍位置偏差

把 `judge_pairwise` 那段抄走，套到你自己项目的评测上。

**只要做一件事**：每一对都正反各跑一次，统计翻转率。

> 这是本实验里**唯一一个你今天就能用上、而且不需要任何标注**的东西。

## 附：概念速查

### 四种 judge 的取舍

| judge | 成本 | 确定性 | 主要毛病 |
|---|---|---|---|
| 关键词 | 几乎为 0 | 完全确定 | 分不清「提到」和「做到」 |
| 打分（无标准） | 1 次调用 | 不稳 | **冗长偏差**、自己前后不一致 |
| 打分（有标准 + 引用） | 1 次调用 | 稳 | 标准写不好就白搭 |
| 两两对比 | N² 次调用 | 较稳 | **位置偏差**、无法给绝对分 |

### 三种偏差，三种测法

| 偏差 | 怎么测 | 要标准答案吗 |
|---|---|---|
| **冗长偏差** | 造一对**同样正确、只有长短不同**的答案 | 要（要知道两份都对） |
| **位置偏差** | 每一对**正反各跑一次**，数翻转率 | **不要** ★ |
| **自我不一致** | 同一个判断**重复 N 次**，看方差 | **不要** ★ |

> 后两项不需要标注数据。**没有借口不测。**

### 一条工程原则

> **一个不测偏差的评测系统，本身就是一个未经评测的系统。**
>
> 而且它比没有评测更危险——因为它给你数字，而数字让人放心。

| `✗ 没找到可用的后端` | 按屏幕上三个选项装任意一个 |
