# 实验 02 参考答案

[English](SOLUTION.md) · **简体中文**

> 自己跑过、预测错过之后再读。

以下是 `LAB_BACKEND=claude` 下的实测结果。默认问题：
**「迪拜最高的建筑和上海最高的建筑，哪个更高？高多少米？」**

正确答案：哈利法塔 828 米（屋顶）/ 829.8 米（含尖顶），上海中心 632 米，
差 **196 米**。

---

## 实测结果

| 模式 | 轮数 | 工具调用 | 你能看到的 | 答案 |
|---|---|---|---|---|
| `hosted` | 厂商内部若干轮 | 看不见 | **只有最终文字** | ✅ 196 米，附 6 个来源 |
| `diy` | 5 | 7 | **每一步** | ✅ 196 米（并指出 829.8 的口径差异） |
| `no_search` | 1 | 0 | 1 步 | ✅ **196 米 —— 居然对了**，见下 |

---

## 逐个说

### `hosted` —— 又快又好，但你是瞎的

答案质量很高：828 vs 632，差 196 米，还额外补充了 CTBUH 的 829.8 米口径差异，
并列了 6 个来源（吉尼斯、维基、大英百科、上海国资委…）。

**但整个过程你一点都没看见。** 我们只发了一句话过去，剩下全在厂商那边跑完。
程序最后会打印这段提醒：

> 注意你看不到的东西：它搜了什么关键词？看了哪些网页？中间读到过什么？
> 失败重试过吗？—— 全都没有。只有最后这段文字。

**这不是缺陷，是交易。** 你用可观测性换开发成本。问题在于很多人做选择时
没意识到自己在交易。

### `diy` —— 慢，但每一步都在

5 轮 7 次工具调用。慢很多，但轨迹里出现了三件 hosted 模式永远不会告诉你的事：

**1. 第 1 轮搜索直接失败了**

```
[工具] search({'query': '迪拜最高建筑 哈利法塔 高度'})
      -> {"error": "没搜到结果"}
```

中文关键词打英文维基百科，零结果。**在 hosted 模式下这种失败你根本不会知道。**

**2. 第 2 轮它自己纠正了**

```
[思考] 中文关键词搜不到，改用英文名称搜索这两座建筑。
[工具] search({'query': 'Burj Khalifa'})   -> 命中
```

这就是真实 agent 的容错长相：工具返回错误 → 进上下文 → 模型看见 → 换策略。
这也是为什么工具出错要 `return {"error": ...}` 而不是抛异常。

**3. 第 3 轮暴露了 search 和 read 的分工**（本实验最重要的一点）

```
[思考] Shanghai Tower 摘要给出 632 米，但 Burj Khalifa 摘要没给数字，
       需要读正文拿到精确高度。
[工具] read({'title': 'Burj Khalifa'})
      -> {"extract": "…total height of 829.8 m…"}
```

同样是搜索命中，上海中心的摘要**恰好**带了 632 米，哈利法塔的摘要**没有数字**。
所以它必须再调 `read`。

> **search 返回的是线索，不是答案。**

这就是「agentic search」和「朴素 RAG」的分界线。朴素 RAG 把 top-k 检索结果
一股脑塞进 prompt 就完事；agentic search 会判断"这条线索够不够"，不够就去读正文。
**如果你只给它 search 不给它 read，它就只能用摘要里碰巧有的东西凑答案。**

**4. 第 4 轮它还发现了口径歧义**

```
[工具 1/2] calc({'expression': '828 - 632'})   -> 196
[工具 2/2] calc({'expression': '829.8 - 632'}) -> 197.8
```

828（屋顶高）还是 829.8（含尖顶）？它两个都算了，在答案里说明了差异。
这是好行为，值得注意。

### `no_search` —— 它答对了。这是个意外

预期是"没有搜索工具，它会瞎编或者拒答"。实测：**1 轮，0 次工具调用，答案完全正确。**

```
[思考] 无联网工具，凭记忆：迪拜哈利法塔828米，上海中心大厦632米，前者更高196米。
[答案] …哈利法塔更高，高出约196米（828 − 632 = 196米）。
       注：数据为建筑结构高度（含尖顶），凭记忆给出，未联网核实。
```

**为什么？因为这个事实太有名、也太稳定了。** 哈利法塔 828 米是训练数据里出现了
无数次的常识，而且它十几年没变过。这种问题，搜索只是在增加成本和延迟。

注意它还**主动标注了不确定性**（"凭记忆给出，未联网核实"）—— 这是很好的行为。

**这个意外本身就是最值得学的一课：**

> **不是所有问题都需要工具。** 稳定的公共常识，模型记忆就够了；
> 需要工具的是**时效性数据、私有数据、以及精确到模型不会记住的细节**。

想看它真的翻车，换个记忆不可能覆盖的问题再跑 `no_search`：

```bash
python3 agent.py no_search "上周有哪些 AI 模型发布？"
python3 agent.py no_search "某个冷门县城 2024 年的常住人口是多少？"
```

对比一下 `hosted` 跑同样的问题。那个差距才是搜索工具真正的价值所在。

## 练习答案

**1. 换个时效性问题** —— 见上。`no_search` 会开始编，或者老实说不知道；
hosted 能给出正确答案。**这才是搜索工具存在的理由。**

**2. `read` 限制到 100 字** —— 常常不够。维基百科开头往往先讲定义和历史，
具体数字可能在第二三句。截太短就拿不到，它会反复 read 或者放弃。
教训：**工具的返回长度是个真实的设计参数**，不是随便填的。

**3. 让 `search` 返回过时数据** —— 绝大多数情况**照单全收**。和实验 01 里
"让 `get_rate` 返回 999"是同一个结论：**模型默认信任工具返回值。**
数据可信度得你在工具里保证。

**4. 行数对比** —— `run_hosted()` 大约十几行且**没有循环**；`run_diy()` 是完整的
ReAct 循环。这个比例说明的正是这个实验的主题：**你省掉的代码，等于你放弃的控制权。**

**5. 加缓存** —— 同一个 query 命中缓存直接返回。真实项目里这能省很多：
agent 经常在相邻轮次里搜几乎一样的东西。顺带你会发现，**能加缓存本身就是
DIY 的一个优势** —— hosted 模式你插不进去。

## 一句话总结

| | 你写的代码 | 你能看到的 |
|---|---|---|
| hosted | 0 行 | 只有最终答案 |
| DIY | 整个循环 | 每一次搜索、每一段摘要、每一次失败 |

**选 hosted 时，你放弃的是可观测性。** 出事那天，你手上只有最后那段文字。

另外注意：`run_diy()` 和实验 01 的 `run()` **是同一个循环**。
「会联网搜索的 agent」不需要任何新机制 —— 换的只是工具。
