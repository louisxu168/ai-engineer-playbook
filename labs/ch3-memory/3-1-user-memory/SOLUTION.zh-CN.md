## 一、实测结果总览

问题：`帮我列一个成都出差期间的餐厅清单。`
后端：Claude Code（`claude -p`），2026-07-28 实测。

| 模式 | 记忆体积 | 关键事实 | 无用信息 | 过期事实 | 回答照顾到 |
|---|---|---|---|---|---|
| `no_memory` | 0 字 | 0/2 | 0 | 不适用 | 1/2 ⚠️ 误判 |
| `full_log` | 199 字 | 2/2 | **5 条** | ✗ 还留着 | 2/2 |
| `naive_extract` | **268 字** | 2/2 | **5 条** | ✗ 还留着 | 2/2 |
| `extracted` | 195 字 | 2/2 | **0 条** | ✗ 还留着 | 2/2 |

**两个结果值得单独拎出来说：**

1. **`naive_extract` 比 `full_log` 还大**（268 > 199）。
   我设计这个实验时预期它「小一点但脏」，结果它**又大又脏**。
2. **四种模式没有一个通过「过期事实」测试**——连写得最好的提取提示词也没有。
   这不是提示词的锅，是架构的锅。下面第四节展开。

## 二、四个记忆文件（全文）

这一节请对着你自己跑出来的文件看。

### `memory_full_log.json` —— 原样存

```json
[
  "我对花生过敏，吃到会直接送医院，这个千万记住。另外我完全不吃辣，一点都不行。",
  "我在北京国贸上班，做后端开发，平时中午就在公司楼下吃。",
  "今天下雨我忘带伞，淋了一路，现在有点感冒，晚上打算早点睡。",
  "上周末去了趟环球影城，人太多了，排队排到怀疑人生，我是真受不了人挤人的地方。",
  "更新一下：我下个月调岗，以后常驻上海浦东了，北京这边不去了。",
  "我下周要去成都出差三天，住在春熙路附近。"
]
```

零思考，零信息损失。问题只有一个：**这个列表只会变长。**

### `memory_naive_extract.json` —— 随便提取（10 条，268 字）

```json
[

  "用户完全不吃辣，不能接受任何辣度",

  "用户平时中午在公司楼下吃午饭",
  "用户今天（2026-07-28）下雨忘带伞被淋湿，之后有点感冒，打算晚上早点睡",   ← 垃圾
  "用户不喜欢人多拥挤的地方，讨厌排长队",
  "用户上周末（约2026年7月中下旬）去了环球影城，因人多排队体验很差",         ← 垃圾
  "用户下个月调岗，之后常驻上海浦东，不再去北京",
  "用户下周（相对 2026-07-28）要去成都出差三天，住在春熙路附近"
]
```

### `memory_extracted.json` —— 好好提取（9 条，195 字）

```json
[

]
```

## 三、逐条对比：好提示词到底好在哪

把两个提取结果并排放，差别有四处，每一处都对应 `extract_good` 里的一条标准。

### 差别 1：整场噪声会话，一个扔了一个没扔

第 3 次会话（下雨/忘带伞/感冒/早睡）：

| | 结果 |
|---|---|
| `naive_extract` | 原样记下来了：「用户今天（2026-07-28）下雨忘带伞被淋湿，之后有点感冒，打算晚上早点睡」 |
| `extracted` | **一条都没记** |

对应 `extract_good` 的第 2 条：「**明确扔掉当下状态**：今天的天气、此刻的心情、
临时的身体不适」。

> **你不说，它就不知道你不想要。** 「提取信息」这个指令本身是中性的——
> 天气也是信息，感冒也是信息。

### 差别 2：环球影城——同一段话，提取出的东西不一样

第 4 次会话里有两样东西：一个**一次性事件**（去了环球影城），
和一条藏在里面的**长期偏好**（受不了人挤人）。

| | 提取出了什么 |
|---|---|
| `naive_extract` | **两条都记**：偏好 + 事件 |
| `extracted` | **只记偏好**：「不喜欢人多拥挤的场所」 |

这是本实验里最漂亮的一处。**好的提取不是摘抄，是从具体事件里抽出可复用的结论。**
下个月这个人还会不会去环球影城，没人关心；但他讨厌排队，这条一年后还有用。

> 顺带一提：`full_log` 模式的最终回答里冒出了一句「你不喜欢排队挤人，
> 我都挑了好订位或错峰能进的」。**垃圾不只是占地方，它会被读进去、影响输出。**
> 这次影响是正面的，但你没法保证下次也是。

### 差别 3：时限

第 6 次会话「下周去成都出差三天」：

| | 写法 |
|---|---|
| `naive_extract` | 「用户下周（相对 2026-07-28）要去成都出差三天」 |
| `extracted` | 「**2026-08-03 至 2026-08-09 期间**……（**此条为临时行程，出差结束后失效**）」 |

对应第 3 条标准。「下周」这个词一个月后就是错的；日期范围永远是对的，
而且标了失效条件，读取时可以直接过滤。

### 差别 4：体积——为什么随便提取反而更大

这是最反直觉的一点：

```
full_log        199 字   6 条（= 6 次会话原文）
naive_extract   268 字   10 条  ← 比原文还多 35%
extracted       195 字   9 条
```

原因在于 `naive_extract` 的每一条都加了冗余包装：

```
原文：  我在北京国贸上班，做后端开发
naive： 用户在北京国贸上班
        用户从事后端开发工作
```

一句 13 字的话，变成了两条共 18 字。**「用户」两个字每条都重复一遍**，
拆分又放大了这个开销。

> **提取 ≠ 变小。** 提取的价值是**去掉不该留的**，不是压缩字数。
> 一个只会改写不会取舍的提取器，是纯粹的负收益：花了一次模型调用，
> 得到一份更大、同样脏的记忆。
>
> 这一条我在设计实验时也想错了——见文末。

## 四、四种模式全都没通过的那一关：事实变了

用户在第 5 次会话说：「调岗，以后常驻上海浦东，北京这边不去了。」

那么「在北京国贸上班」应该被**删掉**。实测：

| 模式 | 记忆里还有北京吗 |
|---|---|
| `full_log` | ✗ 有（第 2 条原文） |
| `naive_extract` | ✗ 有（「用户在北京国贸上班」） |
| `extracted` | ✗ 有（「在北京国贸上班」） |

**连写得最好的提取提示词也没做到。** 为什么？

看 `update_memory()` 里真正发出去的那一行：

```python
raw_text = complete(t("extract_input") + session_text, extract_prompt, backend=backend)
```

`session_text` 是**这一次会话的原文**，仅此而已。
处理第 5 次会话的时候，模型**根本看不到**第 2 次会话存下的那条记忆。

> **它不是没删——它是不知道有东西要删。**

值得注意的是 `extracted` 做了它能做的最好的处理：它同时写下了

```
"常驻工作地为上海浦东（2026年8月起调岗生效）",
"不再在北京工作"
```

也就是说，**矛盾是可解的**——一个读到这三条的模型能推理出正确结论。
但这是运气，不是设计：记忆里同时存着 A 和 not-A，靠下游模型去调和。
记忆条数一多，这种自相矛盾会越积越多。

### 正确的架构

记忆更新不该是 append，该是**读-改-写**：

```
读出已有记忆  →  连同新会话一起发给模型  →  模型输出 add / update / delete
```

这正是 mem0、Memobase 这类记忆框架的核心逻辑。练习 3 会让你实现一遍。

**代价**：每次更新都要把已有记忆发进去，token 花费随记忆量增长。
所以真实系统还会加一层：只把**可能相关**的记忆取出来参与更新——
那又是一个检索问题。

> 这就是记忆系统的真面目：**写是检索问题，读也是检索问题。**

## 五、`no_memory` 那个「1/2」是误判

程序判定 `no_memory` 的回答「✓ 照顾到了：不吃辣」。看原文：

> 3. **吃辣吗？** 出差期间连着吃火锅串串，肠胃扛不扛得住是个现实问题。
>    我一般会建议**辣的和不辣的**按 2:1 搭配。

「不辣」两个字确实出现了，但模型是在**反问用户吃不吃辣**，
顺带提了一句通用建议。这跟「知道你不吃辣所以避开了」完全是两回事。

**关键词判分就是会这样。** 本仓库里所有自动判据都有这个毛病，只是程度不同：

| 实验 | 判据 | 可靠性 |
|---|---|---|
| 2-2 注入 | 特定标记出现与否 | **高**——标记是我们设计的，不会自然出现 |
| 2-3 脱敏 | 正则匹配敏感格式 | **中**——只认识规则表里的格式 |
| 3-1 记忆 | 关键词出现与否 | **低**——「不辣」可以有很多种出现方式 |

> 教学实验里这没关系，因为**你还会亲眼看完整输出**。
> 但如果你要拿这套做真实评测：**别用关键词，用模型判分（LLM-as-judge），
> 而且要人工抽检判分器本身。**

原书的 `user-memory-evaluation` 项目专门讲这件事，值得一读。

顺带说：`no_memory` 这次的表现其实**很好**——它没有瞎编，
而是老老实实反问了四个问题。这是模型的正确行为。
代价只是：**用户得把已经说过的话再说一遍。**

## 六、练习答案

### 练习 1 ⭐ 给剧本加一次会话

加「我最近在减脂，晚上不吃主食」之后：

- `full_log`：原样多一条
- `naive_extract`：大概率拆成两条（「在减脂」+「晚上不吃主食」）
- `extracted`：一条，且可能标注「减脂是阶段性目标，可能变化」

**观察重点不是它记没记，而是它有没有意识到「减脂」是会变的。**
第 3 条标准（有时限的要写清时限）在这里适不适用？——这是个好问题，
因为「减脂」没有明确结束日期。真实系统会给这类记忆加**置信度衰减**。

### 练习 2 ⭐⭐ 改坏 `extract_good`

删掉第 2 条之后重跑，无用信息会从 0 变成 2~5 条不等（有随机性），
体积也会涨。

**结论：那五行提示词里，第 2 条一个人干了大部分的活。**

这和实验 2-1 的发现完全一致：压缩/提取提示词里，**「不要什么」比「要什么」
更值钱**——因为「要什么」模型能猜个八九不离十，「不要什么」它猜不到。

### 练习 3 ⭐⭐⭐ 让记忆能「改」

参考实现（改 `update_memory()` 的提取分支）：

```python
existing = load_memory(mode)
prompt = (
    "这是你已经记住的关于用户的事：\n"
    + json.dumps(existing, ensure_ascii=False, indent=2)
    + "\n\n这是最新一次会话：\n" + session_text
    + "\n\n请输出【更新后的完整记忆列表】。规则：\n"
      "1. 新会话推翻了旧记忆的，删掉旧的\n"
      "2. 新会话补充了细节的，改写那一条，不要新增\n"
      "3. 没被提到的旧记忆原样保留\n"
)
raw_text = complete(prompt, t("extract_good"), backend=backend)
memories = parse_json_reply(raw_text).get("memories", [])
save_memory(mode, memories)          # 注意：是覆盖，不是 extend
```

关键差别只有两处，但都是结构性的：

1. **提取时看得到已有记忆**（`existing` 进了提示词）
2. **保存时是覆盖不是追加**（`save_memory` 而不是 `memories.extend`）

跑一遍，北京那条通常会被清掉。

**但请注意它引入的新风险**：现在每次更新，模型都有机会**误删**一条正确的记忆。
`full_log` 永远不会丢信息，这个方案会。

> **这就是记忆系统的核心权衡：**
> 追加只会脏，不会错；改写会变干净，但可能出错。
>
> 生产系统的常见折中：**软删除**——标记为失效但不真删，
> 读取时过滤掉。既保住了正确性，又能回滚。

### 练习 4 ⭐⭐⭐ 记忆多了之后怎么办

500 条记忆全塞进上下文，会撞上第 2 章的墙。但**这里不该用压缩**。

分界线是这句：**你能不能提前知道这次用得上哪几条。**

| | 压缩（2-1） | 检索（3-2） |
|---|---|---|
| 适用 | 信息都相关，只是太长 | 信息大部分不相关 |
| 做法 | 把全部内容变短 | 只取出相关的几条 |
| 代价 | 一定有信息损失 | 可能没取到该取的 |

用户问「成都吃什么」，500 条记忆里真正有用的可能就 3 条（过敏、忌辣、行程）。
**把 500 条压缩成摘要，等于把那 3 条也稀释了。** 正确做法是检索出那 3 条。

> 所以记忆系统天然是个检索系统。这是下一个实验的主题。

### 练习 5 ⭐⭐ 给记忆加时效

「谁判断过期」——**两边都要，但职责不同**：

| | 写的时候 | 读的时候 |
|---|---|---|
| 做什么 | 记录 `expires` 字段（一个日期） | 拿当前时间和 `expires` 比 |
| 为什么在这边 | 只有写的时候才知道语境（「下周」是相对哪天说的） | 只有读的时候才知道「现在」是什么时候 |

参考结构：

```json
{"text": "赴成都出差三天，住春熙路附近", "expires": "2026-08-09"}
```

**写的时候必须把相对时间变成绝对时间**，否则读的时候没法判断——
这正是 `extract_good` 第 3 条在做的事。

⚠️ 一个常见的坑：`expires` 到期后**不要真删**。用户可能会问
「我上次去成都住哪儿来着」。正确做法是移出「活跃记忆」，
但保留在可检索的历史里。

> **过期 ≠ 无用。过期只是「默认不再主动带进上下文」。**

## 七、一个我自己设计错了的地方

值得写下来，因为这正是这个仓库想教的东西。

设计这个实验时，我预期的对比是：

> `naive_extract`：**小但脏**（记住了垃圾）
> `extracted`：**小且干净**

实际测出来是：

> `naive_extract`：**又大又脏**（268 字，比原文还多 35%）

我漏掉的是：一个没有取舍标准的提取器，会**逐句改写并拆分**，
而改写和拆分都会增加字数。它做的不是「提取」，是「换个说法重写一遍」。

**这比我原本设计的结论更有价值**：

> 中间加一层模型调用，**不等于**结果一定更小、更好。
> 你得说清楚这一层要优化什么，否则它只会把输入换个样子传下去。

这个规律在 agent 工程里到处都是——加一层 planner、加一层 reranker、
加一层 summarizer，如果目标不明确，加的都是延迟和 token，不是效果。

**建立「先猜 → 再测 → 承认猜错」的习惯，比记住任何单条结论都重要。**
