## 一、实测结果总览

问题：`帮我列一个成都出差期间的餐厅清单。`
记忆库：36 条 · `TOP_K = 5`
后端：Claude Code（`claude -p`），2026-07-28 实测。

| 模式 | 取回条数 | **召回率** | 模型调用 | 回答照顾到 |
|---|---|---|---|---|
| `stuff_all` | 36 | **3/3** | 1 | 2/2 |
| `keyword` | 3 | **1/3** | 1 | **0/2** ☠ |
| `expanded` | 9 | **3/3** | 2 | 2/2 |
| `agentic` | 14 | **3/3** | 3 | 2/2 |

**两件事值得单独拎出来：**

1. `keyword` 的回答是 **0/2** —— 不是差一点，是**两条都没照顾到**。
   一个可能把用户送进医院的建议，看起来却非常专业。
2. `agentic` 比 `expanded` **多花 50% 的调用、多取回 55% 的条目，
   换来的召回率完全一样**。这是本实验最反直觉的一条。

> ★ 前两行的召回率（3/3 和 1/3）**不需要模型**就能算出来。
> 你跑十遍都是这个数。第 5 节会讲为什么这件事很重要。

## 二、`keyword` 的失败：一份看起来很专业的危险建议

这是本实验最该看的一段。BM25 取回了这三条：

```
┌─ 取到的 3 条记忆（模型只能看到这些）───────
│ ★ 2026-08-03 至 2026-08-09 期间赴成都出差三天，住在春熙路附近
│   公司报销标准：出差住宿每晚不超过 600 元
│   去年十月去过一次杭州出差，住在西湖边上，觉得性价比一般
└────────────────────────────────────────────
```

**这三条挑不出毛病。** 行程、预算、出差偏好——全都和「成都出差吃饭」相关。
如果你是在 review 一个检索系统的日志，看到这三条，你会觉得它工作正常。

然后看它基于这三条给出的回答（节选）：

> 【步行 5–10 分钟，最省事】
> 1. 马旺子·川小馆——改良川菜，酸菜黑鱼、豆汤饭很稳……
> 2. **陈麻婆豆腐**（春熙路/骡马市）——老字号，**麻婆豆腐+甜水面**……
> 5. **钟水饺、赖汤圆**（春熙路一带）——纯属顺路解决一顿。
>
> 【地铁 2–4 站，值得专门去一次】
> 7. **玉林串串香**——晚上和同事放松吃串串，人均 60–80。
> 8. **小龙翻大江 / 蜀大侠**——正经火锅局，请客不出错。
> 10. **老麻抄手**——微麻起步，别直接点特麻。
>
> 【几个实用提醒】
> - 8 月成都很热且潮，**中午别硬吃重辣火锅**，容易下午没状态；**火锅/串串放晚上**。
> - 记得上次杭州出差你觉得西湖边性价比一般——成都反过来……

数一数问题：

| 推荐 | 问题 |
|---|---|
| 麻婆豆腐、甜水面、串串、火锅、老麻抄手 | 全是辣的，用户**完全不吃辣** |
| 钟水饺、赖汤圆、钵钵鸡 | 川式红油/甜品常含花生，用户**花生过敏会送医院** |
| 「火锅/串串放晚上」 | 在**帮他规划**怎么吃辣 |

同时注意最后一条提醒：「记得上次杭州出差你觉得西湖边性价比一般」——
**它非常好地用上了检索到的东西。** 模型没有任何问题。

> **模型用好了给它的每一条，问题在于给它的那几条里，少了会要命的两条。**
>
> 这就是为什么「检索质量」不能只看「取回来的东西相不相关」。
> **相关性衡量的是取回来的，召回率衡量的是没取回来的。**
> 出事的永远是后者。

## 三、为什么会漏：不是排名问题，是候选问题

自己跑一下：

```bash
python3 -c "import agent; print(agent.tokenize('对花生过敏，误食会送医院'))"
```
```
['对花', '花生', '生过', '过敏', '误食', '食会', '会送', '送医', '医院']
```

```bash
python3 -c "import agent; print(agent.tokenize('帮我列一个成都出差期间的餐厅清单'))"
```
```
['帮我', '我列', '列一', '一个', '个成', '成都', '都出', '出差', '差期',
 '期间', '间的', '的餐', '餐厅', '厅清', '清单']
```

**交集为空。**

看 `bm25_scores()` 里这两行：

```python
tf = tokens.count(w)
if tf == 0:
    continue          # ← 这条记忆对这个查询，一分都拿不到
```

分数是 **0**。而 `search()` 里：

```python
if scores[i] <= 0:
    break             # ← 0 分的直接不要
```

**它连候选名单都没进。**

所以——把 `TOP_K` 从 5 改成 20、改成 36，召回率还是 1/3。
`keyword` 模式实际只取回了 3 条，因为**整个库里只有 3 条跟这个查询有字面重合**。

> **这不是调参问题，是这条技术路线的边界。**
> 词表不重合，BM25 就无从下手。改 k1、改 b、改 TOP_K，一个都救不了。

这就是 embedding 被发明出来的原因：让「花生过敏」和「餐厅推荐」在向量空间里
挨得近，靠的不是共同的字，是共同的**意思**。

## 四、`expanded`：语义鸿沟是模型补的

模型想出来的 6 个查询（实测）：

```
• 饮食偏好 忌口 过敏 不吃什么
• 辣度接受程度 川菜 口味偏好
• 出差 用餐场景 商务宴请 请客 人数
• 预算 人均消费 餐厅档次偏好
• 成都 之前去过的餐厅 评价 城市经历
• 饮酒 咖啡 茶 饮品习惯 素食 宗教饮食
```

**第一个查询里就有「过敏」和「忌口」。** 这两个词用户没说过，问题里也没有——
是模型凭常识补上的：**它知道推荐餐厅必须考虑过敏。**

取回 9 条，3 条目标全中：

```
│ ★ 对花生过敏，误食会送医院（严重过敏）
│   对青霉素过敏                      ← 「过敏」这个查询的副作用
│ ★ 完全不吃辣，一点辣都不能接受
│   买东西偏好用支付宝
│   坐飞机偏好靠过道的座位
│   公司报销标准：出差住宿每晚不超过 600 元
│   去年十月去过一次杭州出差……
│ ★ 2026-08-03 至 2026-08-09 期间赴成都出差三天……
│   早饭习惯喝黑咖啡，不加糖不加奶
```

注意「对青霉素过敏」也被带出来了——这是**精确率**的代价：
查询扩展提高召回，必然也会引入无关项。

> **这个交换划算吗？** 在这里非常划算：
> 多几条无关记忆进上下文，代价是几十个 token；
> 漏掉花生过敏，代价是把人送进医院。
>
> **召回和精确不对等的时候，永远优先保召回。**

### 这一步的本质

```
           关键词检索             向量检索             查询扩展（本实验）
匹配的是    字面                  意思                 字面
跨鸿沟靠    ——                    embedding 模型       LLM 的世界知识
额外成本    无                    跑模型 + 存向量      一次模型调用
基础设施    无                    向量库               无
```

三者不是替代关系。**真实系统通常是「向量 + 关键词」混合，
再加查询扩展。** 因为它们的失败模式不一样：向量检索会漏掉精确匹配
（比如订单号、错误码），关键词检索会漏掉同义表达。

## 五、`agentic` 打平了，但贵 50% —— 这是好事还是坏事？

实测：

| | 召回率 | 模型调用 | 取回条数 |
|---|---|---|---|
| `expanded` | 3/3 | 2 | 9 |
| `agentic` | 3/3 | **3** | **14** |

agentic 第 1 轮就想出了跟 expanded 几乎一样的查询，第 2 轮直接说「够了」：

> **[思考]** 已覆盖过敏、忌口、辣度、预算、场所偏好等核心维度，
> 成都行程和住址也已拿到，足够列餐厅清单了。

**它的判断完全正确。** 问题是：这个正确的判断花了一次额外的模型调用，
而结论是「我上一轮已经做完了」。

> **循环的价值，等于「看到中间结果」带来的信息增量。**
> 这里增量是 0，所以循环买到的只有延迟和 token。

那什么时候循环值钱？**当第二次该搜什么，取决于第一次搜到了什么。** 例如：

```
用户：帮我给爸妈订个礼物
  第 1 轮：搜「父母 家人」→ 找到「父母住在南京，每两个月回去一次」
  第 2 轮：现在才知道要搜「南京」相关的——第一轮根本想不到这个词
```

这叫**多跳检索**（multi-hop）。练习 5 就是让你造一个这样的场景。

> **一条选型经验：**
> 能一次问清楚的，别上循环。
> 循环是为了处理「你事先不知道自己要问什么」，不是为了显得聪明。

这和实验 1-2 的结论是一致的：agentic 不是更高级，是**用成本换不确定性下的鲁棒性**。
不确定性小的时候，你付了成本，什么也没换到。

## 六、为什么这个实验的判据比别的实验硬

召回率是本仓库里**唯一一个不需要模型、不靠关键词匹配**的判据：

```python
recall_hits = [i for i in TARGET_INDEXES if i in found]
```

纯粹的集合运算。`TARGET_INDEXES` 是我们写死的标准答案，取到没取到没有解释空间。

对比一下本仓库其他判据：

| 实验 | 判据 | 会误判吗 |
|---|---|---|
| 2-2 注入 | 特定标记出现与否 | 几乎不会（标记是造的） |
| 2-3 脱敏 | 正则匹配敏感格式 | 会（只认识规则表里的格式） |
| 3-1 记忆 | 关键词出现与否 | **会**（实测出现过误判） |
| **3-2 检索** | **集合包含** | **不会** |

所以 `stuff_all` 和 `keyword` 两行的召回率是**完全确定的**——
你换模型、换时间、跑一百遍，都是 3/3 和 1/3。

> **做评测的时候，能设计成不依赖模型的指标，就不要依赖模型。**
> 检索这一层恰好可以（有标准答案），所以业界评 RAG 都是先看 recall@k，
> 而不是直接看最终答案好不好。
>
> 因为最终答案好不好，混淆了检索和生成两件事。

## 七、练习答案

### 练习 1 ⭐ 换个问题

`周末想约朋友出去玩，有什么建议？` 该取到的是「不喜欢人多拥挤的场所」
和「周末常去骑车，一次骑 40 公里左右」。

- 「周末常去骑车」含**周末**，和问题共享关键词 → **能搜到**
- 「不喜欢人多拥挤的场所」和问题一个字不重合 → **搜不到**

**规律出来了**：能不能搜到，取决于**记忆是不是恰好用了问题里的词**——
这是运气，不是能力。

> 换句话说：**关键词检索的召回率，是数据分布的函数，不是算法质量的函数。**

### 练习 2 ⭐⭐ TOP_K 调到 36

`keyword` 仍然**不等于** `stuff_all`。因为 0 分的记忆被 `search()` 直接 break 掉了，
不管 TOP_K 多大都进不来。实测还是 3 条、1/3。

如果你把那个 `if scores[i] <= 0: break` 也去掉，那才等于 `stuff_all`——
**这时候检索就没有意义了**：它没有筛掉任何东西，只是把顺序换了换。

> **检索的价值 = 它筛掉了什么。** 一个不筛东西的检索器，是个排序器。

### 练习 3 ⭐⭐ 给记忆加别名

把那条改成 `对花生过敏，误食会送医院（饮食 忌口 餐厅 吃饭）` 之后，
「餐厅」这个词就出现了，和问题共享关键词 → **召回率变成 2/3**（加了别名的那条能搜到了）。

**哪个成本更低？** 文档扩展更低，而且优势会随查询量放大：

| | 做几次 | 什么时候做 |
|---|---|---|
| 文档扩展 | 每条记忆**一次** | 写入时（离线，不影响延迟） |
| 查询扩展 | 每次查询**一次** | 查询时（在线，直接加延迟） |

一条记忆写一次、被查一千次的话，文档扩展只花 1 次模型调用，
查询扩展要花 1000 次。

⚠️ 但文档扩展有个硬伤：**你得在写入时就猜到以后会被怎么查。**
猜不全就还是漏。所以生产系统两个都做。

### 练习 4 ⭐⭐⭐ 混合检索

取并集之后召回率仍是 3/3（`expanded` 已经全中了），但取回条数会涨到 10 条左右。

**真实系统为什么几乎总是混合的？** 因为两种检索的**失败模式互补**：

| | 擅长 | 会漏 |
|---|---|---|
| 关键词 / BM25 | 精确串：订单号 `SO-20260803`、错误码 `PAYMENT_TIMEOUT`、人名 | 同义表达 |
| 向量 / 语义 | 同义、换个说法、跨语言 | **精确串**（向量会把 `SO-20260803` 和 `SO-20260804` 认成一个东西） |

用户搜订单号，向量检索会给你一堆长得像的订单号——这在生产环境是灾难。
所以标准做法是两路召回 + 融合排序（RRF 之类）。

> **不是「哪个更好」，是「它们漏的东西不一样」。** 这和实验 1-2 的结论同构。

### 练习 5 ⭐⭐⭐ 造一个 agentic 真正赢的场景

参考问题：

```bash
python3 agent.py agentic "帮我给爸妈订个周末去玩的地方，顺便订个餐厅"
python3 agent.py expanded "帮我给爸妈订个周末去玩的地方，顺便订个餐厅"
```

为什么 agentic 会赢：`expanded` 第一次只能想到「父母 家人 礼物 周末」这类词；
它**不可能**想到搜「南京」——因为在搜到「父母住在南京」之前，
没有任何理由去搜南京。

agentic 可以：

```
第 1 轮：搜「父母 家人」 → 取到「父母住在南京，每两个月回去一次」
第 2 轮：噢，在南京 → 搜「南京」相关
```

**这就是多跳。** 判断标准很简单：

> **画一张依赖图。如果查询 B 依赖查询 A 的结果，就需要循环；
> 如果所有查询互相独立，一次性发出去就行。**

顺带一提，这也是为什么实验 1-2 里「并行工具调用」和「循环」是两回事：
并行解决的是独立查询，循环解决的是依赖查询。

## 八、把两个实验连起来

3-1 和 3-2 合起来是一句话：

> **记忆系统 = 写的时候决定「留什么」+ 读的时候决定「取什么」。**
> **两头都是筛选问题，两头都会漏，而且漏的方式完全不同。**

| | 3-1 写 | 3-2 读 |
|---|---|---|
| 漏的方式 | 该记的没记（提取标准没写清） | 该取的没取（字面不重合） |
| 后果 | 信息**永久丢失** | 信息还在，这次没用上 |
| 修法 | 改提取提示词 | 查询扩展 / 向量 / 无条件注入 |
| 严重性 | **更严重**——丢了就没了 | 较轻——下次可能就取到了 |

所以真实系统的取舍是：**写的时候宁可多存，读的时候努力筛。**
存储便宜，丢失不可逆。

而对于**要命的信息**（过敏、禁忌、合规约束），正确做法既不是靠提取、
也不是靠检索，而是：

> **单独存成一个「永远带上」的清单，无条件拼进每一次上下文。**

不要把人命交给召回率。
