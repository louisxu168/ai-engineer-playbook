# 实验 2-3：日志脱敏 —— 什么不该进上下文

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. 上下文的第三种风险：不是装不下（2-1），不是被投毒（2-2），是**装了不该装的东西**
> 2. 「全部脱敏」为什么会**把任务本身弄没**——安全和可用是有张力的
> 3. **可逆令牌化**：怎么做到零泄露 + 任务照做，这是真实系统的解法
> 4. 为什么这里说「正则有效」，2-2 却说「正则没用」——**差别在威胁模型**
>
> **怎么学**：程序会自动数出「几条真实敏感信息进入了上下文」，也会自动判定
> 「任务有没有做成」。两个都是客观可测的，所以你能一眼看到取舍。
>
> **需要多久**：15 分钟（不联网，跑得快）。
>
> ⚠️ 日志里的敏感信息**全是编造的**：邮箱用 `example.com`（RFC 保留域名），
> 电话用 555 号段（影视专用），API key 明确写了 `FAKE`。

---

## 先搞清楚问题是什么

你是运维，线上出了问题，你顺手把日志丢给 agent 分析。日志长这样：

```
2026-07-28 09:12:03 INFO  user=zhang.wei@example.com action=login ip=10.0.3.44 ok
2026-07-28 09:12:41 ERROR user=zhang.wei@example.com action=checkout code=PAYMENT_TIMEOUT
2026-07-28 09:15:33 DEBUG outbound call apikey=sk-FAKE-9f2b1c4d8e7a6350 endpoint=/pay
2026-07-28 09:23:09 DEBUG card=4111-1111-1111-1111 masked_ok=false
```

**这一步你已经做完了一件不可撤销的事：** 用户邮箱、内网 IP、API key、
银行卡号，全都发出去了。发给了模型厂商，可能被记录、被留存、被人看到。

> 实验 1-1 的那句话在这里变成了一个安全问题：
> **工具返回什么，就原样进上下文。** 你没筛，就等于全发。

直觉答案是「脱敏就好了」。但下面你会发现，脱敏这件事有个真实的两难。

cd labs/ch2-context-engineering/2-3-log-redaction

### 👀 你会看到

  │ 2026-07-28 09:12:03 INFO  user=zhang.wei@example.com action=login ip=10.0.3.44 ok

### 💡 学到什么

**任务做成了，代价是全泄露。** 这是绝大多数人第一次接日志分析 agent 的
真实状态——不是因为不在乎，是因为**根本没意识到这一步发生了什么**。

> 顺带留意模型的回答：它自己主动指出了日志里有明文 API key 和未脱敏卡号。
> **模型看得见这些，说明它们确实进了上下文。**

## 第 1 步：先猜，再跑「全部脱敏」（5 分钟）

### 🤔 先猜（这题是本实验的关键）

`redacted` 模式把所有敏感信息统一替换成 `[已脱敏]`。猜一下：

- 泄露还剩几条？ ___
- **任务还做得成吗？** ___

第二个问题请认真想 10 秒再往下。

### 🔧 做什么

```bash
python3 agent.py redacted "（复制同一个任务）"
```

（跑完 `raw` 后屏幕上会直接打出这行命令，复制即可。）

### 👀 观察什么

盯住最后那两行判定，**两行要一起看**：泄露多少、任务成没成。

### 💡 学到什么

打开 `agent.py` 看 `redact_all()`，就三行：

```python
for pattern, _prefix, _desc in REDACTION_RULES:
    result = re.sub(pattern, placeholder, result)
```

问题不在代码，在**信息论层面**：三个不同用户全都变成了 `[已脱敏]`，
「哪个用户错误最多」这个问题在这批数据上**已经没有答案了**。

> **脱敏不是越狠越好。狠到一定程度，任务就不存在了。**

这是安全工程里最常被忽略的一面：一个「绝对安全」的方案，如果让业务做不成，
它在现实中就会被绕过——工程师会私下切回 `raw`。

## 第 2 步：两头兼顾的那条路（5 分钟）

```bash
python3 agent.py tokenized "（同一个任务）"
```

### 👀 观察什么

三个地方：

1. 模型看到的日志变成了什么样
2. **令牌映射表**——注意它是单独打印的，标着「不发给模型」
3. 最后两行判定

### 💡 学到什么

看 `tokenize()` 的核心思想：

```python
counters[prefix] = counters.get(prefix, 0) + 1
token = prefix + "_" + str(counters[prefix])
mapping[token] = match
result = re.sub(re.escape(match), token, result)
```

**关键在「稳定」两个字**：同一个真实值，永远映射到同一个占位符。

| | 真实身份 | 同一性 |
|---|---|---|
| `raw` | 保留 ✗ | 保留 ✓ |
| `redacted` | 丢弃 ✓ | **丢弃 ✗ ← 任务死在这** |
| `tokenized` | 丢弃 ✓ | **保留 ✓** |

模型能数出「USER_1 出现了 5 次错误」，却不知道 USER_1 是谁。
**推理需要的是同一性，不是身份。** 这两样可以分开，这就是全部诀窍。

而映射表留在你本地——需要的时候你自己换回去（发工单、通知用户），
但这一步发生在**你的进程里**，不在上下文里。

> 这叫**可逆令牌化**（tokenization）。日志脱敏、数据库脱敏、隐私计算、
> 支付行业的卡号处理，用的都是同一招。

## ⚠️ 等一下：这不是和 2-2 矛盾了吗？

2-2 里我说「关键词过滤不是防御」。这里我说「正则脱敏是有效的」。

**这两句都对，因为威胁模型不一样。**

| | 实验 2-2 注入防护 | 实验 2-3 日志脱敏 |
|---|---|---|
| 对手 | 有，且会**适应你的规则** | 没有。日志格式是你自己定的 |
| 你要匹配的 | 「所有能表达命令的自然语言」——**无穷** | 「邮箱 / 卡号 / key 的格式」——**有限且已知** |
| 漏一个的后果 | 整条防线失效 | 漏一条，其余的还是拦住了 |

> **正则适合匹配「格式固定的东西」，不适合匹配「意图」。**
>
> 邮箱有格式，恶意有一万种写法。

这一条想清楚了，比记住任何一个具体技巧都值钱。

⚠️ 但也别过度乐观：**没有对手 ≠ 没有漏网**。日志里新增一个字段
（`ssn=`、`token=`），你的规则不认识它，它就一路进上下文。
真实系统的做法是**白名单**——只放行你明确认识的字段，其余一律拦下。
练习 4 会让你把这件事做一遍。

## 第 4 步：自己动手改（练习）

### 练习 1 ⭐ 加一类新的敏感信息

往 `RAW_LOGS` 里加一行带身份证号的日志，然后往 `REDACTION_RULES` 里加规则。

**先猜**：不加规则直接跑 `tokenized`，程序会说泄露了几条？

### 练习 2 ⭐⭐ 把电话规则写松一点，再挪到前面

现在的电话规则是 `r"\+?\d{1,3}-\d{3}-\d{4}"`。把它换成大多数人会随手写的那种：

```python
(r"\d{3}-\d{4}", "PHONE", "电话号码"),   # 并把这条移到 CARD 那条的前面
```

跑 `tokenized`，**盯住 card 那一行**。

**先猜**：
- 卡号会变成什么？
- 程序最后会报泄露几条？

> 这是写脱敏规则最常见的两个坑合在一起：正则太松 + 顺序不对。
> **先匹配长的、具体的，再匹配短的、宽泛的。**

### 练习 3 ⭐⭐ 让占位符不稳定

改 `tokenize()`，让每次出现都分配一个新编号（`USER_1`、`USER_2`… 即使是同一个人）。

**先猜**：泄露会变多吗？任务还做得成吗？

> 这道题做完，你就真正理解「稳定」这两个字为什么是核心了。

### 练习 4 ⭐⭐⭐ 从黑名单改成白名单

现在的做法是「列出敏感的东西，删掉」。反过来写：**只保留你认识的字段**
（`action`、`code`、时间戳、脱敏后的 user），其余整段丢弃。

**先猜**：哪种在「日志里突然多了一个新字段」时更安全？

> 这是真实系统的做法。黑名单要你穷举风险，白名单要你穷举需要——
> **后者是有限的。**

### 练习 5 ⭐⭐⭐ 让 agent 自己申请解码

加一个工具 `reveal(token)`，让 agent 在**确实需要**真实值时申请，
你的代码打印一条审计日志再决定给不给。

**先想清楚**：这算解决了问题，还是把问题挪了个地方？

## 附：概念速查

### 三条路的取舍

| 做法 | 泄露 | 任务 | 什么时候用 |
|---|---|---|---|
| `raw` 不处理 | ✗ 全泄露 | ✓ 能做 | 数据本来就不敏感（公开文档、开源代码） |
| `redacted` 全脱 | ✓ 零泄露 | ✗ 做不成 | 任务不需要区分实体（「今天有几条 ERROR」） |
| `tokenized` 令牌化 | ✓ 零泄露 | ✓ 能做 | **默认选它** |

### 一条工程原则

> **脱敏要脱掉的是「身份」，不是「同一性」。**
>
> 推理靠的是「这两条是同一个人」，不是「这个人叫什么」。

### 什么东西最容易顺手进上下文

按真实事故频率排：

1. **日志**——最常见，因为「先丢进去看看」成本太低了
2. **数据库查询结果**——`SELECT *` 会把你忘了的列一起带出来
3. **报错堆栈**——里面常有连接串、token、请求体
4. **客服工单 / 邮件正文**——用户自己写的身份证号、卡号
5. **配置文件**——让 agent「看一下 .env 为什么没生效」

共同点：**都是你为了别的目的顺手拿来的数据，而不是你精心准备的输入。**
