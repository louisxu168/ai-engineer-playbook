# 实验 2-1：上下文压缩

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. 上下文撑爆窗口时，业界只有三条路：**不管 / 裁剪 / 压缩**

## 先想清楚问题是什么

实验 1-1 里你已经看到：**上下文就是一段你自己拼出来的字符串，每轮都在变长。**

那问题来了：**变长到装不下怎么办？**

真实 agent 跑长任务必然撞上这堵墙。业界只有三条路：

| 做法 | 怎么做 | 代价 |
|---|---|---|
| **不管** | 每轮把全部历史发过去 | 迟早爆窗口；越到后面越贵越慢 |
| **裁剪** | 只留最近 N 步，旧的扔掉 | 便宜，但**丢掉的找不回来** |
| **压缩** | 让模型把旧历史总结成摘要 | 要**多花一次模型调用**，信息还在 |

这个实验让你把三条路各跑一遍，亲眼看差别。

> **关键设计**：例子任务都特意做成「**最后一步要用到第一步的数据**」。
> 这样裁剪才会真的丢东西，你才看得见代价。

## 第 1 步：先猜，再跑压缩（10 分钟）

### 🤔 先猜

`compact` 模式会在历史超过阈值时，把旧的那几步交给模型总结成一段摘要，
再把摘要拼回上下文。猜一下：

- 提示词峰值会降到多少？ ___
- 摘要里会保住那些高度数字吗？ ___
- 总共要多花几次模型调用？ ___

### 🔧 做什么

```bash
python3 agent.py compact "（复制第 0 步用的同一个任务）"
```

### 👀 观察什么

**两处**：

1. **条子会不会缩回去**。留意这样的输出：
   ```
   提示词 7546 字符  █████████████████████████ +3712
   ⟳ 压缩完成：7406 字符 → 1392 字符（省了 81%）
   提示词 2412 字符  ████████ -5134        ← 掉下来了
   ```

2. **它压出来的摘要长什么样**（会完整打印在框里）。特别看：
   - 数字保住了吗？
   - 有没有写「还没做的事」？

### 💡 学到什么

打开 `agent.py`，找到 `compact_prompt`。**压缩的全部秘密就是那四条要求：**

```
1. 所有具体数字、名称、单位一个都不能丢 —— 这是它后面要用的
2. 已经做完的事写成结论，不要复述过程
3. 明确写出「还没做的事」
4. 不要加任何原文里没有的信息
```

代码只有十几行，**真正干活的是这段文字**。这和实验 1-1 的结论完全一致。

## 第 2 步：跑裁剪，看它付什么代价（10 分钟）

### 🤔 先猜

`truncate` 只留最近 1 步，更早的直接扔掉。猜一下：

- 提示词峰值会是三种里最低的吗？ ___
- 丢掉的数据它会**重查**，还是**凭印象编**？ ___

### 🔧 做什么

```bash
python3 agent.py truncate "（同一个任务）"
```

### 👀 观察什么

**盯着它的 `[思考]`。** 到某一轮它会意识到数据没了 —— 看它怎么说、怎么做。

同时数一下**工具调用总数**，和 `full` 比。

### 💡 学到什么

上下文确实最小。但**工具调用次数会明显变多** —— 它得把丢掉的重查一遍。

> **裁剪不是免费的。** 省下的是单轮上下文，付出的是「重做已经做完的事」。

它有没有编数字？没有 —— 因为系统提示词里有「**数据不在上下文里就重新查，
不要凭印象写**」。**把这句删掉再跑一次**（练习 3），你会看到真正危险的失败。

## 第 3 步：压过头会怎样（5 分钟）

```bash
python3 agent.py compact_tiny "（同一个任务）"
```

摘要被限制成**一句话**。

### 💡 学到什么

压缩率能到 90% 以上，但**精度开始丢**（比如 `599.1` 变成 `599`）。

数字再多几个，一句话就装不下了 —— **那时压缩就退化成了裁剪，
而且还比裁剪更慢**（因为白白多花了一次模型调用）。

> **压缩比例是个旋钮，不是越高越好。**

## 第 5 步：自己动手改（练习）

**每题先猜，再跑。**

### 练习 1 ⭐ 调 `KEEP_RECENT`

文件开头，默认 1。改成 5 再跑 `truncate`。

**猜一猜**：上下文和工具调用数会怎么变？

> 想清楚一件事：`KEEP_RECENT = ∞` 就是 `full`，`= 0` 就是最激进的裁剪。
> **它是个连续旋钮，没有最优值。**

### 练习 2 ⭐⭐⭐ 削弱压缩提示词

把 `compact_prompt` 里第 1 条（「数字一个都不能丢」）删掉，再跑 `compact`。

**猜一猜**：摘要会变好读还是变差？任务还做得完吗？

> **这题是本实验最值得做的。**

### 练习 3 ⭐⭐⭐ 删掉「不要猜数字」

把 `sys_no_guessing` 从系统提示词里去掉，再跑 `truncate`。

**猜一猜**：数据丢了之后，它会重查还是直接报一个记忆里的数？

> 想一想：如果它编的数**恰好是对的**，你怎么可能发现？
> **这是最危险的失败模式。**

### 练习 4 ⭐ 算成本

`truncate` 比 `full` 多调了几次工具？乘以你的 API 单价 —— 那就是裁剪的真实成本。

### 练习 5 ⭐⭐ 把任务加长一倍

改成查 10 座建筑。

**猜一猜**：`full` 的曲线会是什么形状？`compact` 呢？

## 附：概念速查

### 三条路的取舍

| | 上下文大小 | 额外成本 | 信息保留 |
|---|---|---|---|
| `full` | 一路涨，迟早爆 | 无 | 全部 |
| `truncate` | 最小 | **重做已完成的工作** | 丢掉的找不回来 |
| `compact` | 锯齿形，有界 | **每次压缩多一次模型调用** | 取决于压缩提示词 |

**没有免费的午餐，你只能选择在哪里付钱。**

### 真实系统是怎么做的

生产环境的 agent（包括 Claude Code 自己）通常是**混合**的：

- 按 **token 数**触发（比如到 15 万 token），而不是按步数
- 保留最近 N 轮**原文**，更早的压成摘要 —— 就是本实验 `compact` 的做法
- 有些还会**分层**：工具返回值裁掉，但模型的推理保留

本实验的阈值刻意设得很小（`COMPACT_AFTER = 2`），否则 agent 五步就把任务
做完了，压缩根本来不及触发。**效果等价于「窗口很小」。**

### 和实验 1-1 的关系

实验 1-1 的 `no_history` 模式，其实就是这里的 `truncate` 开到最激进
（只留 1 步）。区别在于：

- 1-1 是**故意破坏**，看它怎么坏
- 2-1 是**认真解决**，比较几种真实方案的代价
