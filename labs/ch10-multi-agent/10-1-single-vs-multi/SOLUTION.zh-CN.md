# 实验 10-1 答案：单 agent vs 多 agent

## 一、实测数据

后端：Claude Code（`claude -p`），2026-07-28 实测。

| 模式 | 召回 | 明显 | 隐蔽 | 误报 | 模型调用 |
|---|---|---|---|---|---|
| **single** | **8/8** | 4/4 | 4/4 | **0** | **1** |
| chunked | 8/8 | 4/4 | 4/4 | 0 | 4 |
| specialists | 8/8 | 4/4 | 4/4 | **2** | 4 |
| critic | **7/8** | 4/4 | **3/4** | 0 | 2 |

**单 agent 在每一列上都不输，成本是最低的。**

- `chunked`：结果完全一样，**花了 4 倍的钱**
- `specialists`：召回一样，**多了 2 个误报**，还是 4 倍的钱
- `critic`：**丢了一个真问题**，2 倍的钱

**四种模式里，没有一种比 single 好。**

---

## 二、为什么会这样：单 agent 已经到顶了

这是理解全部结果的关键：

> **single 拿了 8/8。天花板就在那里。**
>
> 无论你加多少个 agent、怎么组织它们，**召回率的上限也是 8/8**。
> 剩下能变的只有两件事：**误报变多**，或者**成本变高**。
>
> 实测里这两件事都发生了。

所以这个实验真正的教学点不是「多 agent 没用」，而是：

> **加 agent 之前，先测单 agent 到顶了没有。**

这一步在真实项目里几乎总被跳过。常见的流程是：
上多 agent → 效果不错 → 归功于架构。
**但没人回头去测：单 agent 是不是本来就能做到？**

练习 1 就是让你**把天花板顶开**（加到 100 段代码），
找到 single 开始漏的那个点——**那个点才是多 agent 开始有意义的地方**。

## 三、`specialists` 的 2 个误报：手里有锤子

`specialists` 报了 **S22** 和 **S23**：

```python
# S22
def send_report(to):
    body = render_template("report.html", data=fetch())
    mailer.send(to, body)

# S23
def parse_dates(rows):
    return [datetime.strptime(r["d"], "%Y-%m-%d") for r in rows]
```

这两段都没有本实验定义的那四类问题。为什么会被报？

**看四个专家各自报了什么，答案就很清楚了：**

```
  [agent 1/4] SQLI     报了 2 条：S01, S09                              ← 完美
  [agent 2/4] SECRET   报了 2 条：S03, S11                              ← 完美
  [agent 3/4] PATH     报了 2 条：S05, S14                              ← 完美
  [agent 4/4] INPUT    报了 8 条：S01, S05, S07, S09, S14, S15, S22, S23  ← ☠
```

**三个专家精确得无可挑剔，全部误报都来自第四个。**

而且 INPUT 专家不只是多报了 2 个误报——它还把 S01、S05、S09、S14
（分别属于 SQLI / PATH 类）也报了进来，**尽管提示词明确说了「这一轮只报这一类」**。
真正属于 INPUT 的只有 S07 和 S15，它报了 8 条。

**为什么偏偏是它？** 因为这四个类别的**清晰程度差得很远**：

| 类别 | 判断标准 | 专家表现 |
|---|---|---|
| SQL 注入 | 有没有把变量拼进 SQL 字符串 | 精确 |
| 硬编码密钥 | 源码里有没有写死的凭据 | 精确 |
| 路径穿越 | 路径有没有被限制在目录内 | 精确 |
| **未校验输入** | **……什么算"校验"？校验到什么程度算够？** | **过度上报 4 倍** |

> **专家模式的失败，集中在定义最模糊的那个专家身上。**
>
> 前三类都能一句话说清"什么算问题"，第四类不能——
> 严格说，**任何**外部输入都可以说"校验得不够"。
> 于是这个专家找到了它被要求找的东西，因为总能找到。

而这个专家收到的系统提示词是：

```
你是一个代码安全审查员，**这一轮只负责一类问题**：
**未校验输入：直接使用外部传入的值，没有校验类型/范围/白名单**
下面是若干段代码……请**只找这一类问题**
```

> **这段提示词隐含了一个预期：这里有未校验输入问题。**
>
> 于是 agent 去找了，而且**找到了**——`strptime` 确实会因为格式不对而抛异常，
> `render_template` 确实在处理外部数据。技术上不算胡说，但都不是本任务定义的问题。

**这是专家模式的特征性失败：过度上报。**

而关键在于：

> **这个失败是被提示词制造出来的，不是模型的固有缺陷。**
>
> 你把一个人关进屋子里说「你今天只管找路径穿越」，
> 他很难交出一张白纸。
>
> **而且它只在"你的类别定义足够模糊"时才发生** —— 这是可以事先判断的：
> **如果你没法用一句话说清"什么算这类问题"，就别为它单独派一个专家。**

练习 3 就是验证这一点：加一句「**一个都没有就返回空列表，这是完全正常的结果**」。
如果误报因此降下来，那就证明了病因在提示词。

### 对比：`chunked` 这次没有误报

同样是 4 个 agent、同样 4 次调用，`chunked` 的每个 agent 收到的是
**完整的四类定义**，只是代码少了。它没有被暗示「你负责的这类一定存在」。

> **成本一样，切法不同，失败方式完全不同。**
>
> 这就是多 agent 真正的设计问题：**不是"要不要多"，是"按什么维度拆"**，
> 而每种拆法都自带一种特征性的坏法。

## 四、`critic` 的致命一刀：推理是对的，结论是反的 ★

这是本实验最值得看的一段。

`critic` 第一阶段（single）找全了 8 个。第二阶段复核时，它把 **S14 判成了误报**：

```python
# S14（真问题：路径穿越）
def download(name):
    target = os.path.normpath(os.path.join(BASE, name))
    return send_file(target)
```

复核员给出的理由，**一字不改**：

> **「normpath 仅规范化路径，未校验结果仍在 BASE 之内，`../` 仍可逃逸
> ——但归类上属真问题」**

**读三遍。**

它说：
1. `normpath` 只做规范化，不做校验 ✓ 对
2. 结果没有校验是否还在 BASE 之内 ✓ 对
3. `../` 仍然可以逃逸 ✓ 对
4. **「但归类上属真问题」** ✓ 它自己都说了这是真问题

**然后它把 `decision` 标成了 `drop`。**

> **推理全对，结论相反。**

于是召回从 8/8 掉到 7/8，隐蔽项从 4/4 掉到 3/4。**多花一次调用，把结果变差了。**

### 为什么会这样

复核员的任务定义本身有个不对称：

> 它被要求「**找出哪些是误报**」。
>
> 一个被派去找误报的 agent，**倾向于找到误报**——
> 和上面那个专家过度上报是**同一个机制**，只是方向相反。

而复核环节还有一个结构性特点，比这个 bug 更重要：

> **复核员只能删，不能加。**
>
> 第一阶段漏掉的东西，第二阶段**永远**找不回来。
> 所以它的期望收益是「减少误报」，期望风险是「误删真问题」。
>
> **当第一阶段本来就没有误报时（本实验正是如此），
> 这次调用的期望收益是 0，期望风险是正的。** 纯亏。

### 怎么修

练习 4 给的方向：**把删除换成降级**。

```python
# 不要：keep / drop
# 改成：高置信 / 低置信 —— 两种都保留，只是排序不同
```

> **不可逆的删除交给人，agent 只负责排序。**
>
> 这和实验 4-1 里「给退款接口加幂等键」是同一个思路：
> **别让 agent 做不可逆的事**，尤其是在它的判断本身就有系统性偏向的时候。

## 五、我把标准答案写错了，而模型抓住了它 ★★

这一节比上面所有内容都重要。

**第一次跑的时候**，`chunked` 和 `specialists` 都报了 **S13**，
而我的标准答案说 S13 是安全的。程序如实标成了「☠ 误报」。

S13 当时长这样：

```python
def export(path):
    target = os.path.join(EXPORT_DIR, path)
    if not target.startswith(EXPORT_DIR):
        raise ValueError("bad path")
    return open(target, "w")
```

我当时的想法是：「有 `startswith` 检查，安全。」

**我错了。** 实际验证：

```
path                 旧写法放行   join 结果                       修好后放行
report.csv           True        /export/report.csv             True
../etc/passwd        True        /export/../etc/passwd          False   ← 就是它
../export_evil/x     True        /export/../export_evil/x       False
```

`os.path.join` **不做路径规范化**。`/export/../etc/passwd` 确确实实
以 `/export` 开头，`startswith` 检查直接放行，然后 `open()` 会把它解析成
`/etc/passwd`。

**这是一个真实的路径穿越漏洞。模型报对了，是我的标准答案错了。**

我把 S13 改成了真正安全的写法：

```python
target = os.path.realpath(os.path.join(EXPORT_DIR, path))
if os.path.commonpath([target, EXPORT_DIR]) != EXPORT_DIR:
    raise ValueError("bad path")
```

然后重跑，上面那张表就是重跑后的数据。

### 这件事的教训

> **当你的评测和被测对象不一致时，先怀疑评测。**

这不是谦虚，是概率问题：

- 你的标准答案是**一个人**在**一个下午**写的
- 被测的模型见过**海量**的安全代码和 CVE

**在"谁更可能记错 `os.path.join` 的语义"这件事上，赌模型比赌自己划算。**

而更具体的信号是：

> **如果多个独立的 agent 都报了同一条"误报"，那大概率不是误报。**
>
> 本实验里 `chunked` 的第 3 个分片 agent 和 `specialists` 的 PATH 专家
> **各自独立**地报了 S13。两个互不通信的 agent 得出同一个结论——
> 这本身就是一个强信号。

这直接延续了实验 6-1 的主题：

| 实验 | 我踩的坑 |
|---|---|
| 6-1 | JSON 解析失败被记成「模型不稳定」——**测量工具的故障被记成被测对象的缺陷** |
| **10-1** | **标准答案写错被记成「模型误报」——同一类错误的另一种形态** |

> **在指责被测对象之前，先给你的评测器写测试。**

⚠️ 顺带说一句：这个坑之所以被抓到，是因为**判据是机械的、结果是列出来的**。
如果我用的是「让另一个模型打个总分」，S13 这件事会被平滑掉，我永远不会发现。
**可解释的判据不只是为了让人看懂，也是为了让错误暴露出来。**

## 六、练习答案

### 练习 1 ⭐⭐ 制造 headroom

把片段加到 100 段左右（复制干净的那些，改改变量名和函数名），single 通常开始漏。

**那个开始漏的点，就是多 agent 开始有意义的点。**

到那时你会看到本实验没能展示的东西：

| 模式 | 有 headroom 时的预期 |
|---|---|
| `chunked` | 召回应该上去——因为每个 agent 的注意力不再被 100 段稀释 |
| `specialists` | 召回也应该上去，而且**隐蔽项**提升更明显 |

> 但请注意：**这两个的收益来源不同。**
> `chunked` 解决的是「东西太多看不过来」，
> `specialists` 解决的是「同时想四件事想不清楚」。
>
> **你的任务是哪一种瓶颈，决定了你该按哪个维度切。**

### 练习 2 ⭐⭐ 造一个需要跨段推理的问题

加两段：

```python
# S25
DEBUG_TOKEN = "dbg-7c2a"          # 单独看：硬编码密钥（已经算问题）

# S26
logger.info("auth attempt with %s", DEBUG_TOKEN)   # 单独看：只是打日志
```

真正的事故是**两段合起来**：密钥被写进了日志，会流进日志系统、被采集、被检索。

`chunked` 把它们分到不同 agent 时——**结构性地看不见**。

> **这不是运气问题。切数据的那一刀，直接切断了这种发现的可能性。**
>
> 一般化：**按数据切分，隐含假设了"问题是局部的"。**
> 这个假设在代码审查、日志分析、合规检查里**经常不成立**。

### 练习 3 ⭐⭐ 给专家加一句「可以什么都不报」

加上这句之后，误报通常会降下来。

如果确实降了，它证明了第三节的判断：

> **过度上报是被提示词的隐含预期制造出来的，不是模型的固有缺陷。**

这条经验可以直接用在任何「分类/检测」类的提示词上：

> **明确告诉模型「空结果是合法的、正常的、不丢人的」。**
>
> 你不说，它就会默认「你既然让我找，那就是有」。

### 练习 4 ⭐⭐⭐ 复核员只能降级不能删除

改成「高置信 / 低置信」之后，**召回不会掉**（因为什么都没删），
但你仍然得到了排序信息——真正可疑的排在前面。

代价是：**你没有减少人要看的条目数量。**

> **这就是那个取舍的本质：**
> - 让 agent 删 → 省人力，但会误删，而且**误删是静默的**
> - 让 agent 排序 → 不省条目数，但**不会丢东西**，而且人能一眼看到重点
>
> 在**漏掉的代价 >> 多看几条的代价**的场景（安全、医疗、合规），
> **永远选排序，不选删除。**

### 练习 5 ⭐⭐⭐ 三种组合起来

specialists（4 次）+ critic（1 次）+ 最后合并 = 约 6 次调用。

预期：召回 8/8（specialists 已经满了），误报可能被 critic 清掉一部分，
但**也可能像本实验一样误删真问题**。

**做完请对着 single 那一行看：花了 6 倍的钱，买到了什么？**

> 如果答案是「什么也没买到」——**恭喜，你亲手测出了这个实验最重要的一课。**
>
> 而且这一课的适用范围远超多 agent：
> **任何架构复杂度，都应该先证明它解决的问题真实存在。**

## 七、放回全局

这已经是本仓库第四次出现同一个形状了：

| 实验 | 便宜但"弱"的做法 | 贵但"强"的做法 | 实测 |
|---|---|---|---|
| 2-1 | 不压缩 | 压缩 | 各有代价 |
| 3-2 | 全部塞进去 | 先检索 | 检索会漏 |
| 4-2 | 全部工具都给 | 检索工具 | **检索漏了，全给没漏** |
| 5-1 | 整份重写 | diff 编辑 | 成本差 8 倍，可靠性没差 |
| **10-1** | **1 个 agent** | **4 个 agent** | **1 个更好** |

**规律非常一致：**

> **"更复杂的做法"总是同时带来新的失败模式，
> 而它承诺的收益**有前提**——那个前提可能不成立。**
>
> 所以顺序应该是：
> 1. 先用最简单的做法，**量出它的天花板**
> 2. 确认天花板确实卡住了你
> 3. **然后**再引入复杂度，并且**量它引入的新失败**

本仓库到目前为止，**在 5 个"简单 vs 复杂"的对照里，简单的赢了 3 次**。

这不代表复杂的做法没用——代表**它们的适用条件比宣传的窄**，
而**你有能力自己测出来**。
