# 实验 3-2：从零写检索 —— 为什么关键词搜不到该搜的东西

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. 从零手写一个 **BM25** 检索器（不到 40 行，零依赖），搞懂它凭什么排序
> 2. 关键词检索的**结构性边界**：查询和答案不共享关键词时，它必然搜不到
> 3. 没有 embedding 也能跨过这条边界：**让模型来搭那座桥**

>

> 是纯粹的集合运算。所以那部分结果你跑十遍都一模一样。
>
> **需要多久**：25 分钟（不联网）。

## 先搞清楚问题是什么

实验 3-1 结束在一个问题上：**记忆攒到几百条，全塞进上下文就装不下了。**

于是你需要检索：每次只取出**这次用得上**的那几条。

这个实验里有 36 条记忆（就是 3-1 那个人攒了半年的），用户问：

```
帮我列一个成都出差期间的餐厅清单。
```

必须取到的有三条：

```
★ 对花生过敏，误食会送医院（严重过敏）
★ 完全不吃辣，一点辣都不能接受
★ 2026-08-03 至 2026-08-09 期间赴成都出差三天，住在春熙路附近
```

**现在盯着第一条和问题看十秒。**

```
问题：帮我列一个成都出差期间的餐厅清单
记忆：对花生过敏，误食会送医院
```

**一个字都不重合。**

关键词检索靠什么找东西？靠字面重合。所以——它找不到。

> 这就是本实验要让你亲身撞一次的那堵墙。

⚠️ 36 条其实还塞得进上下文，这是**故意**的：正因为塞得下，
`stuff_all` 才能当「天花板」用，别的模式漏了什么一比就知道。
真实系统里是几千几万条，那时候 `stuff_all` 这一列根本不存在。

## 第 1 步：跑 BM25，看它漏了什么（6 分钟）★ 本实验的核心

```bash
python3 agent.py keyword "（复制同一个问题）"
```

### 🤔 先猜

- 3 条必须取到的，它能取到几条？ ___
- 取不到的那几条，是因为**排在第 6 名**，还是**压根没进候选**？ ___

### 👀 观察什么

**先看取到了什么，再看漏了什么，最后看回答。三个一起看。**

### 💡 学到什么

这一节请慢一点。BM25 取回来的三条**看起来非常合理**：

```
★ 2026-08-03 至 2026-08-09 期间赴成都出差三天，住在春熙路附近
  公司报销标准：出差住宿每晚不超过 600 元
  去年十月去过一次杭州出差，住在西湖边上，觉得性价比一般
```

行程、预算、出差经验——**每一条都跟「成都出差餐厅」相关**。
检索**看起来是成功的**。

然后看回答里推荐了什么。（提示：麻婆豆腐、甜水面、火锅、串串、老麻抄手……）

> **最危险的检索失败，不是搜出一堆垃圾 —— 是搜出一堆看起来很对的东西，
> 而真正要命的那条不在里面。**

现在回答这个问题：**为什么漏掉「花生过敏」？**

自己动手验证一下：

```bash
python3 -c "import agent; print(agent.tokenize('对花生过敏，误食会送医院'))"
python3 -c "import agent; print(agent.tokenize('帮我列一个成都出差期间的餐厅清单'))"
```

**两个列表有交集吗？**

没有交集 → BM25 分数是 0 → **它连候选都进不去**。
不是排名靠后，是**根本不在名单上**。这不是调参能救的。

## 第 2 步：看懂 BM25 到底在算什么（5 分钟）

打开 `agent.py`，第 2 部分不到 40 行，就是完整的 BM25。

它的直觉只有三条：

| 直觉 | 代码里对应 |
|---|---|
| 查询词在文档里出现越多 → 分越高 | `tf = tokens.count(w)` |
| 但这个词到处都是（比如「的」）→ 不值钱 | `idf = math.log(...)` |
| 文档越长，出现得多是应该的 → 归一化 | `doc_len / avg_len` |

### 🔧 试试改一个数

把 `TOP_K` 从 5 改成 20，重跑 `keyword`。

**先猜**：召回率会变成 3/3 吗？

> 结果会告诉你一件重要的事：**这不是"取少了"的问题。**

### 💡 顺带学到：中文怎么切词

中文没有空格。正规做法要上分词器（jieba 之类），但这里用了更简单的招：

```python
「花生过敏」 → 花生、生过、过敏
```

**相邻两个字组成一个词**（bigram）。不需要任何词典，搜索效果出奇地好——
真实搜索引擎处理中文时也常拿它兜底。

## 第 3 步：让模型来搭那座桥（6 分钟）

既然问题在于「问题里没有『过敏』这个词」，那就**先把这个词想出来**。

```bash
python3 agent.py expanded "（同一个问题）"
```

### 👀 观察什么

盯住「模型想出来的查询」那几行。**这是本实验最值得看的输出。**

### 💡 学到什么

打开 `agent.py` 看 `sys_expand` 提示词，核心是这句：

```
关键在于：**别只重复问题里的词。** 问题里通常不会出现真正该查的那个词。
比如问「推荐餐厅」，真正该查的是「过敏」「忌口」「口味」——
这些词一个都没出现在问题里。
```

> **语义鸿沟是模型补上的，不是索引补上的。**
>
> 向量检索（embedding）解决同一个问题的方式，是让「餐厅」和「过敏」在向量空间里
> 挨得近一点。这里没有 embedding，所以我们用模型的**世界知识**来补：
> 它知道推荐餐厅要考虑过敏，于是它自己造出了那个查询词。
>
> **两条路的代价不同**：向量检索一次调用就够，但要跑模型、要存向量；
> 查询扩展要多花一次模型调用，但零基础设施。

## 附：概念速查

### 四种策略的取舍

| 策略 | 召回率 | 模型调用 | 取回条数 | 什么时候用 |
|---|---|---|---|---|
| `stuff_all` | 100%（必然） | 1 | 全部 | 记忆量小到能全塞（几十条以内） |
| `keyword` | **看运气** | 1 | 少 | 查询和文档用词一致（代码搜索、日志检索、精确匹配） |
| `expanded` | 高 | 2 | 中 | **默认选它**——一次调用换回召回率 |
| `agentic` | 高 | 3+ | 多 | 需要**多跳**：搜到 A 才知道该搜 B |

### 关键词 vs 向量：一句话区分

> **关键词检索匹配的是「字面」，向量检索匹配的是「意思」。**
>
> 「花生过敏」和「餐厅推荐」字面无关，意思相关。
> 所以前者搜不到，后者能搜到。

本实验没有向量检索（需要下载模型权重），但给了你第三条路：
**让模型把「意思」翻译回「字面」**，再交给关键词检索。

### 一条工程原则

> **检索失败最危险的形式，是搜回来一堆看起来很相关的东西。**
>
> 空结果你会警觉；一份合理但缺了关键一条的结果，你不会。

所以生产系统一定要有**召回率兜底**：关键信息（过敏、禁忌、合规约束）
不要指望检索命中，**应该无条件always 拼进上下文**。
