# 实验 4-1：工具设计 —— 决定成败的不是模型，是你写的那几行说明

[English](README.md) · **简体中文**

> **你会学到什么**
>
> 1. 同一个模型、同一个任务，**只改工具描述和错误信息**，结果从「一次做对」到「做不成」
> 2. 一个 **2×2 对照**告诉你：工具描述和错误信息，哪个更值钱、什么时候值钱
> 3. 错误信息不是日志，**是下一轮上下文的一部分** —— 是你能给模型的最及时的指导
> 4. 对**会改变世界**的工具（付款、退款、删除），含糊的错误信息不只是慢，是**直接卡死**
>
> **怎么学**：判定是纯机械的 —— 程序知道唯一正确的那次调用长什么样，比对即可。
> 不靠关键词，不靠模型判分。
>
> **需要多久**：25 分钟（不联网）。

---

## 先搞清楚问题是什么

前面三章里，工具一直是「顺便有的东西」。现在正面看它。

给模型一个工具，你实际上要给的是**两样东西**：

```
1. 事前说明：这个工具是干嘛的，参数怎么填          ← 工具描述
2. 事后反馈：你填错了，错在哪，该怎么改            ← 错误信息
```

大多数人在第 1 项上花了点力气，在第 2 项上**一点力气都没花**（直接 `raise` 了事）。

这个实验把这两件事拆成两个独立开关，做一个 2×2：

|  | 错误信息有用 | 错误信息没用 |
|---|---|---|
| **描述写得好** | `good` | `silent_errors` |
| **描述写得烂** | `vague_desc` | `both_bad` |

**横着比** → 错误信息值多少钱
**竖着比** → 工具描述值多少钱

## 任务和三个坑

一张退款工单：

```
客户 alice@example.com 说她买的那副耳机是坏的，帮她退款。
```

三个工具：`find_orders` / `get_policy` / `issue_refund`。

里面埋了三个坑，**全是真实项目里最常见的**：

| 坑 | 长什么样 |
|---|---|
| **单位** | `amount_cents` 的单位是**分**，129.90 元要写 12990，不是 129.9 |
| **枚举** | `reason_code` 只接受 `DEFECTIVE` / `WRONG_ITEM` / `CHANGED_MIND` |
| **业务规则** | alice 有两笔订单，其中一笔（食品，40 天前）已过退款窗口 |

唯一正确的调用是：

```python
issue_refund(order_id="ORD-1001", amount_cents=12990, reason_code="DEFECTIVE")
```

⚠️ **四种模式下，工具的校验逻辑完全一样**。没有哪个模式「更容易成功」——
只是有的模式让模型**更容易搞明白自己错在哪**。

## 第 0 步：先建立基线（4 分钟）

```bash
cd labs/ch4-tools/4-1-tool-design
python3 agent.py good
```

直接回车看例子，输 `1`。

### 👀 你会看到

```
  ─── 这一单办成了吗 ───
  ✓ 办成了：第 3 轮发起了正确的退款
  用了 3 轮
  工具调用 3 次，其中失败 0 次
```

### 💡 学到什么

**零次失败。** 三个坑一个没踩。

打开 `agent.py` 看 `tools_good` 那段描述。注意它的写法——
**每一句话都在预先回答模型会问的一个问题**：

```
- days:  往前查多少天，整数，最大 90。不确定就填 90。
                                       ↑ 预先解决「我该填多少」的犹豫

- amount_cents: ……例如 129.90 元要写成 12990，不要写 129.9。
                find_orders 返回的 amount_cents 已经是分，直接用。
                                       ↑ 举了反例，还指了数据从哪来

- category: 必须是这三个之一……（品类值在 find_orders 的返回里能直接看到，照抄即可）
                                       ↑ 不但给了枚举，还说了从哪拿
```

> **好的工具描述不是「说明这个函数做什么」，是「预判调用方会在哪里卡住」。**

## 第 1 步：把描述改烂（6 分钟）★ 重点

```bash
python3 agent.py vague_desc "（复制同一个工单）"
```

`tools_vague` 长这样——**这不是我编出来吓人的**，这是自动从函数签名生成的
文档最常见的样子：

```
1. find_orders(email, days) —— 查询订单
2. get_policy(category) —— 查询政策
3. issue_refund(order_id, amount, reason) —— 处理退款
```

### 🤔 先猜

- 它能办成吗？ ___
- 会失败几次？分别栽在哪个坑上？ ___

### 👀 观察什么

**一次一次看失败**。每次失败之后的那一轮，注意它是怎么改的。

### 💡 学到什么

失败是一次一次来的，而且**每一次都对应描述里缺的一句话**。

你会看到一个很有意思的现象：模型把 `amount_cents` 填对了（12990），
**尽管描述里根本没提单位**。

**为什么？** 因为它在 `find_orders` 的返回值里见过这个字段名：

```json
{"order_id": "ORD-1001", "amount_cents": 12990, ...}
```

> **工具的返回值也是文档。** 一个起对了名字的返回字段，
> 抵得上一段参数说明。

这条可以直接用在你自己的项目里：**返回 `amount_cents` 而不是 `amount`，
返回 `created_at_iso` 而不是 `time`。** 命名就是在教模型。

## 第 2 步：把错误信息改烂（6 分钟）★ 重点

```bash
python3 agent.py silent_errors "（同一个工单）"
```

现在描述是好的，但所有错误都只回一句「调用失败。」

### 🤔 先猜

比 `good` 差多少？

### 💡 学到什么

**结果可能会让你意外。** 想清楚这个问题再看 SOLUTION：

> **如果模型一次都没出错，错误信息写得再好，有用吗？**

这就是 2×2 的意义——**有些变量只在特定条件下才起作用**。
单独测一个变量，你会得出「它没用」的错误结论。

## 第 4 步：自己动手改（练习）

### 练习 1 ⭐ 只补一句话

在 `tools_vague` 里**只加一行**，把 `reason_code` 的枚举补上：

```python
3. issue_refund(order_id, amount_cents, reason_code) —— 处理退款
   reason_code 必须是 DEFECTIVE / WRONG_ITEM / CHANGED_MIND 之一
```

**先猜**：失败次数会从 3 次降到几次？

> 这道题是想让你建立一个直觉：**文档的投入产出比高得离谱。**
> 一行字换一轮往返。

### 练习 2 ⭐⭐ 分清「写得少」和「写得错」

看仔细 `tools_vague` 里的第 3 行：

```
issue_refund(order_id, amount, reason)      ← 文档里写的
issue_refund(order_id, amount_cents, reason_code)   ← 实际的
```

**参数名是错的**，不只是缺。这就是文档和实现漂移之后的样子。

把它改成正确的参数名（但仍然不写任何说明），重跑 `vague_desc`。

**先猜**：这一改能省下几次失败？

> **过时的文档比没有文档更糟** —— 没文档模型会谨慎，
> 错文档模型会自信地走错路。

### 练习 3 ⭐⭐ 给 `issue_refund` 加幂等键

跑完 `both_bad` 你会看到模型自己提了这个建议。照做：
给 `issue_refund` 加一个 `idempotency_key` 参数，同一个 key 重复调用返回同一个结果。

**先想清楚**：加了之后，`both_bad` 还会卡死吗？

> 这道题真正想说的是：**有些问题不该靠提示词解决，该靠接口设计解决。**

### 练习 4 ⭐⭐⭐ 把错误信息改成「过度详细」

把某个错误信息写成一大段（比如把整个 API 文档贴进去），重跑 `vague_desc`。

**先猜**：更详细一定更好吗？

> 想想第 2 章：错误信息进上下文，上下文有预算。
> **每一条错误信息都在花钱。**

### 练习 5 ⭐⭐⭐ 换个更难的工单

```bash
python3 agent.py good "alice@example.com 要退她买的咖啡豆。"
```

那笔订单已经过了退款窗口（食品 7 天，买了 40 天）。

**先猜**：`good` 模式下它会怎么办？`both_bad` 呢？

> 注意：这次「办不成」是**正确答案**。观察它有没有把「不能退」
> 和「我不知道怎么调这个工具」区分开 —— 这两件事在日志里长得很像。

## 附：概念速查

### 一份好工具描述的清单

对每个参数问自己：

- [ ] **类型和单位**说了吗？（分 / 元、秒 / 毫秒、UTC / 本地时间）
- [ ] **取值范围**说了吗？（最大 90、必须为正）
- [ ] **枚举值**列出来了吗？（别指望模型猜对你的 code）
- [ ] **举例了吗？** 一个 `"alice@example.com"` 胜过一句「邮箱地址」
- [ ] **这个值从哪来？**（「照抄 find_orders 返回的 category」）
- [ ] **不可逆的操作标注了吗？**

对返回值：

- [ ] 字段名**自带单位**吗？（`amount_cents` 而不是 `amount`）

### 一份好错误信息的三件事

```
1. 什么错了       "reason_code 必须是 DEFECTIVE / WRONG_ITEM / CHANGED_MIND 之一"
2. 你传的是什么   "你传的是 \"damaged\""
3. 该怎么改       "商品坏了用 DEFECTIVE。"
```

第 3 条最常被漏掉，**也最值钱**。

### 一条工程原则

> **错误信息不是给运维看的日志，是给模型看的下一轮提示词。**
>
> 你在 `raise ValueError("invalid")` 里省下的那 20 个字，
> 会在每一次调用里被重新付出去。

## 卡住了？

| 你看到的 | 怎么办 |
|---|---|
| `✗ 没找到可用的后端` | 按屏幕上三个选项装任意一个 |
| 某次跑出来和文档不一样 | **正常**，模型是随机的。看 2×2 的**形状**，不看具体数字 |
| `good` 也失败了 | 少见但可能。再跑一次；仍然失败的话，看它栽在哪个坑，那就是描述还能改进的地方 |
| 想看模型收到的原文 | 把 `SHOW_PROMPT` 改成 `True` |
| 忘了有哪些命令 | 敲 `python3 agent.py`（不带参数） |
