[English](README.md) · **简体中文**

> **你会学到什么**

> 1. Agent 不是什么神秘的东西 —— 它就是 `LLM + 上下文 + 工具` 套在一个 while 循环里

## 第 1 步：看清楚「上下文」到底是什么（5 分钟）

### 🔧 做什么

打开 `agent.py`，把开头这行改成 `True`：

```python
SHOW_PROMPT = True
```

再跑一次 `python3 agent.py full`。

### 👀 你会看到

每一轮，程序会把**真正发给模型的那段文字**原样打出来：

```
  ┌─── 实际发给模型的内容 ──────────────────
  │ 任务：我想买 3 个 mechanical keyboard…
  │
  │ --- 第 1 步 ---
  │ 你的回复：{"reasoning": "先查单价…", "calls": [...]}
  │ 工具 search_products 返回：{"name": "Keychron Q1 Pro", "usd": 199.0}
  │
  │ 现在给出你的下一条 JSON 回复。
  └────────────────────────────────────────
```

### 💡 学到什么

**大模型的接口是无状态的。** 服务器那边什么都不存。你每问一次，都得把前面
发生过的所有事情**重新完整地发一遍**。

所以「上下文」就是上面框里那段字符串。**Agent 在第 5 轮"知道"的一切，
就是那段文字里写了的东西。没有别的了。**

顺便注意「提示词 xx 字符」那个数字在一轮轮变大 —— 那就是上下文在累积。

## 第 2 步：先猜，再删掉历史（8 分钟）

### 🤔 先猜（别跳过）

我们要把上下文里**除最近一步外的所有历史**删掉，只留最后一步。猜一下：

- 轮数会变多还是变少？ ___
- 工具调用次数呢？ ___
- 答案还对吗？ ___

### 🔧 做什么

```bash
python3 agent.py no_history "（复制你第 0 步用的同一个任务）"
```

> ⚠️ **任务必须和第 0 步完全一样**，否则不构成对比。
> 程序跑完会打印一行现成的命令，复制改模式名就行，不用手抄。

### 👀 观察什么

盯着每轮标题里的这一句：

```
第 3 轮 | 上下文只含第 2 步 | 提示词 204 字符
```

对比 `full` 模式那次是 `上下文含第 1~2 步`，字符数一路涨到 700+。
这里永远只有一步，字符数卡在 200 左右**不涨**。

### 💡 学到什么

`no_history` 对应真实事故：**上下文窗口被截断**。对话太长、被压缩、
被裁剪 —— agent 就会开始重复做已经做过的事。

> **如果它居然没坏**（照样答对了），恭喜你撞到了一个有意思的现象。
> 别急着看答案，先想想：第 4 轮的上下文里根本没有中间结果那个数，
> 它是怎么知道的？想不出来再翻 SOLUTION。

## 第 3 步：把剩下三种消融跑完（15 分钟）

**每跑一个之前都先猜。** 表格填完再往下：

| 模式 | 删掉了什么 | 你猜：轮数 | 你猜：答案对吗 | 实际 |
|---|---|---|---|---|
| `no_reasoning` | 模型自己的思考过程 | | | |
| `no_tool_calls` | 压根不给它工具 | | | |
| `no_tool_results` | 工具照调，但不给看返回值 | | | |

```bash
python3 agent.py no_reasoning "（同一个任务）"
python3 agent.py no_tool_calls "（同一个任务）"
python3 agent.py no_tool_results "（同一个任务）"
```

跑完可以用 `python3 agent.py all` 一次看全部对比表（约 3~8 分钟，
**记得先把 `SHOW_PROMPT` 改回 `False`**，不然会刷屏）。

### 💡 学到什么

这四种坏法，**每一种都对应一类真实线上事故**：

| 模式 | 对应的真实故障 |
|---|---|
| `no_history` | 上下文窗口被截断 |
| `no_reasoning` | 你为了省 token 把 thinking 丢了 |
| `no_tool_calls` | 权限配错、工具没注册上 |
| `no_tool_results` | 工具集成写挂了 |

**这个实验其实是一本 agent 故障图鉴。**

## 附：概念速查

读代码时想不起来某个概念，回这里查。

### Agent 的循环

```
loop:
    reply = llm(messages)              # 模型说它想干嘛
    if 没有工具调用: 结束                # 它给答案了 → 退出
    for 每个工具调用:
        result = 你的代码去执行(...)     # 模型跑不了，你跑
        messages.append(result)        # 结果塞回去
```

**模型是个会说 JSON 的规划器，你是它的手。**

### 完整版：一个循环有几个出口？

上面那 6 行漏了一件要命的事 —— **只检查 `tool_calls` 是个死循环**。
模型完全可以每轮都点名工具，永远不给答案。

真实的循环至少要这样：

```python
trajectory = [ {role: "user", content: task} ]

for round in 1 .. MAX_ROUNDS:                 # ← 出口 3：硬性轮数上限

    prompt = STATIC_PREFIX + trajectory       # 系统提示词 + 工具定义，然后
                                              # 整条轨迹，每轮重发一遍

    if length(prompt) > CONTEXT_LIMIT:        # ← 出口 4：装不下了
        trajectory = compact(trajectory)      #    注意是压缩后【继续】，不是停

    reply = call_model(prompt)                # 无状态：服务器那边什么都不存

    if reply failed to parse:                 # ← 出口 5：JSON 抠不出来
        if retries_left: continue             #    重试 —— 千万别静默当成
        else: raise ParseError                #    「它答完了」

    trajectory.append(reply)                  # 它说的话，立刻记进轨迹

    if reply has "answer":                    # ← 出口 1：它自己声明完成
        return reply.answer

    if reply.tool_calls is empty:             # ← 出口 2：它不再点名工具
        return reply.content                  #    （等价于完成）

    for call in reply.tool_calls:             # 你来执行，它只是点名
        result = TOOLS[call.name](**call.args)
        trajectory.append( {role: "tool", content: result} )

return FAILED                                 # 跑满上限还没答案
                                              # ← 这是【失败】，不是完成
```

**出口分三类：**

| | 出口 | 语义 |
|---|---|---|
| **正常完成** | `answer` 字段存在 | 它说完了 |
| | `tool_calls` 为空 | 它不再要工具（等价于说完了） |
| **资源耗尽** | 轮数到上限 | ☠ **失败**，不是完成 |
| | 上下文装不下 | → 压缩后**继续**，不是停 |
| | token / 成本预算 | 真实系统必须有 |
| **异常** | 解析失败 | 见下面那个坑 |
| | 工具连续失败 / 反复调同一个 | 循环检测 |
| | 用户中断、超时 | |

**本实验实现了出口 1、2、3。** 出口 4 是[实验 2-9](../../ch2-context-engineering/2-9-context-compression/README.zh-CN.md)
的主题；出口 5 本实验**故意没做**，原因见下。

### ⚠️ 一个坑：解析失败和「完成」长得一模一样

`agent.py` 里是这么写的：

```python
reply = parse_json_reply(raw_text)          # 抠不出 JSON 就返回 {}

has_answer   = "answer" in reply            # {} → False
wanted_calls = extract_tool_calls(reply)    # {} → []

if has_answer or len(wanted_calls) == 0:    # ← {} 会走进这里！
    answer = reply.get("answer") or raw_text.strip()
```

**空字典 `{}` 同时满足「没有 answer」和「没有 tool_calls」**，
于是解析失败被当成「它答完了」，把原始文本直接当答案返回。

这在本实验里是**故意的** —— `no_tool_calls` 模式下模型经常用大白话回答，
没有 JSON 可抠，那时候原始文本确实就是答案。

但代价是：**一次真正的解析失败（输出被截断、格式跑偏），会被静默当成一个「完成」。**
循环正常退出，返回一段看起来像答案的垃圾，**不报错**。

> 这和[实验 6-1](../../ch6-evaluation/6-1-llm-as-judge/README.zh-CN.md) 里
> 「JSON 解析失败被记成模型能力差」是同一个形状。
> 生产环境里要把这两种情况分开。

### 为什么会有两个「正常完成」出口？

出口 1（`answer` 字段）和出口 2（空 `tool_calls`）其实是冗余的 ——
**而出口 1 是拼字符串这条路欠下的债：**

- **真实 API**（结构化 tool use）只需要出口 2：`stop_reason != "tool_use"` **就是**停止信号，
  模型根本不需要自己声明 `answer`。
- **拼字符串的实现**必须有出口 1，因为你没有 `stop_reason` 可看，
  只能让模型在 JSON 里自己说「我完事了」。

**让模型自己声明终止，就意味着它可能忘了声明** —— 那就得靠出口 3（轮数上限）兜底。

### 上下文的五个组成部分

| 部分 | 作用 | 谁写的 |
|---|---|---|
| System prompt | agent 是谁、规则是什么 | 你 |
| 工具清单 | 它能调什么，参数长什么样 | 你 |
| User message | 任务 | 用户 |
| Assistant message | 它的思考 + 它请求的工具调用 | 模型 |
| Tool message | 你的代码返回了什么 | 你的代码 |

### 「轮」和「步」的区别

- **第 N 轮** = 程序视角：主循环第 N 次迭代，**正在**问模型
- **第 N 步** = 模型视角：第 N 轮的结果，**已经**记进历史了

所以第 N 轮发出去的提示词里，装的是第 1 步到第 N-1 步。

### 一轮可以调多个工具（并行）

一条模型回复里可以同时点名好几个工具，前提是它们**互不依赖**：

| 调用 | 依赖谁 | 能并行吗 |
|---|---|---|
| `search_products("keyboard")` → 199 | 无 | ✅ |
| `get_rate("USD","CNY")` → 7.24 | 无 | ✅ 和上面一起调 |
| `calc("199 * 3")` → 597 | 上面第一个 | ❌ 得先拿到 199 |

**省下的不是工具调用次数，是往返模型的次数** —— 每次往返要等 6~13 秒，
本地函数只要几微秒。

依赖关系靠什么保证？**只靠系统提示词里那两句话，代码里没有任何校验。**
根本机制是：工具参数是**字面量**不是引用，你手里没那个数就填不进去。

### Python 语法速查

代码注释是中文的，但有些写法新手可能卡住：

| 写法 | 什么意思 | 为什么这么写 |
|---|---|---|
| `CATALOG.get(key)` | 找不到返回 `None` 而不报错 | 用 `[]` 找不到会直接崩 |
| `dict(step["assistant"])` | **复制**一份字典 | 不复制的话下一行 `.pop()` 会改坏原始记录 |
| `.pop("reasoning", None)` | 有就删，没有也不报错 | 第二个参数是「找不到时的默认值」 |
| `json.dumps(x, ensure_ascii=False)` | 转 JSON 且中文正常显示 | 不加会变成 `\uXXXX` |
| `steps[-1]` / `[steps[-1]]` | 最后一项 / 包成单元素列表 | 包起来是为了让 `for` 循环写法不用改 |
| `range(1, n + 1)` | 产生 `1, 2, … n` | 不写 `+1` 会少循环一次 |
| `eval(s, {"__builtins__": {}}, {})` | 执行字符串，但切断内置函数 | 防危险代码（真实项目别这么用） |

**一个贯穿全文的设计**：所有工具出错时都 `return {"error": ...}` 而不是抛异常。
因为这段错误信息会被拼回上下文给模型看，让它自己改正 —— 崩掉就没这个机会了。
