# 实验 3-4：稠密向量检索 —— 它救回了什么，又漏掉了什么

[English](README.md) · **简体中文**

> **你会学到**
>
> 1. **「上 embedding 就好了」这句话，实测是半对的。** 稠密检索救回了一部分，
>    但**最危险的那条记忆，六种配置里没有一种能捞回来**
> 2. 稠密检索不是稀疏检索的**升级版**，是**换了一种漏法**
> 3. ANN（近似最近邻）的全部本事就一件事：**少看一些向量**。
>    投影树和可导航图只是两种「少看」的方式
> 4. 一个**调参数完全没用**的坑，而且它只在特定形状的数据上出现 ——
>    所以它会通过你的测试、然后在线上炸
> 5. **ANN 在 2000 条上是纯亏的。** 交点在一万条附近
>
> **怎么学**：两个索引都从零写在 `ann.py` 里，只用 numpy，没有 annoy / hnswlib。
> 所有召回率都是**机械算出来的**（第一部分比对写死的标准答案，
> 第二部分比对精确检索的结果），不需要模型当裁判。

## 从实验 3-5 留下的那个洞开始

[实验 3-5](../3-5-sparse-embedding/README.zh-CN.md) 停在一个很难受的地方：

```
用户问：      帮我列一个成都出差期间的餐厅清单
该取出的记忆： 对花生过敏，误食会送医院

            这两句话一个字都不重合 → BM25 给它 0 分
```

几乎所有教程接下来都会说同一句话：**「关键词检索的局限，用 embedding 解决。」**

这个实验不复述这句话，**去量它**。

## 第 1 步：稠密 vs 稀疏（3 分钟）★★★

```bash
python3 agent.py compare
```

它会问你要检索什么。**故意不设默认问题** —— 检索的效果完全取决于问的是什么。
想复现下面的数字就输入编号 1（成都出差餐厅清单，和实验 3-5 同一个问题）。

### 先猜

同一份 36 条记忆、同一个问题，稠密检索会把 BM25 漏掉的两条捞回来吗？

- [ ] 两条都能捞回来 —— embedding 就是为这个发明的
- [ ] 能捞回一条
- [ ] 一条都捞不回来

### 👀 你会看到

```
  三条标准答案在各自排序里排第几（共 36 条）：
    对花生过敏，误食会送医院（严重过敏）      稀疏 #36   稠密 #21
    完全不吃辣，一点辣都不能接受            稀疏 #4    稠密 #1
    2026-08-03 至 2026-08-09 期间赴成都出差   稀疏 #1    稠密 #2
```

### 💡 学到什么

**先看「不吃辣」那一行：#4 → #1。** 稠密检索确实在干活，它把一条
和问题**一个关键词都不共享**的记忆排到了第一。这就是 embedding 的价值，是真的。

**再看第一行。** `#36 → #21`。

36 条里排第 21。**这不是「差一点」，这是这条路上救不回来。**
而它偏偏是那条漏掉会把人送进医院的记忆。

> **稠密检索不是稀疏检索的升级版。**
>
> 它是**换了一种漏法**：稀疏漏的是「用词不重合」的，
> 稠密漏的是「语义空间里不靠近」的 —— 而「餐厅清单」和「花生过敏」
> 在 embedding 眼里，就是不够近。
>
> 更难受的是**它漏得很体面**：稠密检索的 top-5 里塞的是
> 「坐飞机偏好靠过道」「有一只叫豆豆的橘猫」，
> 这些东西的相似度**高于**花生过敏。你 review 日志时不会觉得有问题。

### 再往下走一步（值得做）

把开头的 `MODEL` 换成 `bge-m3`（`ollama pull bge-m3`）再跑一遍，
再把 `LANG` 换成 `"en"` 跑一遍。**四种组合。**
然后数一下：那条花生过敏，有几种能进 top-5？

答案在 SOLUTION，但**自己数出来的印象完全不一样。**

## 第 2 步：向量多了之后（5 分钟）

36 条记忆用精确检索就够了。但真实的记忆库是几十万条 ——
到那时候「全部算一遍」也成了瓶颈，这才是原书这个实验真正的主题。

```bash
python3 agent.py ann
```

它会生成 2000 条合成记忆、嵌入（约 30 秒，之后有缓存），
然后对比三种索引。两个 ANN 索引都在 `ann.py` 里，一共不到 120 行。

### 先猜

投影树（ANNOY 的思路）和可导航图（HNSW 的思路），
在 2000 条这个规模上，哪个能赢精确检索？

### 👀 你会看到

```
  方法                        建索引      每次查询    召回率      访问向量数
  exact (brute force)         0 ms    0.120 ms   1.000    2000/2000
  tree  trees=1  leaf=32     31 ms    0.019 ms   0.204      31/2000
  tree  trees=5  leaf=32     14 ms    0.077 ms   0.556     141/2000
  tree  trees=20 leaf=32     67 ms    0.295 ms   0.924     455/2000
  graph deg=16 ef=10        171 ms    0.227 ms   0.980     171/2000
  graph deg=16 ef=50        171 ms    0.927 ms   1.000     461/2000
  graph deg=16 ef=200       171 ms    4.542 ms   1.000    1142/2000
```

### 💡 学到什么

**「访问向量数」是解释其他三列的那一列。**

精确检索访问 2000 个 → 召回率必然 1.000。
ANN 的全部本事就是**少看一些**：看得越少越快，也越容易漏。
`trees=1` 只看 31 个（1.5%），所以快 6 倍，所以召回率只有 0.204。

> **这张表里没有「哪个更好」，只有「你想在哪一点上停」。**
>
> 而且请注意那些**绝对值**：`tree trees=20` 每次 0.295ms，
> **比精确检索的 0.120ms 还慢**，召回率还只有 0.924。
> 在这个规模上它是纯亏的。第 4 步会告诉你什么时候不亏。

## 第 3 步：一个调参数完全没用的坑（3 分钟）★★

```bash
python3 agent.py trap
```

图索引有个参数 `ef`：候选队列多大，也就是「允许同时记住几个暂时最好的」。
教科书说 ef 越大召回率越高。

这一步交叉测两个变量：**建图要不要加反向边**（`ann.py` 里一行），
以及**语料是分布均匀的、还是塞满近重复的**。
每一格换 20 个不同入口点各测一遍。

### 先猜

哪一格的 ef 会失效？

### 👀 你会看到

```
  语料：分布均匀（最近邻相似度中位数 0.8646）
    只连「我的近邻」      卡死  0/20   召回率不足  0/20   min 1.000
    再加上反向边          卡死  0/20   召回率不足  0/20   min 1.000

  语料：大量近重复（最近邻相似度中位数 0.9043）
    只连「我的近邻」      卡死  2/20   召回率不足 20/20   min 0.080  ☠
    再加上反向边          卡死  0/20   召回率不足  0/20   min 1.000
```

### 💡 学到什么

**四格里只有一格塌了**，而且塌得很彻底：20 个入口点**全部**达不到 1.000，
其中 2 个把 ef 从 10 开到 200 **一个数都不动**，召回率 0.080。

一行代码（加反向边）把 `20/20 不足` 变成 `0/20`。

> **一个 kNN 图不等于一个可导航的图。** 只连出边，搜索会卡在起点那一小片里出不来
> —— 它访问的向量确实变多了，多访问的都是同一片里的。
> HNSW 论文里那些看起来多余的设计（双向连接、多层入口），解决的正是这件事。

**但真正该带走的是「均匀」那两行：这个 bug 根本不出现。**

而真实的记忆库**就是**近重复那一份 —— 同一个偏好在不同会话里被反复记下，
措辞略有不同。**实验 3-1 的 `remember_all` 产出的正是这种东西。**

> ☠ 所以这个 bug 会**通过你的测试、然后在线上炸**。
> 不是因为它难，是因为你的测试数据太干净。而且它**不报错**。

## 第 4 步：ANN 从多大规模开始才划算（2 分钟）

```bash
python3 agent.py scale
```

```
    向量数      精确 ms/次    投影树20棵     谁更快
      2000     0.169 ms     0.311 ms    精确快 1.8×
     10000     1.327 ms     0.508 ms     树快 2.6×
     50000     6.307 ms     1.180 ms     树快 5.3×
    200000    27.322 ms     1.230 ms    树快 22.2×
```

**精确是 O(N)，树是 O(log N) —— 两条不同斜率的线，有一个交点。**

交点大概在一万条附近。左边用 ANN 是纯亏：多几百行代码、多一份索引内存、
召回率从 1.000 掉下来，换来的是**更慢**。

> 实验 3-5 那 36 条，和这里的 2000 条，**都在交点左边。**
> 先量一下你的 N 在哪边，再决定要不要上 ANN。

## 自己动手

### 练习 1 ⭐ 换模型、换语言
`MODEL` 改成 `bge-m3`，`LANG` 改成 `"en"`，四种组合都跑一遍 `compare`。
花生过敏那条，有几种配置能进 top-5？

### 练习 2 ⭐⭐ 把那条捞回来
不换模型、不换算法，只改**问题**。你要怎么问，才能让花生过敏进 top-5？
（提示：实验 3-5 的 `expanded` 模式在做的就是这件事。）

### 练习 3 ⭐⭐ 混合检索
把稀疏分数和稠密分数**加起来**（先各自归一化），再取 top-5。
召回率变了吗？这就是原书 3-6 `retrieval-pipeline` 的核心想法。

### 练习 4 ⭐⭐⭐ 让投影树的召回率上去，但别变慢
`ann.py` 的 `forest_query` 现在只走到**一个**叶子。
真正的 ANNOY 会用优先队列同时探索多个分支。加上它。

### 练习 5 ⭐⭐ 复现那个坑，然后修好它
`CORPUS_N` 调到 500 再跑 `trap`：坑还在吗？为什么？
然后不加反向边，只增加入口点个数 —— 能不能修好？
